### 2026-10-12 — task 6.2: map state over sockets
- **Tasks:** 6.2
- **Branch:** `feature/6.2-map-streaming` — done
- **Decisions / deviations from the plan:** a new API slice `mapview` (`MapViewService`) reads the player's map: `GET /api/v1/map?minX&minY&maxX&maxY` and the socket event `get-map` return only the cells in the player's knowledge (`known_points`; unknown cells are absent, which is the fog of war) plus the real cells of their own bots and bases, each cell with what the renderer needs (owner, chassis, module icons, damage, item kind, deposit capacity), and the live areas; a range is at most `MAP_VIEW_MAX_SIDE` (96) cells per side. `GET /api/v1/map/bots/:botId` gives the cell of an own bot (the client centres the map on the base). Streaming: `MapStreamer` turns the engine's `vision` batches into `map-cells` pushes to the owner's room and an own bot's `BotMoved` event into two cells (old one empty, new one holding the bot). The engine now announces a player's live areas as the engine event `live-areas` whenever they change (`LiveVision.announceAreas`), which the API keeps in `LiveAreaRegistry` and forwards as the socket event `live-areas`; the client colours cells live by area containment. Snapshots are stamped in ms of game time (`seenAt`), not ticks. On the client the map lives in a `MapStore` (outside Redux: batches arrive often and only the canvas reads them) filled by `useMapStream`; `TileLoader` asks for 32×32 tiles on screen once each and again after a reconnect or a `ScanCompleted` event; `MapCanvas` wires the renderer to pan (drag), zoom (wheel) and cell inspection (click). The game page shows the map beside the terminal until the window manager (6.10) replaces that layout. `radio-changes` already feed the signal bars and hatching (only changes are pushed, so a bot's signal shows once it first changes).
- **Open points:** the initial signal of every bot is not available to a client that connects later (needs a link-status endpoint, with 6.5); the engine's in-memory knowledge can be a write-behind flush ahead of the database for non-live cells; the stale-bot variant (§6.3) is drawn only when the data says so (not sent yet).
- **Next step:** task 6.10 (window manager), then 6.3, 6.4, 6.5, 6.7, 6.8.
- **Verify with:** `npm run typecheck && npm run test:coverage`

### 2026-10-12 — task 6.3: physical storage GUI
- **Tasks:** 6.3
- **Branch:** `feature/6.3-storage-gui` — done
- **Decisions / deviations from the plan:** the storage window needs manual actions, which 6.7 builds on, so the engine-side pipeline is built here: `EngineCore.manual(userId, botId, fn, args)` (engine port op `manual`, `POST /api/v1/bots/:botId/actions`). A manual action is a call of the script API done by hand and follows the rules of a script's call: control of the bot through the radio network (`ensureControl`), a working processor (else `NO_MODULE`, so a bot without one cannot be controlled by hand), the module the call needs (else a 400), the same per-tick ops budget and turn order (it sits in the same backlog as the scripts' calls), the same delay (the bot is busy for the ticks the action takes, so one bot does one manual action at a time, like a script that waits for each answer), and the answer is the one a script gets (`{ ok, data }` or `{ ok: false, code, msg }`). `sleep` and unknown names are refused. The eight categories and their switches (global AND personal) are 6.7 / 6.8 and will be checked in `EngineCore.manual`. `GET /api/v1/bots/:botId/storage` (`StorageViewService`) gives the working storage capacity and use, the resource stacks, the carried items and the load; the window (`kind: 'storage'`, one per bot) polls it every 3 s because scripts change it too, shows resources and items, and offers "take the item ahead" (`take`) and "drop the last item ahead" (`drop`). The load test of the engine was made independent of the speed of the machine (a virtual clock for the scheduler's cutoff, a generous slice for the honest bots); it had started to fail on CI runners.
- **Open points:** the Cypress spec for take/drop is part of 6.6; `store` / transfer between storages (category Logistics) do not exist in the script API yet.
- **Next step:** task 6.4 (factory GUI).
- **Verify with:** `npm run typecheck && npm run test:coverage`

### 2026-10-12 — task 6.5: bot terminals in windows
- **Tasks:** 6.5
- **Branch:** `feature/6.5-bot-terminals` — done
- **Decisions / deviations from the plan:** `connect` (server side done in 5.9 / 5.13: password, lockout, wireless adapter, range and relay chain through the radio network) now opens a **terminal window of its own** (`terminal:<botId>`, the stored session `connect` created is passed in the window's params) instead of replacing the base terminal in place; the old stack of terminals and the "Back on …" line are gone. `exit` in a connected terminal closes its window and ends its session (so does closing the window by its button); `exit` in the base terminal still signs out. `useTerminal` takes `{ connection, onConnected, onExit }`; without `connection` it is the base terminal. Link state: the typed game events (`LinkLost`, `LinkRestored` with `missed`) now come to the client as `game-event` (the event union moved to `lib/utils/interfaces/events.ts` and the API re-exports it, so both sides share one definition); when the link drops the terminal shows "Connection interrupted", disables its input and refuses to send anything but `exit`; when it returns it says so, with a summary of the scans and events missed, and the same session goes on (that is the automatic resume: nothing is reopened). A command refused with `NO_SIGNAL` also marks the link down, in case the event was missed.
- **Open points:** a client that connects while a bot is already out of reach does not know it (only changes are pushed) until a command is refused; terminals are not reopened after a page reload (the sessions stay stored on the server, the history is in the log).

- **Branch:** `feature/6.8-settings` — done
- **Decisions / deviations from the plan:** a new slice `settings`: tables `game_settings` (key/value rows; today one row, `manualCategories`) and `user_settings` (`manual_categories` JSON, `reduced_motion`, cascade-deleted with the user), a `SettingsRepository` port with a Prisma adapter, `SettingsService`. A switch nobody set is on, so a category added later starts on (`withDefaults`); effective availability is `global AND personal` (`effectiveSwitches` in lib, shared with the client). API: `GET/PATCH /api/v1/settings` (the player's settings, the game's, and the effective switches) and `GET/PATCH /api/v1/admin/settings` (role `admin`; the plan's 2FA and audit log for admin endpoints come with Phase 9). **Enforcement is in the engine, not the UI:** `EngineCore.manual` checks the category of the action (`categoryOfFunction`: movement, combat, extraction, fabrication, maintenance; scan, view, where-am-I and reading files are observation and have none) and `EngineCore.act` checks the category of the world action (`ACTION_CATEGORIES`: crafting, research, learning and assembling are fabrication; repair and disassembly maintenance; connect and adopt communication), through a `ManualPolicy` port that `SettingsService` implements; a refusal is `403 MANUAL_CATEGORY_DISABLED`. Scripts never go through these two doors, so they are never restricted. The categories logistics and trade have no actions yet. The profile also holds `reducedMotion` (null = follow the system), which the animations of 6.11 read. The settings window (`kind: 'settings'`, from the toolbar) has the player's eight switches (a category the game switched off is marked), the motion choice, and for an admin the game's switches.
- **Findings:** the lookup table of categories was an object, so `categoryOfFunction('constructor')` returned a function; it is a `Map` now (the test for it found the bug).

### 2026-10-12 — task 6.7: bot control panel
- **Tasks:** 6.7
- **Branch:** `feature/6.7-control-panel` — done
- **Decisions / deviations from the plan:** the panel is generated from the script API's own function catalog (`SCRIPT_FUNCTIONS` in lib), so every action a script can do is there and a new function appears without UI work: `actionGroups(moduleTypes)` takes the functions the bot's modules grant ("no module, no function"), leaves out `sleep`, and groups them by `categoryOfFunction` — observation first (always on, no switch), then the eight categories in order; a category the bot has no action for is not shown. Each action is a row of inputs built from the argument kinds (numbers, text, left/right, a list of the bot's modules for `moduleId`) and a button; `buildArgs` turns the typed text into the arguments of the call and names the argument that is missing or not a whole number before anything is sent. A category switched off in the game or by the player stays visible, marked, with its rows disabled; the engine refuses it too (6.8). The actions go as manual actions of the engine (6.3): same rules as a script's call (ops budget, module, delay, link, category), same answer, shown under the row. Clicking one of the player's own bots or bases on the map opens its panel (the map cells now carry the bot id); the toolbar opens the base's. The factory and storage windows stay the friendly front of the fabrication and logistics actions; connect, ping, sendMessage and adopt are terminal commands (6.5) and are not script-API functions yet, and trade comes with Phase 10.
- **Next step:** task 6.9 (tutorial), then 6.11, 6.6, 6.12.
- **Verify with:** `npm run typecheck && npm run test:coverage -w client`

### 2026-10-12 — task 6.9: tutorial
- **Tasks:** 6.9
- **Branch:** `feature/6.9-tutorial` — done
- **Decisions / deviations from the plan:** seven steps (lib `TUTORIAL_STEPS`): open the terminal, list the modules, scan, write a script, run it, craft a module, assemble a bot. A step is not ticked by a click but by **what the player has really done**, read from what the game keeps (`PrismaTutorialFacts`: a terminal session exists; a `modules` input in the terminal log; more known cells than the base; a `.js` / `.ts` file on a drive of their bots; an execution; a part, a factory job or a bot assembled; a bot of their base), so it works the same whether they did it by terminal, GUI or script, and a step once done stays done (`TutorialService`). Progress (`status`: active / skipped / completed, and the steps done) lives in the user's profile: a `tutorial` JSON column on `user_settings`. API: `GET /api/v1/tutorial` (also records what is newly done), `POST /tutorial/skip`, `POST /tutorial/restart` (from the settings window: starts over and notices at once what was already done). Engine events were not used for this: the facts are durable and a missed event would lose a step. The overlay (`TutorialOverlay`) is a checklist at the bottom right that asks every 4 s; the toolbar button for the step is outlined; skipped / completed tutorials show nothing (a completed one shows a short note to a player who has just finished it). Cypress `tutorial.cy.ts`: steps ticking as the player types `modules` and scans from the control panel; skip, reload, restart.

### 2026-10-12 — task 6.11: map animations
- **Tasks:** 6.11
- **Branch:** `feature/6.11-map-animations` — done
- **Decisions / deviations from the plan:** the typed game events reach the map through `MapStore.publishEvent` (from the socket's `game-event`); `AnimationSystem` (framework-free, `features/map/animation/`) turns them into effects that the renderer draws over the cells each frame and asks for the next frame while anything moves. Implemented effects (design §15.2): a move is a **tween** (the bot is drawn between its old and new cell, `TWEEN_MS_PER_CELL` per cell — the event does not carry `ticksPerCell`, so the speed is a client constant), a shot is a tracer with a muzzle flash and a spark, a hit is a floating damage number, mining throws dust and a depleted deposit pops a ring, a scan sends a radar pulse (radius from the number of cells), a damaged module flashes and a broken one smokes, losing and regaining the link pulse a red and a green ring, low energy blinks a ⚡. **Cap and detail:** at most 64 effects alive (the oldest go first); at low zoom (the renderer's level-of-detail threshold) nothing is started. **Reduced motion:** `useReducedMotion` takes the player's setting (6.8) and, while there is none, the system's `prefers-reduced-motion`; then a move is instant and every effect is replaced by a still outline of the cell for 0.6 s. Events without a place (a scan names only a bot) are located through `MapStore.locate`. **Not animated, because the engine publishes no event for them yet:** craft / assemble (build-up and boot), repair, disassemble, adopt / control lost; they come with the events (§24.1). The renderer takes the system as an option, so the ambient scene of the landing page can reuse it.
- **Next step:** task 6.6 (Cypress for every Phase 6 screen), then 6.12 (Cypress for the gameplay journeys).
- **Verify with:** `npm run typecheck && npm run test:coverage -w client`

### 2026-10-12 — task 6.6: end-to-end tests of the Phase 6 screens
- **Tasks:** 6.6
- **Branch:** `feature/6.6-phase6-e2e` — done
- **Specs:** `map.cy.ts` (own base in the middle, fog of war before and after a scan, pan with negative coordinates, zoom, a drawn canvas, another player's map), `windows.cy.ts` (toolbar, focus order, drag and place memory across a reload, resize and minimum size, close and reopen), `storage-factory.cy.ts` (storage of the base; a worker with a manipulator takes the item ahead and drops it; crafting three modules in the factory window, finishing and assembling a bot), `control.cy.ts` (actions by category, argument checks, moving a bot from its panel opened from the map, a personal switch that the engine enforces too, an admin's global switch as a ceiling, no manual control without a processor), `connect.cy.ts` (a window of its own, exit, out of range, a relay chain, "Connection interrupted" and resume in the window of a bot, a foreign bot's password, adopt, lockout), `radio.cy.ts` (weaker signal bars as a bot walks away, "connection lost"), `resilience.cy.ts` (reload, an expired access token, no session). The whole suite has 91 tests and runs in about 2.5 minutes.
- **Support:** Cypress commands `assembleWorker` (crafts through the API and assembles a bot) and `teleportBot` (puts a bot on a cell in the database and makes the engine read the world again with a scan of the base, which also makes the radio network recompute and tell the link events); tasks `placeBotAt`, `positionOf`, `placeItemAhead`. The e2e API runs with `BOT_ATTEMPT_DELAY_MS=100` and `BOT_LOCKOUT_FAILURES=3`.
- **Bugs the specs found, fixed here:** (1) `connect` to one of the player's own bots did not check the radio link of that bot (relays included), only the foreign ones were checked by range: `TerminalService.openConnection` now asks the link gate for an own bot. (2) The base terminal took itself for "out of reach" when `connect` was refused with `NO_SIGNAL` for the target; only the terminal of a connected bot judges its own link. (3) A pointer that the browser does not know (synthesized) made `setPointerCapture` throw in the map and the windows: `capturePointer` ignores it.
- **Not covered, with the reason:** `sendMessage` and `ping` (not implemented: the communication category has only terminal commands so far); relay towers and "a tower out of oil" (relays are the player's own bots; there are no towers); the socket reconnect and two tabs on one account (Cypress cannot cut a WebSocket or open a second tab; `realtime.gateway.test.ts` and the socket tests of `api.int.test.ts` cover the rooms per user); buffered scans appearing with their real times and the summary of missed events (a bot out of reach cannot be driven from a window; unit tests of the radio buffers and of `useTerminal`); adopting a *stale* bot of a lost base (stale bots are Phase 8); the pinned state of the bars of a client that connects while a bot is already out of reach (only changes are pushed — an open point of 6.2).
- **Next step:** task 6.12 (Cypress for the core gameplay journeys), then the exit criteria of Phase 6.

### 2026-10-12 — task 6.12: end-to-end tests of the core gameplay journeys
- **Tasks:** 6.12
- **Branch:** `feature/6.12-gameplay-e2e` — done
- **Spec:** `gameplay.cy.ts`, eight journeys that run real scripts in the terminal of a bot assembled through the API: a **mining loop** (the ore arrives in the bot's storage), a **deposit that runs out** (a partial yield, then `EMPTY` for the same miner and for a second bot that mines it by its coordinates, and the cell is empty), a **bot with no energy** (`NO_ENERGY` as an answer, not an exception), a **shot at a bot of the player's own** until a module breaks, with the gun's `COOLDOWN` in between (friendly fire), a **scanner in live or in one-time mode** (`NOT_LIVE`, `BUSY`), a **live area** (a bot of another player that comes close is seen by the owner's live scanner, and is an ageing snapshot after `disable`), **learning a blueprint** found in the world, and a **corpse base restored** by a repair bot that is started in reach and mends the adapter out of reach. The 99 tests of the suite run in about 4 minutes.
- **Support:** commands `writeScriptFile`, `eventually` (the engine writes the world behind, so a task that reads the database asks again); tasks `placeResourceAhead`, `removeCell`, `cellAt`, `stockOf`, `moduleStates`, `damageAllModules`, `setModuleProps`; `assembleWorker` and `finishFactoryJobs` take the base by id (a player can have two bases).
- **Findings:** the recipes list was not refreshed after learning a blueprint (a `Recipes` tag now ties the list to `learn`, and the factory window polls it); a gun's chance to hit falls with the distance, so the shooting journey fires several times.
- **Not covered in the browser, with the reason:** a script acting on a stale scan and re-scanning (the script-API results `EMPTY` / `BLOCKED` / `GONE` are covered by `script-api.test.ts` and the handler tests; a browser version needs the engine to re-read cells a test changed in the database, which made it flaky — the deposit-runs-out journey shows the same `EMPTY` answer), artillery splash, ammunition and armour numbers (the unit tests of `combat-handler` and `weapon-module` own them), the visible animation of a bot's movement under a live scan (the animation system is unit-tested and the canvas is not readable beyond "something is drawn"), and the engine's turn order between two scripts.
