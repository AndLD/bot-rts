# Migration to 0.2.0-dev.2 from 0.2.0-dev.1

The second development version of `0.2.0`. It fixes what a project found taking `0.2.0-dev.1` and adds two optional document roles. The note of the final version, `0.2.0.md`, is written with that version and tells the whole story from `0.1.2`, so a project that takes `0.2.0` after this one reads that note, and this one stays as it is. A project that takes this version from `0.1.2` or earlier reads the note of `0.2.0-dev.1` first: it holds the required actions of the big changes (the phase folders, the issue queue, the reports, the migration scripts).

## What changed for a project

- **`migrate` finds the version a project was at after the `sync` of an older version** (issue I-2, report 61). The `sync` of a version before `0.2.0` replaces the version of the lock and keeps no record of where the project was, so `migrate` counted it as `0.1.0`: the start recorded for `harness rollback` named `0.1.0`, and the notes of versions the project had taken were printed again. `migrate` now reads the version from the lock of the last commit when the lock has no record. A project that takes this version with the `sync` of `0.2.0-dev.1` is not affected.
- **The migration puts the phase folders and the issue queue into the layer map of a project with its own layers** (I-3, report 62). A project whose `layers` role lists `<phases>/phase-*.md` but not the folders had 30 lines of `check layers` after the migration. The script of `0.2.0` (run again by every development version) adds `<phases>/phase-*/**` and `<issues>/**` to the layer that claims the one-file phases, unless a layer claims them already, and prints what it added; a project that did this by hand is left as it is.
- **The migration keeps a task that a branch claims** (I-4, report 63). A task in hand (claimed by a draft pull request) that was still ⬜ was read as a defect that had not started and became an issue, and its phase was closed without it. The script now keeps a ⬜ task for which a branch `<type>/<task id>-<slug>` exists, and the procedure `update-framework` says to set the task in hand to 🟡 before the `sync`.
- **`check probes` names the columns of the probe table** (I-5, report 64). A table of the older shape (`Id | Scenario | Expected`) gave a line for each probe; it now gives one problem that names the columns it has and the ones it needs.
- **The bootstrap writes a risk register and the index of design records** (4.7). Two scaffold templates, `risk-register.md` and `rfc-index.md`, at two new optional roles of the document map, `documents.riskRegister` and `documents.rfcs` (the starter values put them in a cross-cutting folder of the plan). They are written only when a project is bootstrapped; a project that exists is untouched, and no check reads them.

## Required actions

1. **Take the migration.** Set the task you have in hand to 🟡 in its task file, then run `sync` on a branch of its own (it refuses on a protected branch and with uncommitted changes); `node harness/tools/harness.mjs migrate` where the `sync` of your version did not start it. The script of `0.2.0` runs again and adds the plan folders to your layer map where it has one (it prints what it added, or the line to add by hand).
   Check: `node harness/tools/harness.mjs check generated` exits 0, and `migrations.version` in `harness.lock.json` is `0.2.0-dev.2`.
2. **Make the table of your probes `Probe | Scenario | Areas | Words read at the last review`**, when your harness-review bindings have a probe table of another shape (for example `Id | Scenario | Expected`): the third cell of a probe names its areas of the migration notes (the list is in `harness/migrations/areas.json`), separated by commas; move what the other columns held (the expected behaviour) to a list below the table. Copy the table of `harness/core/templates/scaffold/harness-bindings.md` as the starting shape.
   Check: `node harness/tools/harness.mjs check probes` exits 0.
3. **Have every file of the plan in a layer.** When the script printed a line telling you to add a glob to your layers by hand, or your layers claim the phase folders and the queue in another way than a glob of the one-file phases, add `<phases>/phase-*/**` and `<issues>/**` to the layer of your plan state.
   Check: `node harness/tools/harness.mjs check layers` and `check paths` exit 0.

## Optional actions

- Give a project that exists a risk register and design records: set `documents.riskRegister` and `documents.rfcs` in the profile file (the starter values are in `harness/profile/starter.json`), copy `risk-register.md` and `rfc-index.md` from `harness/core/templates/scaffold/` to those paths, and run `sync --local`.
- Run `node harness/tools/harness.mjs probes 0.2.0-dev.1 0.2.0-dev.2` and the probes it lists as separate sessions. Running them is the project's choice; a profile switch that lets a project say so (`auto`, `ask`, `disabled`) is an open issue of the framework (I-6).

## How to verify

`node harness/tools/harness.mjs check all` exits 0, your gate (lint and tests) passes, and `version` in `harness.lock.json` is `0.2.0-dev.2`. `node harness/tools/harness.mjs rollback` undoes the migration commit if a step cannot be done now.
