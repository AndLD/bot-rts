### H-20261030-01 — The framework's staging folder sits where no code check looks

- **Severity:** 🟠 · **Dimension:** D7, D14 · **Effort:** S · **Export impact:** blocker (the framework's own tests are its proof)
- **Evidence:**
  - Design §2 and 17.3 put the framework source in `docs/harness-framework/framework/`. Its tools carry `node --test` tests next to them
    (design §2, `tools/lib/`), and 17.7 "moves the tests" there.
  - `.prettierignore:10` ignores `docs`. `package.json:34` runs `node --test scripts/*.test.mjs` only. ESLint runs per workspace.
  - Gate replay (section 3): two staging files give "format changed files" (a no-op, since Prettier ignores `docs`) and the generated files.
    No test runs.
  - CI's `static` job runs `npm run test:scripts`, with the same glob.
  - Design §10 says each task keeps this repository green with "the documentation check, lint, the script tests and the coverage gate"
    (`design.md:667`). None of these reaches the staging folder.
- **Why it matters:** from 17.7 to 17.14, ten pull requests would move tested tools into a folder whose tests nothing runs, here or in CI,
  until 17.15 publishes the framework. A green CI would say nothing about them, and non-negotiable 1 would hold on paper only.
- **Fix (17.3):** the skeleton wires the folder into the checks.
  - `test:scripts`, or a new `test:framework` in the `static` job and in the local gate, runs `node --test` over the staging folder.
  - `.prettierignore` stops ignoring `docs/harness-framework/framework/` (Markdown stays ignored).
  - `planGate` treats the folder as tooling that runs those tests, not as documentation.
  - 17.3's acceptance gains: a failing test in the staging folder fails CI and the push.

### H-20261030-02 — The local gate is bypassed in worktrees, against a rule no mechanism holds

- **Severity:** 🟡 · **Dimension:** D7, D14 (environment collision), D15 · **Effort:** M · **Export impact:** helps
- **Evidence:**
  - `docs/testing/known-issues.md:24-25`: "Push again; never `--no-verify`."
  - `.githooks/pre-push:5`: "Skip once with `git push --no-verify`."
  - `scripts/hook-guard-bash.mjs` does not refuse the flag, and no row of `rule-checks.md` holds the rule.
  - `phase-16-log.md:68, 122, 187, 217, 257, 277`: six pushes of Phase 16 used `--no-verify`, "the main checkout holds the database ports
    (see 15.12)", with checks run by hand.
  - 15.12 made the ports configurable per worktree (`.env`, `docs/testing/README.md:89-97`), but no session set them.
- **Why it matters:** the local gate exists to catch a failure before CI does. A session in a worktree turns it off whenever the main
  checkout runs its database. In Phase 17 that is every push that changes `package.json` or `harness/` (H-04). The rule says the opposite of
  the hook, so a session cannot tell which one holds.
- **Fix:**
  - **Phase 12 task.** The pre-push setup (it stays in this repository as `hooks.prePushSetup`, design §3.4) uses a database that already
    answers on the configured port. If none answers and the port is taken, it fails with the two lines to put in `.env`, not with a Docker error.
  - **The one rule** is written once: the bypass is the owner's, for an emergency, and it is recorded in the log. A rule-map row holds it.
  - **17.11** adds the guard: the Bash guard refuses `--no-verify` from the agent, while the owner keeps the terminal.
