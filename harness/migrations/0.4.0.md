# Migration to 0.4.0 from 0.3.0

The fourth minor version. It changes how a flow starts its workers (the executor `cli` and an order of executors, the flow's `permissions` given to the sessions it starts, the setting `commands`, and a level for a change of the meaning of a contract), adds three optional pieces to a project's tools (the off-plan record, `harness plan-write`, `harness review measure`) and one check (`markers`), changes the CI template, and fixes a few things found in use (I-7, I-14, I-16 to I-19, I-22). **No migration script runs**, and nothing is required of a project beyond taking the version; the choices below are the project's.

This note is the whole story from `0.3.0`. It replaces the note of the development version (`0.4.0-dev.1`): `harness migrate` leaves that one out when this note is among the notes to read. A project that took `0.4.0-dev.1` has done its required actions already. Two things the development note left unclear are said here: **how a project gets the CI template's change** (not by `sync`; see "CI template") and **where a project finds the format of an off-plan record** (see the optional action "Turn on the off-plan record").

## What changed for a project

- **Flows: executors and permissions** (a change of the meaning of the procedure `run-flow` and a minor addition to the agent-runtime contract, still version 2: an adapter without the additions still conforms).
  - The executor `cli` (a worker on the runtime's command line) joins `session` and `manual`, in an order: `session` is the default, `cli` its fallback for one step, `manual` the fallback of that; `subagent` stands outside the order. `harness flow dispatch` prints the next executor beside every start, and `harness flow check` refuses a "step started" line on another executor than the step's own without the fallback and its reason. A log line written before reads as before. The Claude Code preset splits its `session` executor into `session` (the desktop app) and `cli`; a project's own runtime adapter that offered the command line as a means of `session` may move it to a `cli` executor (optional).
  - A session a flow starts gets the flow's `permissions` mode through the app's `permission_mode`; the app's start takes no tools, so `harness flow dispatch` names the tools of `allow` for the project's settings, which the owner adds. A project whose flows set `permissions` and start sessions adds those tools to `.claude/settings.json` (or the local file), or its unattended sessions are refused the tools the mode does not allow. The "step started" line gains `· **Permissions:** <mode>` when the flow sets a mode.
  - The flow's `levels` gain the kind `contract.change` (D3 by default): a flow decides a change of the meaning of a contract below its `askAt` and asks from it up (with the default `askAt` D2 it still asks the owner); in seamless mode it decides and lists it in the digest. A flow that must keep asking for every contract change in seamless mode cannot: run it in brainstorm mode with `askAt` at D3 or below. A change of the meaning of a core rule or a non-negotiable stays the owner's.
  - A new flow setting `commands`: `any` (default, as before) or `plain` (workers write files with the edit tools, no heredocs or subshells, so a strict permission mode asks less). `harness flow check` refuses another value.
  - The usage table of the preset is calibrated for Sonnet on Pro (`consumer-take`, `cut`, and a row for `tasks`); `flow estimate` and `gate` give smaller estimates. Nothing to do.
  - `harness flow status` reads a consuming repository's pull request as the take of a version only when its title names the version as a whole token (I-14).
- **The off-plan record** (optional). A project with the new profile role `paths.offPlan` keeps one fragment per pull request for work that no task covers; `harness plan log --off-plan` prints them and `harness check off-plan` (part of `check all`) fails on an unreadable record and on merged pull requests with neither a `Plan: <task id>` line nor a record, counted from the commit that added the folder's `README.md`. A project without the role is unchanged. A new bootstrap now creates the folder and its `README.md` (I-22); an adopted project keeps its profile file as it is, and turns the record on by the optional action below.
- **`harness plan-write on|off|state`** (optional). A new optional logic role `plan-write` of the runtime contract: the Claude Code preset writes `Edit(<folder>/**)` rules into `permissions.allow` of the tracked `.claude/settings.json`, so an agent writes the plan's files without a prompt. A new bootstrap turns it on (`--no-plan-write` leaves it off); a project that took an earlier version runs `harness plan-write on` once if it wants it.
- **`harness review measure`** (optional) prints the measurements of a harness review that a script can decide, against the ceilings of the project's harness review bindings, and exits 1 over a ceiling. The bindings stub has the new rows (all `—` until a review proposes ceilings); a project reads the rows it wants into its own bindings.
- **`harness check markers`** is part of `harness check all`: it fails on a line that starts with 7 or more `<` or `>` and a space or the end of the line, in a tracked Markdown or JSON file (a committed conflict marker). `harness branch update` leaves the merge in progress, naming the file, instead of committing a file that holds such a line. A file that holds one on purpose writes it inside a line or an indented block.
- **CI template** (I-18): the `pr-title` job also runs on `workflow_dispatch` (it reads the title of the open pull request of the branch with `gh pr list`, and asks the `pull-requests: read` permission), so a pull request that the update workflow brings up to date no longer stays blocked on a skipped required check. **`harness sync` does not change a project's CI workflows**: the files of `.github/workflows/` are scaffolded, written once by the bootstrap and then the project's own (design §2), so the new job reaches a project only by the project's own change. The note of `0.4.0-dev.1` said `harness sync` brings it; it does not. A project tells whether it has the job by looking at its CI workflow (`.github/workflows/ci.yml`, or the file that holds its `pr-title` job) for three things of the template `adapters/host/github/templates/ci.yml` (the copy is `harness/adapters/host/github/templates/ci.yml` in a project that vendors the framework): (1) the trigger `workflow_dispatch:` under `on:`; (2) the `pr-title` job's condition `if: github.event_name == 'pull_request' || github.event_name == 'workflow_dispatch'`; (3) the job's own `permissions:` with `pull-requests: read`, and the step that, on a dispatch, takes the title from `gh pr list --head "$BRANCH" --state open`. A workflow that lacks any of them is changed by hand to match the template (the template has `<%= … %>` places for the profile's values, which a project replaces with its own, as its workflow already does). A project with no `pr-title` job in its CI workflow has nothing to do. The dispatch happens only when the project has the update workflow (`update-branches.yml`) and that workflow has no `AUTO_MERGE_TOKEN` of its own; a project that has no such workflow, or has the token, loses nothing by leaving its workflow as it is.
- **Git hooks**: `pre-push` and `pre-commit` use the worktree's own `harness.mjs` in a linked worktree instead of the main checkout's (I-19). Nothing to do.
- **Documents**: the procedure `release` and the releasing guide say to push the tag of a release or hotfix from a local branch at the merge commit, before the merge back (I-17); the notes of a migration say what they left out and `migrations/README.md` has the rules for notes (I-16). Nothing to do.

## Required actions

1. **Take the version.** Run `sync` on a branch of its own, then `node harness/tools/harness.mjs migrate` if the `sync` did not start it. No script runs; nothing else is required.
   Check: `node harness/tools/harness.mjs check all` exits 0, and `migrations.version` in `harness.lock.json` is `0.4.0`.
2. **If the project has a file that holds a line of 7 or more `<` or `>` characters followed by a space or the end of the line** (a document about merge conflicts, for one), write it inside a line or an indented block, or `check markers` fails.
   Check: `node harness/tools/harness.mjs check markers` exits 0. A project with no such file has nothing to do.

## Optional actions

- **Add the `pr-title` change to the project's CI workflow** (by hand; `sync` does not do it, see "CI template" above) if the project has the job and its update workflow dispatches CI: the `workflow_dispatch` trigger, the job's condition, its `pull-requests: read` permission and the dispatch step, as the template has them. Check: the three items of "CI template" are in the project's workflow, and the next pull request that the update workflow brings up to date shows the `pr-title` check as passed, not skipped.
- **Turn on the off-plan record.** (1) Add `paths.offPlan` to the profile file (`docs/development-plan/off-plan` is what `harness init` writes for a new project); (2) create that folder with a `README.md` in the format of the template, which a project has at `harness/core/templates/scaffold/off-plan-readme.md` when it vendors the framework (a detached project keeps it where its copy of the core is). The template's first line is a link back to the plan index written as `{{rel:paths.planIndex}}`: replace it with the relative link to your plan index, as the other files of the plan have; the rest is copied as it is. For a project bootstrapped on `0.4.0` the same file is already in the folder that `harness init` wrote, and that file is the format. (3) Run `harness sync`, then `harness check off-plan`. The record counts the merged pull requests from the commit that added the folder's `README.md`, so the earlier ones are not asked for. A record is one file per pull request, `<pull request number>-<slug>.md`: a title line `# <what the pull request did>` and the three fields `**What changed:**`, `**Why and who asked:**`, `**What it leaves to do:**`. Check: `node harness/tools/harness.mjs check off-plan` exits 0.
- Run `harness plan-write on` to let agents write the plan's files without a prompt. Check: `harness plan-write state` says it is on.
- Add the tools of the flows' `allow` lists to the project settings if its flows start sessions with `permissions`; set `"commands": "plain"` for flows whose workers run in a strict mode.
- Run `harness review measure` and read its rows into the project's harness review bindings.

## How to verify

```bash
node harness/tools/harness.mjs check all
node harness/tools/harness.mjs probes 0.3.0 0.4.0
```

The first exits 0 on a healthy project, and `version` in `harness.lock.json` is `0.4.0`; the second lists the probes whose areas this version touched.
