# Migration to 0.2.0-dev.3 from 0.2.0-dev.2

The third development version of `0.2.0`. It adds an optional backlog for feature requests (a place for proposals the owner has not approved), a switch for the probes of a migration, and stops copying the framework's own tests into a project. The note of the final version, `0.2.0.md`, is written with that version and tells the whole story from `0.1.2`, so a project that takes `0.2.0` after this one reads that note, and this one stays as it is.

## What changed for a project

- **A backlog for feature requests, beside the issue queue** (3.20, 3.21). The profile role `paths.backlog` names a folder (a project without the role has no backlog, and nothing below applies): an index of the proposed items that `harness plan summary` generates and the plan index counts on a line of its own, a file per item (`B-<n>.md`, from the new backlog template), and `archived/` for the promoted ones. The backlog is the place for what the owner has **not approved**: an item is `Proposed` (or `Promoted`), has no phase, no marker, no branch and no claim, and **is never started as it is**. Every item has a `Source:`, which is `report` followed by the link of each report that asks for it, `owner`, or `agent`; `check plan` fails on any other value.
- **The owner promotes an item into a task of a phase before anything is built** (3.21). `harness plan promote <B-n> --phase <n> [--agent <marker>] [--size <n>] --approved` writes the next task of the phase from the item (its title and description, its source, a link to the item), sets the item to `Promoted` with `Promoted to: <task id>`, moves it to the archive, and updates the size of the phase. An order of development, an execution order or a `Needs` that names a proposed item is a problem of `check plan`, and the phrases that approve phases and issues approve no item. **If you started a backlog with the first development version of this feature** (items with ⬜, 🟡 or ✅ and a `feature/B-<n>` branch), see the optional actions.
- **A report that asks for something new is a backlog item, not an issue** (3.20). `harness reports plan` has the relation `feature`, `reports candidates` compares the backlog too, and a report named in the `Source:` of an item counts as triaged. The procedures `triage-reports` and `change-plan` say so where the project has a backlog, and the answer to the report says that the request waits for the owner's decision. An issue that turns out to be a feature request moves there as a new item that names it (`B-1, formerly I-6`): the number `I-6` is never given again, and an order written by `I-6` resolves once the item is promoted.
- **`harness plan summary` creates the backlog of a project that sets the role later** (3.20). It writes the folder, its two indexes and the block of the plan index from the scaffold templates, once, and says so.
- **A profile switch for the probes of a migration** (3.22, report 65). `probes.run` is `auto`, `ask` (the default) or `disabled`, and the ignored `harness-profile.local.json` overrides it on one machine. The end of the output of `harness migrate` and of `harness probes` says what the mode asks of whoever takes the version, and the procedure `update-framework` follows it. No command starts a probe itself yet, so `auto` and `ask` are instructions: with `ask`, the one who takes the version asks the owner first and runs the probes only on a yes. This changes what a project's agent does when it takes a version: before, it ran every probe; now it asks.
- **`sync` no longer copies the framework's tests into `harness/`** (I-1, report 30). They prove the framework against its own repository, so in a project 20 of 428 failed for what the project does not have, and nothing in a project runs them. `framework.json` lists the file name endings a sync leaves out (`excluded`). The `sync` that takes this version is made by the tools of the version you leave, which still copy them; the next `sync` removes them, and `check vendored` accepts a copy that still holds them.
- **The session start prints a line about the backlog** where the project has one: how many proposals wait, and that none is started as it is.

## Required actions

1. **Take the migration.** Run `sync` on a branch of its own, as the procedure `update-framework` says (set the task you have in hand to 🟡 in its task file first). The script of `0.2.0` has no new step for this version.
   Check: `node harness/tools/harness.mjs check all` exits 0, and `migrations.version` in `harness.lock.json` is `0.2.0-dev.3`.

No other action is required: the backlog is optional, `probes.run` has a default, and the tests that remain in `harness/` harm nothing.

## Optional actions

- **Choose how the probes of a migration run.** Set `probes` to `{ "run": "auto" }`, `{ "run": "ask" }` (the default, when the key is absent) or `{ "run": "disabled" }` in the profile file, or only on this machine in `harness-profile.local.json`. Taking a version costs a session per probe that its areas touch, each reading thousands of words, so a project that does not want that sets `disabled`.
  Check: `node harness/tools/harness.mjs probes 0.2.0-dev.2 0.2.0-dev.3` ends with the line for the mode you chose.
- **Start a backlog.** Add `"backlog": "docs/development-plan/backlog"` (or another folder) to `paths` in the profile file, run `node harness/tools/harness.mjs plan summary` (it creates the folder and the block of the plan index), then `node harness/tools/harness.mjs sync --local` (the procedures `change-plan` and `triage-reports` now carry the backlog's text). A project with its own `layers` puts the folder in the layer of the issue queue. Move a feature request that is in your issue queue there by hand: a new item with `Status: Proposed`, `Source:` and `Formerly: I-<n>`, and remove the issue's file (the number stays taken). When the owner decides to do an item, `harness plan promote <B-n> --phase <n> --approved` makes it a task.
  Check: `node harness/tools/harness.mjs check plan`, `check layers` and `check links` exit 0.
- **Bring a backlog of the first development version up to date.** An item written with ⬜, 🟡 or ✅ fails `check plan` ("the status line must hold Proposed|Promoted"). Set an item nobody has started to `Proposed` and remove its `Agent` (a marker belongs to the task). For an item that was built or is in progress, run `harness plan promote <B-n> --phase <n> --agent <marker> --size <n> --approved` on a copy of it set to `Proposed`, then set the new task's status and move the item's log beside it, as this repository did for its first item. Remove a `feature/B-<n>-<slug>` branch name and a `Plan: B-<n>` claim from your habits: the claim is the task's.
  Check: `node harness/tools/harness.mjs check plan` exits 0.
- **Drop the copied tests now.** Run `node harness/tools/harness.mjs sync` again on a branch of its own; `find harness -name '*.test.mjs'` then prints nothing.
- Run `node harness/tools/harness.mjs probes 0.2.0-dev.2 0.2.0-dev.3` and the probes it lists as separate sessions, as `probes.run` says.

## How to verify

`node harness/tools/harness.mjs check all` exits 0, your gate (lint and tests) passes, and `version` in `harness.lock.json` is `0.2.0-dev.3`. `node harness/tools/harness.mjs rollback` undoes the migration commit if a step cannot be done now.
