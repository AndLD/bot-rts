# Phase 9 — Admin console (135 SP)

**Status:** 🟡 In progress · **Branches:** see the [implementation log](#implementation-log) · **Work log:** [phase-9-log](./work-logs/phase-9-log.md)

A new admin console, specified in design [§25](../game-design/25-admin-console.md), that lets admins supervise any player's
bots and resources, monitor the health, performance and load of the game, moderate players, and operate the world safely.
The starting point is only a few legacy API endpoints and no UI (design §25.1); the security hotfix for them is task 0.8.

**Priorities:** must — 9.1–9.6, 9.10, 9.13, 9.14, 9.15; should — 9.7, 9.8, 9.9, 9.12, 9.16, 9.17, 9.17a, 9.18, 9.19; could — 9.11, 9.17b. The phase depends on the engine and
the game event bus (Phase 5), the map renderer (Phase 6), the notification system (Phase 7) and the observability metrics
(8.3).

**Execution order:** 9.1 → 9.2 → 9.3 → 9.4 → 9.5 → 9.6 → 9.10 → 9.7 → 9.8 → 9.9 → 9.12 → 9.11 → 9.15 → 9.14 → 9.13 → 9.16 → 9.18 → 9.19 → 9.17 → 9.17a → 9.17b.

| 9.16 | **View as player** (design §25.2, added 2026-10-15 after the first tasks were done): an owner or an admin opens the game as a chosen player sees it, with the game's own screens in a read-only mode: the map with that player's fog of war and known cells, bases and bots, storage and factory, terminal history, the list and content of files, notifications, achievements and settings. | 9.17 | **Game clock foundation** (design §12.4, §25.3; replaces the first half of the earlier 9.17, 2026-10-15). Today the day is a constant (`DEFAULT_GAME_TIME`, 24 real minutes) imported by the time service and by the energy model, and every consumer reads time from the one injected `Clock`. This task makes the game's time a **runtime setting that every process follows**, without touching what must stay on real time. (a) A separate `GAME_CLOCK` token (a `Clock`) for the rules of the game (crafting and research timers, the factory's jobs, the day/night time, notification due times, the engine's own use of time); the existing `CLOCK` stays the real clock for sessions, JWTs, rate limits, bans, the audit trail and database timestamps. The sites that read the clock (about 87 files, 28 modules) are first classified in a table in `docs/testing/`, then moved one module at a time with their tests unchanged; a test fails when a new rule of the game reads `CLOCK`. (b) `GAME_CLOCK` is an offset clock (real time plus an offset); in production the offset is a constant 0 and cannot change. (c) A `gameTime` document in the game settings (day length, hours per day, spans, the anchor of the day cycle, the mode, the offset) replaces the constant: the engine thread receives it through a new `setGameTime` request (applied between ticks, like `control`; on every link: worker, Redis, disabled), API nodes follow it by reading the database about once a second and at once after a change, and every connected client is told of a change by a `game-time-changed` socket event (sent to all player sockets after the new settings are stored and applied, across nodes through the Socket.IO Redis adapter), and then reads `/game-time/current`, the factory and the storage again (the countdowns of the factory use the server's `now`); a tab that was offline reads them again when it reconnects, and the relative times of the notifications stay on the browser's real time. The tick loop stays on real time. (d) The defaults are the current ones, so nothing changes until a setting is changed. Includes: unit tests of the offset clock (never goes back, ignores the offset in production), contract tests of `setGameTime` on every link, an engine test (a craft finishes on the tick after an advance, the tick count is unchanged), an integration test (the API and the engine agree on the time after a change), a socket test (a connected client gets the event once per change and reads the time again), a test that sessions and logins are not affected, and the table of the classification of the clock's consumers | 8 | ✅ |
| 9.17a | **Game time controls in the console** (added 2026-10-15; needs 9.17): a **Game time** tab (owners and admins, any environment, a reason, audited, and online players are told with a notice) with a live preview of the clock, the day phase and the sunlight. **Time of day:** set it (for example from 05:00 to 16:30); the day cycle is re-anchored, so nothing else moves. **Day length:** any value from 1 minute to 24 hours (the default is 24 minutes; presets for 48 minutes, 6 h 30 min and 24 hours), changed **seamlessly**: the cycle is re-anchored at the moment of the change, so the time of day reads the same just before and just after and continues at the new speed (no jump). **Real-world sync:** the game shows the wall-clock time of a chosen IANA time zone (a 24-hour day, the zone's own daylight-saving changes included, computed from the zone's local time with `Intl` on the server and in the browser), and leaving the mode returns to the cycle at the current time of day. **Dev tool (non-production, `DEV_TOOLS_ENABLED`, owners):** advance the game clock by a step (1 minute, 1 hour, 1 day) so that timers finish without waiting; it only moves forward and the reset of 9.17b puts it back. Validation: lengths out of range, unknown zones and moves backwards are refused with a clear error. The solar panels, the night filter and the clock of the game follow the new settings at once. Includes: unit tests of the time functions with an anchor and with a zone (including a daylight-saving day), integration tests of the endpoints and of the propagation, the `authorization-matrix` entries, a Cypress spec (change the day length and see the clock continue, also in a second open tab without a reload; set the time of day; real-world sync with a zone; advance the clock and see a craft finish), and the pages of the admin documentation in English and Russian | 5 | ⬜ |
| 9.17b | **Dev tools: reset the database** (added 2026-10-15; non-production only, behind `DEV_TOOLS_ENABLED`, owners, a typed word and a reason, audited): with the world stopped (the engine pauses and flushes), every table of the game is emptied in an order that respects the foreign keys, the migrations stay, the root owner and the admin who pressed the button are kept (or recreated from `ROOT_USER_*`), the engine reloads an empty world, the game clock offset goes back to 0, and every other session ends. Includes: unit and integration tests against PostgreSQL (the order of the tables, what stays, the engine's reload), the `authorization-matrix` entries, a Cypress spec (reset and see an empty world), and the pages of the admin documentation in English and Russian | 3 | ⬜ |
| 9.18 | **Global feature switches** (design §25.3, Economy and balance, added 2026-10-15): the switches of whole features of the game, besides the categories of manual control that 9.8 moved to the console. A typed registry in `lib` lists them (each with its name, what it stops, and its default): the first set is sign-ups, deploying a base, creating and using API keys, spawn seeds and the public MCP/API access, and Phase 10 adds the market and the chat the same way. The state is stored in the game settings, read by every node (cached for a short time), and checked on the server by the use case that the feature belongs to (a refused request answers `FEATURE_DISABLED` with the feature's name, never a bare 500). A public status endpoint tells the client which features are off, so the screens hide or explain them. The Economy page gets a tab for them: each switch with a reason and an audit entry, and an owner/admin permission `balance.write` as for the categories. Switching a feature off never deletes data, never kills what is running unless the switch says so, and is shown to the players. Includes: unit and integration tests of every enforcement point, the `authorization-matrix` entries, a Cypress spec (switch sign-ups off and see the sign-up refused, switch a base deployment off, switch back), and the admin documentation in English and Russian | 5 | ✅ |
| 9.19 | **Data retention from the console** (design §25.3, Operations, added 2026-10-15): every retention job of the game can be switched on and off and tuned from the admin console, and all of them can be put back to their defaults with one button. The jobs: the steps of the data lifecycle job (terminal lines and their per-bot cap, security lines, ended terminal sessions, finished executions, notifications, expired logins and links, never-confirmed accounts, the notice and the erasure of inactive accounts), the history of the monitoring (fine and coarse series), the sign-in attempts, and the new **`player_activity` cleanup** (rows older than a configurable number of days, default 400, which the analytics of 9.11 never needed so far). Each job has a switch, its ranges and timeouts (days, caps, the interval of the job), its default, and its last run (how many rows it removed, when, whether it failed) on the Operations page. The values live in a `retention` document of the game settings (versioned in the audit trail with before and after), override the environment defaults, are read by the job at the start of every pass (no restart), and are validated: a floor for each range so that one slip cannot erase what the game needs (for example, sessions of a running script, the audit log is **not** a retention job and is never deleted), a typed word and a reason to switch on an erasure of accounts, and a refusal of values that are not numbers or are out of the allowed span. One "Reset all retention settings to the defaults" button (reason, audited) removes the overrides. Includes: the new cleanup step with its unit and integration tests, the settings store and its validation, the `authorization-matrix` entries (`balance.write`-level permission `ops.retention`, owners and admins), the tab of the Operations page, a Cypress spec (change a range, switch a job off, see the job obey on its next pass, reset), and the pages of the admin documentation in English and Russian | 5 | ✅ |
