## [0.5.0] - 2026-11-07

Migration note: [migrations/0.5.0.md](migrations/0.5.0.md)

### Added

- `harness flow audit <n>` reports where the tokens of a flow went (by tool, by shell command, by step and by session, the largest results, and the peak context of each session), from the transcripts of its sessions. It needs the new optional runtime role `transcripts`, which the Claude Code preset fills; a runtime without it says the audit cannot run. Nothing to do for a project that does not use it.
- the quiet variants of a stack's commands. The profile roles `commands.lintQuiet`, `typecheckQuiet`, `formatQuiet`, `testQuiet` and `testCoverageQuiet` (the same check with the output reduced to the failures and a summary), the optional stack-adapter role `quiet-commands` that gives them as defaults (both presets fill it), and a `quiet` variant of the test and lint steps of the local gate's plan, which the gate runs unless `--verbose` is given. The procedures cite the quiet variant of the quality gates; a project that sets none gets the plain command, so nothing breaks. A project takes the defaults by setting the roles in its profile file (the stack presets' values are in their manifests), and a project's own stack adapter may fill the role.
- output budgets for agents and a short, capped schema for the step report of a flow's worker. The method has a new section 8 (read with a filter, the quiet variant of a command, short pull request bodies, commit messages, log entries and closing messages, with long text in a file of the plan) and its definition of done a matching line; the step prompts (`core/plan/flow-step-prompts.md`) get a `budget` section for every step and a `report` section with the schema (Status, Merged, Decisions, Deviations, Next step, then Recommendations) and a hard cap of 30 lines and 2,400 characters, the rest going to the task's log; `harness flow report-check <file>` checks a saved report against both; the procedures `run-flow`, `start-task`, `open-pull-request` and `end-session` cite the budgets. A project takes it with `harness sync` (the procedures' packaged skills are regenerated); a flow file of a project that has its own `custom` step still gets the budget and report sections.
- a flow setting `orchestratorLimits.context` (50% of the orchestrator's window by default, beside `reuseLimits`) and a handoff entry in the flow's log (`### … — handoff: <why>` with State, Decisions, Next step, Waiting for), which `harness flow check` holds; `harness flow status` and `dispatch` print the orchestrator's context against the limit (`--orchestrator <percent>` feeds a reading back; a runtime that cannot read it leaves the judgment to the orchestrator), and `dispatch` prints a cache hint (how long the previous worker's prompt cache still lives, and that a start past it is logged cold). The procedure `run-flow` (step 9) and the runtime contract's `context` role say so (a change of their meaning, decided as `contract.change`). Nothing is required of a project: a flow without the setting takes the default; to give an existing flow the setting, add `"orchestratorLimits": { "context": 50 }` to its settings block (the flow template has it).
- the standard step prompts of `tasks`, `consumer-take` and `triage-fix` steps gain a paragraph (section `delegate` of `core/plan/flow-step-prompts.md`) that tells the worker to hand a large log, a long diff, a long test output or a research of sources to a subagent that returns a summary of at most 10 lines with pointers as evidence, and never to delegate a decision, a write, a merge or a reading a procedure requires in full; the procedure `start-task` and the runtime contract's `subagent` executor say the same. Nothing to do for a project: the prompts are rendered from the framework's copy, and a runtime without a `subagent` executor leaves the reading to the worker.
- `harness check notes` (part of `harness check all`) fails when a note of the migrations folder has no line in the section "The notes" of its `README.md`, or a line has no note; a project without that section is not checked. Nothing to do for a project.
- the profile role `flows.permissions` (`{ "mode", "allow" }`, in the runtime's own words) is the default of a flow whose settings have no `permissions` of its own, which wins; `harness flow dispatch` takes it and `harness check flows` checks it. Optional: a project that wants its flows' workers to start in a mode other than the runtime's strictest sets it once in the profile file, instead of in each flow.

### Changed

- the framework's commands and hooks are quiet by default. `harness check all` prints the problems and one line (`N checks passed`), `harness check <name>` one line on a pass; the steps of the pre-push gate and the project checks (`checks.project`) write their output to a file and print nothing on a pass, and on a failure the path of the file and the failing lines, at most `output.maxLines` of the profile file (default 40). `--verbose` restores the full output of `check` and `gate`; a script that read the output of a passing check must use it. New: `harness flow dispatch <n> <step> --brief` prints the step, its worker and how to start it, and the line to log, without the guidance for reading its report and the usage.
- what a project does to take the context optimization (Phase 6), for the note of the version: **required, nothing** (every new role and setting has a safe default, which the migration test's fixture holds: a project of `0.4.0` that sets nothing passes `check all` and its procedures cite the plain commands). **Recommended:** set the quiet commands in the profile file (`commands.lintQuiet`, `typecheckQuiet`, `formatQuiet`, `testQuiet`, `testCoverageQuiet`; the values of the project's stack are in `adapters/stack/<stack>/manifest.json`, `defaults.commands`, and a project with its own commands writes its own), then `harness sync` so the procedures cite them; a script that read the output of a passing `check all` or `gate` must pass `--verbose`; a flow file may add `"orchestratorLimits": { "context": 50 }` to its settings (the default applies without it). **Probe areas:** plan format, procedures, engineering method, adapter contract, stack adapters, runtime adapters, profile file, checks. A new project from `harness init` has the quiet commands, the flow template with the setting and the output budgets already. Not proven here: the Jest and pytest quiet options against a real project, and the fall of the measured tokens; both are the first consumer's take.
- `harness plan-write on` and `off` say, in their last message, to run the project's formatter on the settings file when the project's lint checks formatting (the file is written with one array entry a line). Nothing to do for a project.

### Fixed

- `harness flow status` reads the take of a version that a later take superseded as done (the lock names a later version and the take's pull request is merged), not as a mismatch, so a flow that needs a finished flow no longer waits for it. Nothing to do for a project.
- `harness flow estimate`, `gate` and `sample` take `--plan` as the plan the runtime reports (`Pro`) or the subscription the table names (`pro`), in any case; the message of an unknown subscription names the forms. Nothing to do for a project.
- the quiet test commands of the node-ts preset (I-31). `testQuiet` and `testCoverageQuiet` are for a single package; a project whose root script is `npm run test --workspaces` writes `testQuiet` as `npm run --silent test --workspaces --if-present -- --reporters=summary --silent` (and `testCoverageQuiet` the same way), because there npm takes the flags after `--` and Jest never sees them (the take of 0.5.0-dev.1 measured −75% output with this form, none with the default). The preset now also defaults `typecheckQuiet` (`npm run --silent typecheck`) and `formatQuiet` (`npm run --silent format -- --log-level warn`).
- `harness flow audit` finds the command-line workers of a flow (I-32): the finder also reads a worker's id from its "step ended" entry (the line `Worker: cli <id>`), the Claude Code adapter's `locate` finds a transcript by that id in any project folder, and a session reused by several steps is split by step with the times of its turns and the ends of the steps in the log. Flow 3's own log gave 2 sessions before and gives 10 now (13 rows by step). The runtime contract's `locate` row names the three kinds of id.

## [0.4.0] - 2026-11-07

Migration note: [migrations/0.4.0.md](migrations/0.4.0.md)

### Added

- `harness review measure` prints the measurements of a harness review that a script can decide, which the reviews ran by hand with `wc`, `grep` and a loop over the Markdown files: the words of the always-loaded set (the entry file, what it imports and the root files that import it) with the rows and words of its `procedures` block apart (M6), the normative and exception words of that set (M20), the rows of the rule map by status, the hand-written rows apart from the generated ones (M5), the Markdown files that no link reaches (M7), the highest fan-out and fan-in of a document (M21), and the references that break the dependency rule between layers, listed (M3). It counts as the earlier reviews did, so a number compares with the previous report, and it prints each number against the ceiling of the project's harness review bindings (a table row `Number | Baseline | Ceiling`, or `Aspect | Number | Budget`): it exits with 1 when a number is over its ceiling. The harness review method cites the command in the step that measures; the bindings stub has the new rows (all with `—` until the first review proposes the ceilings), and a project that took the version reads the rows it wants into its own bindings. Nothing is required of a project.
- the off-plan record, for work that no task covers (documentation, tooling, CI, a change of the plan). A project with the new optional profile role `paths.offPlan` keeps one fragment per pull request in that folder (`<pull request number>-<slug>.md`: what changed, why and who asked, what it leaves to do), so that two pull requests never edit the same lines. `harness plan log --off-plan` prints the records in the order of the pull requests, and `harness check off-plan` (part of `harness check all`) fails on a record that does not read and lists the merged pull requests with neither a `Plan: <task id>` line nor a record, from the commit that added the folder's `README.md`. The method states the rule: nothing merges without a record (a task's log, a phase's log or an off-plan fragment). A project that wants it adds `paths.offPlan` to its profile file, a folder with a `README.md` (the format is in the profile row and in this repository's `docs/development-plan/off-plan/README.md`), and runs `harness sync`; a project without the role is unchanged.
- `harness plan-write on|off|state [--folders <a,b>] [--scope project|local|user]` lets an agent write the plan's files (the plan, its phases, flows, issues and backlog, and so the logs) without a permission prompt of the agent runtime. It is a new optional logic role of the agent-runtime contract, `plan-write` (a minor addition to contract 2: an adapter without it still conforms); the Claude Code preset fills it with `Edit(<folder>/**)` rules in `permissions.allow` of the project's tracked `.claude/settings.json` (the ignored local file or the user-wide one only with `--scope`), and refuses the settings file, the hooks and the Git directory. A new project's bootstrap (`harness init`, `harness bootstrap`) turns it on, says so in its output, and takes `--no-plan-write` to leave it off; the user-wide setting is never turned on by the bootstrap. A project that took an earlier version runs `harness plan-write on` once, if it wants the permission.
- a setting `commands` of a flow (the flow template and the plan method): `any`, the default, leaves the workers to write commands as they like, heredocs included, as before; `plain` adds a section to the prompt of each step that asks for files written by the runtime's edit and write tools (no heredoc or redirection into a file), no nested commands or subshells, and independent commands as parallel calls of one message, so that a strict permission mode of the agent runtime can check each command before it runs and asks the owner less. `harness flow check` refuses another value. A project has nothing to do; a flow whose workers run in a strict mode may set `"commands": "plain"`.
- `harness check markers` (part of `harness check all`, so of `docs:check` where a project runs it) fails on a line that starts with 7 or more `<` or `>` characters and a space or the end of the line, in a tracked Markdown or JSON file: the marker of a merge conflict that was committed unresolved. `harness branch update` no longer commits a file it resolved to the branch's side when that file holds such a line; it names the file and leaves the merge in progress. A project has nothing to do; a file that holds such a line on purpose (a document about conflicts) writes it inside a line or an indented block.

### Changed

- a session that a flow starts gets the flow's `permissions` setting by the means of the runtime's application (a minor addition to the agent-runtime contract, version 2: an adapter whose application takes none still conforms). The Claude Code preset starts a desktop-app session in the setting's mode (`permission_mode` of `start_session`, which the app takes at or below the orchestrator's own mode and refuses above it); the app's start takes no tools, so `harness flow dispatch` names the tools of `allow` as allow rules for the project's settings (`.claude/settings.json`, or the local `.claude/settings.local.json`), which the owner adds. Before this change a session ran in the orchestrator's mode whatever the setting said. The "step started" line of a flow's log gains `· **Permissions:** <mode>` after the model when the flow sets a mode; a line without it still reads as before. A project whose flows set `permissions` and start sessions should add the tools of its `allow` list to its project settings, or its unattended sessions are refused each tool that the mode does not allow.
- the order of the executors of a flow (a change of the meaning of the procedure `run-flow` and of the agent-runtime contract, approved by the owner on 2026-11-05). The runtime contract (still version 2, a minor addition) gains the executor `cli`, a worker on the runtime's command line, and sets an order: `session` (a session the owner can open in the runtime's application) is the default of every step, `cli` is its fallback for one step at a time, and `manual` the fallback of that; a `subagent` stands outside the order, for a short step of analysis only. `harness flow dispatch` prints, beside every start, the next executor of the order with the log line that names it as the fallback and its reason (`- **Executor:** cli, the fallback of session: <the reason> · …`), and a step in another repository goes to `cli` with its reason (a session cannot be counted on to start in another folder without the owner's message). `harness flow check` refuses a "step started" entry on another executor than the step's own without the fallback and its reason, and the reuse rule never continues a worker of another executor, so the next step goes back to a session. The flow settings and a step's override accept `cli`. The Claude Code preset splits its `session` executor in two: `session` is the desktop app's sessions, and `cli` the command line (`claude -p`, with the flow's `permissions` as flags). A project whose flows use the preset has nothing to do; a log line written before reads as before. A runtime adapter of the project's own that offered the command line as a means of its `session` should move it to a `cli` executor, which is optional.
- the usage table of the Claude Code preset (`adapters/runtime/claude-code/usage.mjs`) has calibrated rows for the step kinds `consumer-take` and `cut` of Sonnet on Pro, from the measured steps of flow 1 (`harness flow calibrate`): 2.62 % of the 5-hour window and 0.42 % of the weekly one per SP for a take, 3.42 % and 1.03 % for a cut, where the provisional table said 6 % and 0.8 %, and 4.8 % and 0.64 %. `harness flow estimate` and `gate` use them for those kinds; the other kinds, models and subscriptions keep the provisional coefficients, which still overestimate a task (the sample had too few tasks to propose a figure). A project that sets nothing sees smaller estimates for a take and a cut; nothing to do.
- the procedure `release` and the releasing guide say to push the tag of a release or a hotfix from a local branch at the merge commit, before the merge back into the integration branch, and why (the tests run on the checked-out branch, and a tag newer than its version fails the migration tests as a downgrade); the failure message of the migration tests names the tag the project was bootstrapped from. A project has nothing to do.
- the `pr-title` job of the CI template also runs when the workflow is dispatched (`workflow_dispatch`, which the update workflow does for a pull request it brings up to date when it has no `AUTO_MERGE_TOKEN`): it reads the title of the open pull request of the branch (the job asks the `pull-requests: read` permission) and checks it as before, so that pull request no longer stays BLOCKED for a required check that was skipped. A project that took the template runs `harness sync` to get the job; a branch with no open pull request passes the dispatched check.
- the Git hooks `pre-push` and `pre-commit` run the tools of the tree that runs them: in a linked worktree, whose `core.hooksPath` names the main checkout, they use the worktree's own `harness.mjs` (found at the same path below its top folder) instead of the main checkout's, so the worktree's generated files are checked against its own `core/`. A project has nothing to do; a hook folder outside the project tree, or a worktree without the file, behaves as before.
- a flow may decide a change of the meaning of a contract at a level of its settings (a change of the meaning of the procedure `run-flow`, approved by the owner on 2026-11-06). The flow's `levels` gain the kind `contract.change`, D3 by default: a flow in brainstorm mode decides it below its `askAt` and asks from it up (with the default `askAt` D2 it still asks the owner), and a flow in seamless mode decides it and lists it in the digest to review later. The worker names the change as an open decision of its step report and the orchestrator decides it as any other; the pull request of the change cites the decision entry of the flow's log as the approval, or the record of the step does when the change merged first, and a refusal reverts it. A change of the meaning of a core rule or of a non-negotiable stays the owner's whatever the mode. A project has nothing to do; a flow that should keep asking for every contract change in seamless mode cannot, so such a project runs that flow in brainstorm mode, with `askAt` at D3 or below.
- the usage table of the Claude Code preset (`adapters/runtime/claude-code/usage.mjs`) is calibrated again for Sonnet on Pro from the measured steps of flows 1 and 2 (`harness flow calibrate`): a `tasks` step now has a row of its own, 1.8 % of the 5-hour window and 0.25 % of the weekly one per SP, where it took the default row (12 % and 1.6 %), and the weekly figure of a take and of a cut falls to 0.23 % and 0.69 % per SP (from 0.42 % and 1.03 %). `harness flow estimate` and `gate` give a task of Sonnet about a sixth of the earlier estimate, so the gate no longer holds such a step back for hours while it would fit. The figures are upper bounds: the account's window also counts the orchestrator and the owner's parallel work. Opus, Haiku, the other kinds and the larger subscriptions keep their provisional figures. A project has nothing to do.

### Fixed

- `harness flow status` takes a pull request of a consuming repository for the take of a version only when its title names the version as a whole token, so the take of `0.3.0-dev.1` is no longer read as the take of `0.3.0` (nor of `0.3.0-dev.10`, nor the reverse). A project has nothing to do.
- the notes and messages of a migration say what they left out. `harness migrate` to a development version also prints the final note of its line when the tree holds it, marked as not yet taken; the message about a release order says apart an order of phases written as arrows that no release holds (nothing to do), names a release whose old cell gave no task id (its ids and status are set by hand), and says the status 🏷 is set by hand; `migrations/README.md` gains the rules a note follows about checks of a development note, the release table and documents that cite deleted files, and the note of `0.3.0` says that a project's text about the copied tests must follow. A project has nothing to do.
- a bootstrap now creates the off-plan record. The starter answers set `paths.offPlan` (`docs/development-plan/off-plan`) for a new project, and the scaffold writes the folder's `README.md` (the format of a record) from the new template `off-plan-readme.md`, so `harness check off-plan` runs from the start. A project that is already adopted keeps its profile file as it is; to turn the record on it adds `paths.offPlan` to its profile file, a folder with a `README.md` in the same format, and runs `harness sync` (as the note of the off-plan record says).

## [0.3.0] - 2026-11-05

Migration note: [migrations/0.3.0.md](migrations/0.3.0.md)

### Added

- adapters of a project's own repository. A folder `harness-adapters/<axis>/<name>/` that the profile file selects as `local:<name>` (in `adapters.stacks`, `adapters.runtimes` or `adapters.host`) is loaded by the tools like a preset, so a project whose stack, agent runtime or host the framework has no preset for (Go, GitLab, Copilot) no longer waits for a release. A sync, `harness migrate` and `harness check vendored` leave the folder alone, and `harness rollback` restores it with the rest of a migration. `harness check adapters` holds the manifests to their contracts, and the new check `local-adapters` (part of `harness check all`) runs the conformance suite on every local adapter; `harness migrate` runs it with the new version's suite and stops before it commits when an adapter no longer meets the contract, naming the adapter, the failed checks and the migration notes that say what changed. The guide and the procedure `new-adapter` offer both ways and say how a local adapter is sent upstream. A local adapter imports nothing from the framework's tools by a relative path. A project with no `harness-adapters/` is unaffected; a project that wants one takes the version with the sync.
- the release order in a file of its own. A project that ships versions can name a file in the new profile role `paths.releases` (by default `docs/development-plan/releases.md`): one table `Release | Status | Tasks, in order | Consumers | Notes` (status ⬜ planned · 🟡 developing · 🏷 a development version cut · ✅ released) and a list "Not scheduled", from the new template `core/plan/releases-template.md`. The tools read the order of the tasks from it instead of the section "Order of development" of the plan index (the session start and `harness plan summary` included), the plan index shows the current and the next release in a generated block that links to the file, and `harness check plan` refuses in it a backlog item (`B-<n>`) and an id that exists nowhere, and an index that keeps the section beside the file. A project without the role loses nothing: its tools read the section of the index as before, and a project that ships no versions needs no file. The migration of `0.3.0` moves a table of the section into the file, sets the role and leaves the block in the index; an order written in prose (arrows of phase numbers) cannot be read by the tools and is left as it is, with a message: write it as the table of the template, set `paths.releases` and run `harness plan summary`.
- flows, files of the plan that an orchestrator runs. A project that has a releases file can name a folder in the new optional profile role `paths.flows` (by default `docs/development-plan/flows`): one file `flow-<n>-<slug>.md` per flow (an ordered chain of steps that delivers one or more releases, with a settings block — `mode` brainstorm or seamless, `askAt`, `levels`, `executor`, `reuse`, `commits`, `usage`, `repos` — and a steps table) and its log beside it, from the new templates `core/plan/flow-template.md` and `core/plan/flow-log-template.md`. `harness plan summary` creates the folder's index, writes its table from the flow files and links it from the releases block of the plan index; its check refuses a release that two flows declare or that the releases file lacks. The new procedure `run-flow` (a skill too) says how an orchestrator runs a flow: decision levels D0 to D4, the hard limits no mode crosses, the step report a worker ends with, the unbiased analysis, escalation and digests (plan method, section 10). The resume phrases may name flows ("Run flow N", "Run flows N–M", "Continue flow N"): add them to `plan.resumePhrases` of the profile file if the project uses flows. The Git rules let a flow's phrase approve only what its settings allow, never a merge or an answer they keep for the owner. A project without the role changes nothing.
- `harness flow check | status <n> | next <n> | prompt <n> <step>`, the tools of the flows of the plan (the procedure `run-flow`). `harness flow check`, also the check `flows` of `harness check all`, holds the parts of a flow file and of its log, unique step ids (an inserted step with a suffix after its base), that the ids a step names exist (tasks and issues, never a backlog item), that a version is a row of the releases file that the flow declares, that the `Needs` of steps point to earlier steps and those of flows resolve without a circle, and that the flows index agrees with the files. `harness flow status` recomputes the state of each step from the repository, not from the State column (the ids of a `tasks` step ✅ with their pull requests merged, the tag of a `cut`, the version in the consumer's lock for a `consumer-take`), prints the mismatches with the column and the log, a step an orchestrator left open, and the next step; `harness flow next` prints that step with its prompt, and `harness flow prompt` the prompt of a step, rendered from the standard wording in the new `core/plan/flow-step-prompts.md` (a `custom` step carries its own text). The session start names a flow that is running or waits, with its next step. A project without flows has nothing to do; one with flows runs `harness flow check`, which `check all` now includes.
- usage in the flows. The agent-runtime contract gains the optional role `usage` (`usageFor(profile)`): how an orchestrator reads the account's windows, and a table of coefficients that turns a step's SP, model and kind into a share of the 5-hour and the weekly window (money on an API key). The Claude Code preset reads them from the desktop app (`get_usage`) and carries provisional coefficients for Pro, Max 5x, Max 20x and the API; the Cursor preset asks the owner and has a mock; a runtime that leaves the role out gets the owner asked. New: `harness flow estimate <n>` sizes a flow, `harness flow gate <n> <step> --five-hour <percent>@<reset> --weekly <percent>@<reset>` says whether a step may start (GO, WAIT until a reset, STOP, ASK) with the safety factor on its estimate, and `harness flow sample` appends measurements to the flows' `usage.jsonl`; `harness flow dispatch` prints the estimate, how to read the usage and the gate; `harness flow check` flags a step that cannot fit one window where the subscription is known, and a bad line of `usage.jsonl`. The flow settings `usage` gain `safetyFactor` (1.2) and `maxWaitMinutes` (300), and are merged one level deeper, so a flow that sets only its subscription keeps the default thresholds. A project sets its subscription in `usage.subscription` of the ignored `harness-profile.local.json`; nothing else to do.
- `harness flow calibrate [--min <n>] [--subscription <id>]` proposes new coefficients for the runtime adapter's usage table from what flows measured in `usage.jsonl`. It pairs each step's start and end samples, drops the windows that a reset cut, takes the median use per SP of each subscription, model family and step kind (tokens per SP converted to percent per subscription where the runtime reports them, since whole percents are coarse on the larger subscriptions), prints each proposal beside the table's figure with the number of steps behind it (at least 3), compares cold and warm starts and says whether `reuse: auto` pays off (otherwise set `reuse` to `never`), and sets whole flows against their steps. It never writes: the procedure `run-flow` says to run it at the end of a flow and to accept a proposal by a pull request that changes the table. Nothing to do for a project that uses the presets.
- a flow may drive steps in another repository. A flow still belongs to its home repository; its `repos` setting may name external ones, each a row `{ "remote": "<owner>/<name>", "role": "consumer", "kinds": ["consumer-take"] }` under an alias that a new optional `Repo` column of the steps table uses (the flow template now leaves the column out: with the home repository only, every step is the home repository's). The folders on this machine go in the ignored `harness-profile.local.json` (`repos.<alias>`). In an external repository the orchestrator only starts a worker (in that folder; the manual executor when it is not set): it edits nothing there, the prompt sends the worker to that repository's own entry file, a release cut and the answers to reports stay the home repository's, and a step there names the work by what it does ("take `1.0.0`"), never by task ids (`harness flow check` refuses an id, a kind that is not `consumer-take` or `custom`, and a bad row). `harness flow status` checks such a step through the host: the lock file the repository holds and its pull requests that mention the version. The host contract gains the optional role `remote-state` (`remoteFile`, `remotePullRequests`; the GitHub preset reads them with `gh`). Changed: the `repos` setting of a flow was a map of aliases to paths, which nothing used yet; an alias is now a row (a path there is refused), and the home repository is implicit. A project that has no flow of its own yet has nothing to do.
- the migration note of `0.3.0` (`migrations/0.3.0.md`): the whole story from `0.2.0`, with the required actions of a project that has a prose order of development or a local runtime adapter (which must now fill the role `executors`), and the optional first flow. Fixed: after a step that the orchestrator ran itself (a cut at its own level, which names no worker) the next step may continue the previous worker; `harness flow status` counts a pull request of an external repository as taking a version only when its title names it, not when its body mentions it; the flows index no longer shows a floating-point tail in the sum of the estimates. Nothing to do for a project.

### Changed

- a flow the owner started may cut releases and answer reports at the levels its settings give them (a change of the meaning of core rules, approved by the owner in its pull request). The Git rule `agent.ask-merge` lets the orchestrator of such a flow approve the merges of a release or a hotfix when the cut's level (by default a development version D1, a final release or a hotfix D3) is below the flow's `askAt`, or the flow is seamless; it merges by merge commit once the required checks are green, never by the host's auto-merge or an administrator's bypass, tags, and logs the cut as a decision with its level. The procedure `release` says what it does in the owner's place ("When a flow cuts": it reviews the migration note by the unbiased analysis of `run-flow` first). The report rules and the procedure `triage-reports` let such a flow approve answers and closings on the host at their level (D4 by default); creating a report on the host stays the owner's. Nothing changes for a project without flows. The shell guard still refuses auto-merge on release and hotfix pull requests, and the rule-to-check map shows what holds a flow's cut.
- the agent-runtime contract is at version 2 and gains the logic role `executors` (`executorsFor(profile)`), how an orchestrator of a flow hands a step to a worker: a `session` it starts and controls (with the hooks and CI wake-ups of a session), a `subagent` for a short step of analysis, or `manual` (the owner pastes the prompt and the report). Each executor returns the means to start a worker with a model and an effort, continue it with a next prompt, fetch its full final report and read its context. The Claude Code preset maps the desktop app's sessions, the command line (`claude -p`, continued with `--resume`) and subagents; the Cursor preset is a stub with the manual executor only. New: `harness flow dispatch <n> <step> [--context <percent>]` picks a step's executor, decides with `reuse: auto` whether the previous step's worker continues it (the same repository, model and effort, related steps, its context below the new setting `reuseLimits.context`, 40% by default, no stop and no pause longer than the prompt cache lives, fewer than `reuseLimits.steps`, 3, steps run) and prints the means; the flow-log template gains a `Worker:` field, which the next dispatch reads. A runtime adapter of the project's own repository (`harness-adapters/runtime/<name>/`) must now fill `executors`: copy `executors.mjs` from the skeleton and return `{ manual }` when the runtime offers no automation; a project that uses the presets has nothing to do.

### Fixed

- a flow continued from another account (an owner with two subscriptions on one machine) no longer resumes a worker that account cannot find. The flow-log template's "step started" line gains an `Account:` field; the runtime contract (still version 2) gains an optional operation of an executor, `account()`, the means to read the account the orchestrator runs on (the Claude Code preset: `printenv CLAUDE_CODE_USER_EMAIL` in the desktop app, `claude auth status` on the command line); `harness flow dispatch` takes `--account <id>`, and the reuse rule adds "the same account" when both are known. Whenever `dispatch` continues a worker, it also prints the fresh start to fall back on when the continue fails for any reason, and the procedure `run-flow` says to take it and log a D0 decision instead of retrying. Nothing to do for a project: a log without `Account:` fields reads as before, and an adapter without `account` is not compared.
- a worker that a flow starts on the command line is no longer left refused every edit and command. A `claude -p` worker has no one to answer a permission prompt, so under the default mode it could not write a file or run Git, and reported itself blocked. The flow settings gain `permissions` (`{ "mode": "<a mode of the runtime>", "allow": ["<a tool by name>"] }`, in the runtime's own words, absent by default); the runtime contract passes it to an executor's `start` and `continue`, the Claude Code preset turns it into `--permission-mode` and `--allowedTools`, `harness flow dispatch` prints what a worker will be allowed (and warns when nothing is set), `harness flow check` checks the setting, and the procedure `run-flow` says that the choice is the owner's. A session that the desktop app starts runs under the app's own permission settings and is not affected. A local runtime adapter may add an optional `permissions` operation to an executor; nothing is required of a project.
- the migration of `0.3.0` no longer writes prose into the release table's id column. Of an old table's cell, only the ids the tools read (a task of a phase, "Phase N" of a phase that exists, an issue) stay in "Tasks, in order"; the words around them go to "Notes", and the migration says so. A release the project skipped on purpose (a row with no task whose words say "skip") gets the new status ⏭ (skipped on purpose, in the releases template and the legend of the file); it is never "next" in the plan index. An order of phases written as arrows beside the table, which the tools do not read, is kept in "Notes" and the migration now prints a required action that says how to keep it (name the phases as "Phase N" in the table). The migration of the earlier versions is unchanged.
- the first `check all` after taking `0.3.0` no longer fails on its own account. The migration puts the new releases file in the layer that claims the plan index (or prints a required action naming the layer to add, with `check layers` as its check); the line of `core/plan/README.md` that used the ordinary word "base" is reworded, so a project whose product terms name "base" is not failed by it (the note says what to do with such a word in another version); and the migration note of `0.3.0` and the procedure `update-framework` say that the first gate after a take runs every suite of the project, because the vendored copy counts as code.
- the migration of `0.3.0` takes task ids for the column "Tasks, in order" only from the part of an old table's cell that lists tasks (its start: ids, separators, "then", "and" and notes in brackets), so a phase or a task that the words after it only mention ("Phase 17 is closed") is no longer written under a release that does not hold it; the whole cell stays in "Notes". The sentence that stood before the old table and ended in its colon is closed with a full stop, so it is not left broken in "Notes". The migration of the earlier versions is unchanged.
- a push from a linked Git worktree no longer lets the gate's tests rewrite the repository's Git config. Git runs the pre-push hook of a linked worktree with `GIT_DIR` set to `.git/worktrees/<name>`, and the steps of `harness gate` inherited it, so a test that ran `git init` or `git config` in a temporary folder set `core.bare = true` or a new `core.hooksPath` on the pushing repository. The hook now unsets the variables that point Git at a repository (`git rev-parse --local-env-vars`) before the project's setup script, and the gate starts every step without them. A project takes the fix with the sync; a repository a push already damaged needs `git config core.bare false` and its `core.hooksPath` set back by hand.
- a condition inside a line of a procedure (`… {{#if role}} … {{/if}} …`) is rendered instead of copied into the generated skills. The template engine knew the blocks `if`, `unless` and `each` only with each tag on a line of its own, so the skills `change-plan`, `end-session` and `triage-reports` shipped the raw `{{#if …}}` and `{{/if}}`. A condition closed on the same line now keeps or leaves out the text between its tags, a role inside it is optional (a profile without it no longer stops the sync), and any other block tag inside a line is an error rather than text. A project takes the fix with the sync, which rewrites its skills.

Migration note: [migrations/0.2.0.md](migrations/0.2.0.md)

### Added

- migration scripts. A version may ship `migrations/<version>.mjs`; `harness migrate` runs, with the new version's tools, the scripts of every version after the project's own up to the target that the lock does not record, in version order, records them (`migrations` in `harness.lock.json`), and prints the migration notes of those versions in order. A lock without the record counts as `0.1.0` with nothing applied. The migration test bootstraps a project from each released tag and migrates it to the current tree. A script checks its starting state and can run twice.

After the `sync` of an older version, `migrate` takes that sync's files into its commit and refuses any other uncommitted change.

Each probe in the harness-review bindings has an `Areas` column (the areas of the migration notes) and the words read at the last review; the bindings stub of a new project has four starting probes. `harness probes <from> <to>` prints the probes to run again for the versions taken and, for an area no probe covers, the framework's starting probe (`core/reviews/harness/starting-probes.md`); `harness check probes` holds the area names.
- reports from users are taken in and sent upstream by procedures, set by switches in the profile file. `reports.intake` (`off`, `notify`, `auto`) and `reports.triageLimit`: the session start lists the open reports and those not triaged yet, and with `auto` the agent triages at most the limit before other work by the procedure `triage-reports`, which looks for the same or a close problem in the issue queue, its archive and the open tasks before adding a new issue. `reports.upstream` (`off`, `ask`, `post`): the procedure `report-upstream` drafts and posts a suspected defect of the framework. `harness reports …` reaches the host through its adapter's new `reports` role (GitHub: `gh`); answering, closing and creating need the owner's approval. A local, ignored `harness-profile.local.json` overrides the switches at once. A switch that is on adds one line to the entry file's Git rules; one that is off adds nothing, no skill and no row of the reading map.
- a backlog for the feature requests, beside the issue queue and optional like it. It is the place for what the owner has not approved: an item is a proposal, never started as it is. The profile role `paths.backlog` names a folder with an index of the proposed items (generated by `harness plan summary` and counted in the plan index), a file per item (`B-<n>.md`, from the new backlog template), and `archived/` for the promoted ones. An item is `Proposed` or `Promoted` (with `Promoted to:`), has no branch, no claim and no log, and has a `Source:` set to `report` and the link of each report, `owner` or `agent`. The owner's decision is `harness plan promote <B-n> --phase <n> [--agent <marker>] [--size <n>] --approved`, which writes the next task of the phase from the item, sets the item to `Promoted`, moves it to the archive and updates the size of the phase; an order of development, an execution order or a `Needs` that names a proposed item is a problem of `check plan`. `harness reports plan` has the relation `feature`, `reports candidates` compares the backlog too, the session start says how many proposals wait, and an issue that moves to the backlog keeps its number (`B-1, formerly I-6`), which the issue queue never gives again. A project without the role has no backlog; a project that sets `paths.backlog` gets the folder, its indexes and the block of the plan index from the next `harness plan summary`.
- a project can have procedures of its own. The new profile role `paths.procedures` names a folder of procedure files in the format of `core/procedures/`; the skill generators package them for the selected agent runtimes (the note of origin in a skill names the project's file), the `procedures` block of the entry file lists them after the framework's, and `harness check generated` fails on a stale skill of one. A name that the framework's procedures have too is an error. The CORE scan does not read the folder; the project classifies it in its layer map. Nothing to do for a project that does not set the role.
- the procedure `change-plan` (invocation `auto`, so an agent loads it as a skill on its own): adding a task, adding a phase, recording a defect or an improvement found in use as an issue, and splitting a phase. It tells the agent to read the plan method, the rules of a phase file and the template first, never to copy an old phase, task or issue, and to leave every generated block to `harness plan summary`. Its row is in the procedures block of the entry file and its skill is written by the next `sync`.
- the procedure `update-framework` (explicit: a person asks for it, as for `release`): taking a version of the framework from the one in the lock to the target across any number of versions. The branch of its own, `sync` and `migrate` (run by hand after the `sync` of a version before 0.2.0), the migration notes of every version in order with the check of each required action, `check all` and the project's gate, the probes that `harness probes <from> <to>` selects compared with the last review, what the notes missed written in the pull request and reported upstream, `harness rollback` when it fails, and the pull request. It also says how to adopt a project that copied the first harness and how to report a defect found in the framework. Its skill is written by the next `sync`.
- templates for a risk register and for design records (RFCs), the two cross-cutting documents the plan method names but the framework shipped nothing for. The bootstrap writes them once into a new project, at the new optional roles `documents.riskRegister` and `documents.rfcs` (the starter values are `docs/development-plan/cross-cutting/risk-register.md` and `.../decisions/README.md`): the register with its rules and its table (likelihood, impact, mitigation, owner, status, date reviewed), and the index of the records with the rules (immutable after acceptance, superseded by a new record, cited by the task) and the template of a record. Both appear in the document map of the profile document. No check reads them. A project that already has such documents, or leaves the roles empty, gets nothing; to take the templates, set the two roles and copy the files from `harness/core/templates/scaffold/`.
- `probes.run` in the profile file (`auto`, `ask`, the default, or `disabled`; the ignored `harness-profile.local.json` overrides it on one machine) for how taking a version handles the cold-start probes of the project, which are a session each and read thousands of words. The end of the output of `harness migrate` and of `harness probes` says what the mode asks of whoever takes the version: run them (`auto`), ask the owner first and run them only on a yes (`ask`), or leave them (`disabled`). The procedure `update-framework` follows the mode. No command starts a probe itself yet, so `auto` and `ask` are instructions; a project that takes the version and wants no probes sets `disabled`.

### Changed

A resuming agent reads the index and one task file instead of the whole phase, and a finished task writes only its own log. `harness check plan` holds the layout, the session-start hook prints the newest next step across the logs and the open tasks, and `harness plan split <phase>` (and the migration script of this version, for the open phases) splits a one-file phase and rewrites every link into it. The tools still read the one-file layout. The phase template became a phase-index template and a task template.
- the defects and improvements found in use are no longer a phase that never ends. They are an issue queue, `paths.issues`: a file per issue (`I-<n>.md`, with `Area:`, `Reported:` and its log beside it), an index of the open ones, and `archived/` where `harness plan summary` moves the finished ones. Branches are `bugfix/I-<n>-<slug>`; "Work the issue queue" and "Fix I-<n>" approve their pull requests. The migration script of this version turns a project's open-ended phase into a normal phase that keeps every id, makes only its defects that have not started into issues (`I-1, formerly 12.5`), and replaces `plan.openEndedPhase` and `plan.openEndedPhaseNumber` of the profile file with `paths.issues`. `harness check plan` fails when an order names an id that exists nowhere.

A phase of the older layout is checked as before. A project whose phase folders (the ones `harness plan split` or the migration of this version wrote, or its own) lack a part reports it; the message names the part and the template.
- the procedures that the method requires of every agent unasked can be loaded by the agent: `start-task`, `end-session`, `finish-phase` and `triage-reports` are `invocation: auto`, so the Claude Code preset (and Cursor) no longer writes `disable-model-invocation: true` into their skills. The format says it: `explicit` is only for a procedure that an agent must not start on its own judgment (design §8.1). A project takes the change with the next `sync`, which rewrites the four skills; nothing else to do. A procedure of the project's own folder (`paths.procedures`) follows the same rule.

The method also says how a probe runs: a probe of another repository, or one that depends on the session start, runs as a separate session started in that repository, because a subagent of the reviewing session inherits that session's entry file and gets no session-start hook. A project that already has bindings adds the two probes and its budget at its next review; nothing else to do.
- every version has a migration note, a development version included: `migrations/<x.y.z>-dev.<n>.md` says what a project does when it takes that development version from the previous one (the previous development version of the same `x.y.z`, else the previous final version) and is frozen once the version ships; the final note stays the complete story. `harness migrate` and `harness probes` read the notes of the versions after the project's own up to the target, leaving out the development notes of an `x.y.z` when its final note is among them. `harness release --dev` now refuses a version without its note, as the final release does, and writes a stub (the changelog fragments added since the previous release, the areas, and a `TODO` in the required actions) when the note is missing; a `TODO` left in the required actions stops any release. The release guide and the procedure `release` put the note before every cut. A project with its own release flow adds the note of the development version before it tags it; nothing else to do.

### Fixed

They prove the framework against its own repository (its profile file, every preset, its documents), so in a pinned project 20 of 428 failed for what the project does not have, and nothing in a project runs them. `framework.json` lists the file name endings a sync leaves out in `excluded`; the next sync removes the test files from `harness/`.

- `harness adopt` (design §6.4; task 1.1): the bootstrap for a repository that copied the first harness. The agent-runtime contract gains the optional role `hook-adoption` (`adoptConfiguration`), which the Claude Code preset fills: it adds the framework's hook entries and read exclusions to the project's own `.claude/settings.json` and names the hook commands that are the project's own.
- The framework is its own project (design §11): lock mode `self` with the profile role `paths.frameworkDir` (`.`), `harness init --self` and `harness bootstrap --self`, its own plan (Phases 1 to 3), CI and rules. The first tagged development version is `0.1.0-dev.1`.
- The skeleton of the framework: the folders of the layout, `framework.json` at `0.1.0-dev`, the MIT license, this changelog and the
  README. The core documents, the tools and the adapters follow in the build tasks of the design.
- Vendoring (design §1): `harness sync` (from a folder or a Git tag, with the selected adapters only), `sync --local`, `check vendored`,
  `diff`, `override` and `detach`, with `harness.lock.json` in the modes `pinned`, `detached` and `self`. Plain Node, no dependencies.
- The generic tools (design §3.4), merged from both copies that existed: `check all`, `check links` (anchors keep `_` as the host does),
  `check paths` (new), `check core`, `check plan` with `plan summary` and `plan log`, `check changelog` with `release` and `release notes`,
  `check product-knowledge` (its file names and exceptions in the profile's `productKnowledge`), and `ci changes` with
  `checks.documentationPaths`. The profile gains `checks`, `productKnowledge`, `release` and `paths.entryFile`.
- The two features of the second source (design §3.4): the link check's index rule (`checks.indexedFolders`: the README of an indexed folder
  links every file and subfolder that Git tracks in it) and the agent-complexity markers of the plan (`plan.complexity`: the scale and the
  model of each marker; every open task carries one in an `Agent` column before `SP`, done tasks are exempt, and the plan index shows each
  phase's range). Without `plan.complexity` the plan has no markers.
- The core documents (design §3.2): the engineering method (`core/method/`), the plan method with the index, phase and task-log templates,
  the definition of done and the guiding principles (`core/plan/`), the review methods with their report templates (`core/reviews/`) and
  the changelog-fragment format (`core/templates/`). Their links to project documents are role names, and none leaves `core/`.
- The entry file's rules as managed blocks: `core/rules/non-negotiables.md` and `core/rules/git.md`, rendered into the blocks
  `non-negotiables` and `git-rules` with the Role binding line from the profile (`plan.openEndedPhaseNumber`,
  `repository.protectionScript`), each rule with a stable id; the lock keeps one hash per block (`<path>#<block>`), and the layer map
  counts the blocks as CORE, so `layers.core` is empty for a project that uses the framework.
- `check generated`: every managed file and block rendered again and compared, in every mode.
- The plan method describes the agent-complexity markers as a standard, optional task property (its section 7): the `Agent` column of the
  phase template, the range column of the index template, the conformance rule and the exemption of done tasks.

- The adapter contracts (design §4): `core/contracts/{stack,runtime,host}.md`, their machine form `profile/manifest.schema.json` (`x-roles`),
  `harness check adapters` (a manifest filled to its contract), and the adapters' `terms` joined into the CORE scan. `adapters.stacks`
  entries may list the `packages` they own, and `check profile` fails when two stacks claim one folder or a project with several stacks
  leaves one without folders.
- The GitHub host adapter (`adapters/host/github/`): `protect.mjs` (`harness host protect`, the ruleset of the protected branches, now on
  Node, with the detection of whether the host can protect the repository and the new profile role `host.protection`, which must agree
  with it), `workflows.mjs` (the triggers and job names of the workflow files) and the workflow templates `ci.yml` and `release.yml`
  (the pull-request title check, change detection, the aggregator, coverage packages read from the profile).
- `harness check values` (replaces a project's profile test): the host's CI triggers equal the protected branches; every required check is a
  job; no branch, repository or plan path of the profile is spelled out in the files of `checks.roleOnlyPaths`, and no workflow names a
  protected branch outside its triggers or lists the coverage packages.
- `{{#unless …}}` blocks in the template engine.

- The node-ts stack preset (`adapters/stack/node-ts/`): `gate.mjs` (the plan of the local gate: typecheck, lint and format of the touched
  packages, the tests related to the changed files, the whole package for a change that cannot be followed, the changed-file coverage),
  `coverage.mjs` (the merge of Istanbul shards and the neutral coverage summary, without a dependency), `ci-jobs.mjs` (a static job and a
  coverage job per package for the host's workflow frame) and its manifest, with the stack role "ignore files".
- The gate driver `harness gate` (the local gate of a push): it routes each changed file to the stack that owns it, runs the documentation
  checks for a push that changes documentation, and adds the project's own steps (the profile role `gate`: `outside`, `isolated`, `needs`,
  `prepare`, `steps`). `harness coverage check-changed` and `harness coverage merge` apply the coverage gate to the neutral summary.
- `harness check scaffold`: the stack's ignore files exclude the vendored framework.

- The runtime hooks (`tools/runtime-hooks/`): `guard-shell` (the Git rules of the entry file, `--no-verify`, and the merge guard of a host
  without protection), `guard-edit` (environment files, and the vendored framework in pinned mode), `format-edited` (the formatter of the stack
  that owns the file, from the project's installation, never downloaded) and `session-start`, with `io.mjs`, which reads the event of Claude Code
  or Cursor (recognised by `cursor_version`; native and compat modes) and answers in its form. Recorded event samples of both runtimes are in
  `tests/fixtures/events/` (the Cursor ones are written from its documentation, not recorded in a live session).
- The Git hooks `tools/git-hooks/pre-commit` (no commit on a protected branch, except the root commit of a new repository) and `pre-push` (the
  vendored check, a protected or deleted remote ref, the project's setup script `hooks.prePushSetup`, then `harness gate`), and `harness guard`.
- The Claude Code preset (`adapters/runtime/claude-code/`): `CLAUDE.md` that imports the entry file, `.claude/settings.json` from the profile
  (`settings.mjs`: the hook entries and the `Read(...)` deny rules of the new profile role `access.denyRead`), and the scaffold invariants
  (`harness check scaffold` fails on a missing hook entry or deny rule).
- The merge guard of the GitHub host adapter (`gh pr merge` while a required check is not green), used when `host.protection` is false.
- The core rows of the rule-to-check map, generated from the `enforces` declarations of the adapters and the Git hooks, for both protection cases
  (a managed block in the rule-map document); the manifest gains `enforces`.

- The neutral procedures (B6): `core/procedures/` with `start-task`, `end-session`, `open-pull-request`, `finish-phase`, `release`, `harness-review` and
  `code-review` (frontmatter `name`, `description`, `invocation`; a body that names roles and commands as `{{commands.lint}}`). The Claude Code preset
  packages each as `.claude/skills/<name>/SKILL.md` (explicit ones with `disable-model-invocation`), generated by `harness sync` and held by
  `harness check generated`; the entry file's managed block `procedures` lists them for every agent: "when …, follow
  `harness/core/procedures/<name>.md`". `new-adapter` follows with the conformance suite.
- The bootstrap (design §6): `harness init` (interactive, or with flags and `--set`), `harness bootstrap`, `harness template <dir>` (the
  template repository, built by the engine) and `BOOTSTRAP.md`, all through one engine that completes the profile file from the answers,
  `profile/starter.json` and the new `defaults` of the adapters' manifests. The scaffold is the core templates of `core/templates/scaffold/`
  and the new optional `scaffold-files` role of each axis (node-ts: the Node version, the ignore file, a package manifest and an empty lock
  file; claude-code: `CLAUDE.md` and the settings; github: the CI and release workflows). The bootstrap commits the root commit of the
  integration branch, makes the production branch, installs the Git hooks and runs `check all`; `--detached` equals a pinned bootstrap
  followed by `detach`. `documents.harnessBindings` is optional.
- The conformance suite (design §5): `harness adapter test <path>` runs the checks of an adapter's axis (`tools/conformance/`), and the presets pass it in
  the framework's tests, with deliberately broken copies of them failing the check that names what is broken. Every adapter has a `conformance.json` of
  samples; the skeleton of each axis (`adapters/<axis>/_skeleton/`, vendored) starts red with `TODO` markers; the guide `core/contracts/new-adapter.md` and the
  procedure `new-adapter` (packaged as a skill) say how to write an adapter.
- the Cursor preset (`adapters/runtime/cursor/`; task 1.2), **unverified in a live session**: it is written from Cursor's documentation and passes the conformance suite, but has not run in a real Cursor session (the owner has no Cursor access yet, decision of 2026-11-02). The checklist for such a session is in the preset's README; a fix found there ships as `0.1.1`. Native mode (Cursor is the only runtime): `.cursor/hooks.json` for `sessionStart`, `beforeShellExecution`, `preToolUse` on `Write` and `afterFileEdit`, and the skills in `.cursor/skills/`. Compat mode (next to Claude Code, which Cursor already loads from `.claude/`): no hook file and no skills of its own, so nothing runs twice, and `harness check scaffold` fails on a framework hook in `.cursor/hooks.json`. Both modes keep the `access.denyRead` patterns in a block of `.cursorignore`. Cursor reads `AGENTS.md` itself, so the entry file must be `AGENTS.md`. The recorded-form samples of the Cursor events moved from `tests/fixtures/events/` into the adapter (`events/`), marked as written from the documentation.
- the optional runtime role `managed-blocks` (`managedBlocks(profile) → [{ path, block, content }]`) for blocks of a file of the project that the sync keeps up to date between `# harness:begin <block>` and `# harness:end <block>` lines, as an ignore file needs (an HTML comment would be a pattern). The sync adds the block at the end of the file when the file lacks it and makes the file when it is missing, so the project's own lines stay; `check generated` and the lock hold the block like any other. The packaging of a procedure may now return no path for a profile (`skillPath(procedure, profile)`). A project that wrote an adapter of its own needs no change.
- the Python stack preset (`adapters/stack/python/`; task 1.3), written by following the new-adapter procedure: uv workspaces, pytest with coverage.py (branch coverage; the raw report is merged and turned into the neutral summary by `coverage.mjs`), ruff for lint (E, F, I, B, UP, ANN, T20) and format, mypy in strict mode; the local gate plan (`gate.mjs`), the CI jobs, and a scaffold with a root `pyproject.toml`, `.python-version` and `.nvmrc`. A project selects it with `adapters.stacks`, alone or next to `node-ts`. The project creates `uv.lock` once with `uv lock` and commits it: CI installs with `uv sync --locked`.
- the examples (task 1.4). `examples/profile/` is a filled profile of a fictitious project, `examples/product/` its product specification, and `examples/plan/` a sample plan with one phase and two tasks with their logs; the framework's tests hold each to the check it exercises, and `examples/README.md` explains them. The bootstrap now writes the **product-knowledge skeleton** into a new project's `docs/product/` (an index, a glossary, a register of open questions and a backlog, from `core/templates/scaffold/product-*.md`), sets `productKnowledge` and the document roles `specification` and `glossary` in its profile file, and adds a row for the specification to the reading map of its entry file, so `harness check product-knowledge` runs on every new project. A project that bootstrapped before has no such files and no `productKnowledge`, and nothing changes for it.
- the proof of the design on a scratch project for every combination (task 1.5), repeatable with `tests/proof/proof.sh <directory>`: (A) node-ts with Claude Code, (B) python with Cursor in native mode, (C) node-ts and python together with both runtimes (Cursor in compat mode), (D) a detached project with a core rule edited, and (E) a repository that copied the first harness, adopted with `harness adopt`. On each, `harness check all` passes (run from the project's own copy of the tools), the stack's commands pass (`npm ci`, lint, tests and the documentation check; `uv lock`, `uv sync --locked`, ruff, mypy, pytest with coverage.py and `harness coverage summarize`), and the files of the runtime are as the design says (62 checks in all). A short targeted harness review (`tests/proof/review.mjs` gives the measurements) scores D1 layer integrity 5 (no stack or product term and no link out of CORE in 24,000 words of core), D3 injection 5 (no profile value written outside the profile) and D6 routing 4 (no orphan document; the always-loaded entry file is about 1,650 words, because it carries the rules every task needs). **The Cursor preset is unverified in a live session**: the proof runs its files and hooks against samples written from Cursor's documentation, not Cursor; the checklist in its README stays open, and a fix found there ships as `0.1.1`.

### Changed

- The total line of the plan summary starts at the plan's first phase (`Phase 1` for a plan of one phase), not at Phase 0.
- The protection rule of the entry file no longer names a script: the host enforces it with the ruleset `harness host protect` sets, and
  when `host.protection` is off the rule falls back to the hooks. The profile role `repository.protectionScript` is gone, and so is the
  clause from the Role binding line.
- Two rules of the non-negotiables are worded without a stack: "no new untyped public boundaries" (the stack's lint rule names them) and
  "no debug printing" (use the logger).
- The method's local-database step applies only where the profile has the database commands (`commands.dbUp`, `dbMigrate`, `dbSeed`), an
  optional role group; `documents.method` defaults to the vendored method.
- The host command line of the host adapter's logic roles is the seam `cli` (was `gh`), so one conformance check can pass a stand-in to any host. The
  claude-code event samples moved from `tests/fixtures/events/` into the adapter (`adapters/runtime/claude-code/events/`), where the suite replays them.
  A sync also vendors the three skeletons.
- the stack contract grew where the Python preset needed it, all additive for a stack that exists: `harness coverage summarize` writes the neutral summary from the raw report of one local run (for a tool that does not write it itself); `coverage-merge` gets `{ root, pkg }` as a second argument; an `ignore-files` entry may carry a `pattern` and an `example` for a tool that excludes paths with a setting; the release tool reads and writes the `version` of the `[project]` table of a TOML file; and `.nvmrc` is a file of lines in the node-ts preset, so that a project with two stacks bootstraps. A stack adapter of your own needs no change. The new-adapter guide has a section on what a stack learns the hard way.

### Fixed

- three defects the proof found. (1) A project with two stacks got a CI workflow with the same job ids twice (`static`, and each coverage package): each stack now names its static job after itself, runs its own commands, runs the documentation check only in the first, and keeps the coverage jobs of its own packages (`ciJobs(profile, context)` in the stack contract). (2) The document map of the profile document dropped a row when any role in it had no value, which hid the releases guide, the changelog and the plan method from every new project: each document has a row of its own now, and the starter profile names the changelog. (3) An orphan: the documents the map dropped were not reachable from the entry file; with the map fixed, a new project has none.
- `harness release` could not release from a development version such as `0.1.0-dev.1` (it did not parse it); a development version is now below its own release, so `0.1.0` and `patch` both give `0.1.0`. Found cutting `0.1.0`.
