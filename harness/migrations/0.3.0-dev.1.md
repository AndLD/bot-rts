# Migration to 0.3.0-dev.1 from 0.2.0

The first development version of `0.3.0`. It is for trying the version before its final tag: the note of the final version, `0.3.0.md`, tells the whole story from `0.2.0` and is finished with that version, so a project that takes `0.3.0` after this one reads that note, and this one stays as it is. The version moves the order of the releases out of the plan index into a file of its own, adds **flows** (files of the plan that an orchestrator agent runs, step by step, to deliver releases), lets a project keep **adapters in its own repository**, and fixes defects found in use (I-8 to I-11). A project that ships no versions and starts no flow needs almost nothing from this version; the actions below say who needs what.

## What changed for a project

- **The release order has a file of its own** (5.1). A project that ships versions names it in the new profile role `paths.releases`: one table `Release | Status | Tasks, in order | Consumers | Notes` and a list "Not scheduled", from the template `core/plan/releases-template.md`. The tools read the order of the tasks from it instead of the section "Order of development" of the plan index; the index shows the current and the next release in a generated block that links to the file. The script of this version moves a table of the section into the file, sets the role and leaves the block in the index. **An order written as prose** (arrows of phase numbers) cannot be read by a tool and is left as it is, with a message. `check plan` refuses a backlog item and an unknown id in the file. A project that ships no versions needs no file.
- **Flows** (5.2, 5.4). With `paths.flows` (and only where there is a releases file), a flow is a file `flow-<n>-<slug>.md` with a settings block and a table of steps, and its append-only log beside it. The new procedure `run-flow` (and its skill) says how an orchestrator runs one: decision levels D0 to D4, the modes `brainstorm` and `seamless`, the step report a worker ends with, the unbiased analysis. `harness flow check` (also in `check all`), `status`, `next` and `prompt` read a flow against the repository. The resume phrases may name flows ("Run flow N"). A project without flows changes nothing.
- **The authority of a flow** (5.3, a change of the meaning of core rules). A flow the owner started may cut releases and answer or close reports at the levels its settings give them, for its home repository only; the rule `agent.ask-merge` lets such an orchestrator approve the merge of a release or hotfix pull request by merge commit once the required checks are green. The shell guard still refuses auto-merge and an administrator's bypass there. Nothing changes outside a flow.
- **Executors: the runtime-adapter contract is at version 2** (5.5). The new **required logic role `executors`** says how an orchestrator starts a worker with a model and an effort, continues it, fetches its report and reads its context: `session`, `subagent` or `manual`. The Claude Code preset maps the desktop app's sessions and the command line; the Cursor preset offers `manual` only. `harness flow dispatch` picks the executor and decides whether the previous worker continues. **A local runtime adapter must now fill the role** (required action 3).
- **Usage** (5.6, 5.7). The optional runtime role `usage` reads the account's windows and carries provisional coefficients. `harness flow estimate`, `gate`, `sample` and `calibrate` size a flow, say whether a step may start, record measurements and propose new coefficients (`calibrate` writes nothing).
- **Flows across repositories** (5.8). A flow's `repos` setting names external repositories as rows (`remote`, `role`, `kinds`); their folders are in the ignored `harness-profile.local.json`. The new optional host role `remote-state` lets `flow status` read the consumer's lock and pull requests. The old `repos` setting of 5.4 (a map of aliases to paths) is gone; nothing used it.
- **Adapters of a project's own repository** (3.4). A folder `harness-adapters/<axis>/<name>/` that the profile file selects as `local:<name>` is loaded like a preset; a sync and `migrate` leave it alone, `check adapters` holds its manifest to the contract, and the new check `local-adapters` runs the conformance suite on it. `harness migrate` stops before it commits when a local adapter no longer meets the contract.
- **Fixes** (I-8 to I-11 and 5.9). A push from a linked Git worktree no longer lets the gate's tests rewrite the repository's Git config (I-8; a repository already damaged needs `git config core.bare false` and its `core.hooksPath` set back by hand). A condition inside a line of a procedure is rendered instead of copied into the generated skills (I-9). A flow continued from another account no longer resumes a worker that account cannot find (I-10; the log's "step started" line gains an `Account:` field). A worker a flow starts on the command line is no longer refused every edit and command (I-11): the flow settings gain `permissions`, absent by default, which the Claude Code preset turns into `--permission-mode` and `--allowedTools`. Smaller fixes of the flow tools: after a step the orchestrator ran itself the next step may continue the previous worker, and `flow status` counts a pull request of an external repository as taking a version only when its title names it.

## Required actions

1. **Take the migration.** Run `sync` on a branch of its own, then `node harness/tools/harness.mjs migrate` if the `sync` did not start it. The script of `0.3.0` moves a table of the "Order of development" section of your plan index into the releases file and sets `paths.releases`; if you ship no versions, it changes nothing.
   Check: `node harness/tools/harness.mjs check generated` exits 0, and `migrations.version` in `harness.lock.json` is `0.3.0-dev.1`.
2. **If your order of development is prose** (arrows of phase numbers, not a table), write it as the table of `harness/core/plan/releases-template.md` in the file named by `paths.releases`, set the role, and run `node harness/tools/harness.mjs plan summary`. The migration says when this applies and leaves the section as it was.
   Check: `node harness/tools/harness.mjs check plan` exits 0.
3. **If you have a local runtime adapter** (`harness-adapters/runtime/<name>/`): fill the new required role `executors`. Copy `executors.mjs` from `harness/adapters/runtime/_skeleton/` and return `{ manual }` when the runtime offers no automation; add the role to the manifest and set `"contract": 2`. A local stack or host adapter needs nothing.
   Check: `node harness/tools/harness.mjs check local-adapters` exits 0.
4. **If you will use flows, say your resume phrases.** Add "Run flow N", "Run flows N–M" and "Continue flow N" to `plan.resumePhrases` of the profile file, and `paths.flows`. A document of yours that restates the order of development as a section of the plan index, or the rule that every release cut and every answer to a report is the owner's, now restates a changed rule: link to the core document instead.
   Check: `node harness/tools/harness.mjs check all` exits 0.

## Optional actions

- **Start your first flow**: copy `harness/core/plan/flow-template.md` to `<paths.flows>/flow-1-<slug>.md` and its log from `flow-log-template.md`, name the releases it delivers, list the steps and run `node harness/tools/harness.mjs flow check`. A step in another repository needs a `Repo` column, a row in `repos`, and the folder in the ignored `harness-profile.local.json`.
  Check: `node harness/tools/harness.mjs flow status 1` prints the next step.
- **Tell the tools your subscription**: `{ "usage": { "subscription": "pro" } }` in the ignored `harness-profile.local.json` (`pro`, `max5x`, `max20x` or `api` for Claude Code).
  Check: `node harness/tools/harness.mjs flow estimate 1` names the subscription.
- **Say what a worker of a flow may do**, if a flow starts workers on the command line: set `permissions` in its settings block (for example `{ "mode": "acceptEdits", "allow": ["Bash(git *)", "Bash(gh *)", "Bash(npm *)", "Bash(node *)"] }`). The choice is the owner's; without it such a worker reports itself blocked at its first edit.
  Check: `node harness/tools/harness.mjs flow dispatch 1 1` prints what the worker will be allowed.
- Adapters of your own repository: see `harness/core/contracts/new-adapter.md` and the procedure `new-adapter`.

## How to verify

```bash
node harness/tools/harness.mjs check all
node harness/tools/harness.mjs flow check
node harness/tools/harness.mjs probes 0.2.0 0.3.0-dev.1
```

The first two exit 0 on a healthy project; the third lists the probes whose areas this version touched.
