## [0.2.0] - 2026-11-04

Migration note: [migrations/0.2.0.md](migrations/0.2.0.md)

### Added

- migration scripts. A version may ship `migrations/<version>.mjs`; `harness migrate` runs, with the new version's tools, the scripts of every version after the project's own up to the target that the lock does not record, in version order, records them (`migrations` in `harness.lock.json`), and prints the migration notes of those versions in order. A lock without the record counts as `0.1.0` with nothing applied. The migration test bootstraps a project from each released tag and migrates it to the current tree. A script checks its starting state and can run twice.
- `harness rollback` and the safeguards that make a migration undoable. `sync` refuses to start on the production or the integration branch and with uncommitted changes, and records the commit and version it starts from in the lock; `migrate` commits the migration as one commit (the sync's changes included); `rollback` puts every file that commit changed back to its content at the start and removes the files it added, and nothing else. After the `sync` of an older version, `migrate` takes that sync's files into its commit and refuses any other uncommitted change.
- the cold-start probes of a project name the areas they exercise, so that taking a version reruns the right ones. Each probe in the harness-review bindings has an `Areas` column (the areas of the migration notes) and the words read at the last review; the bindings stub of a new project has four starting probes. `harness probes <from> <to>` prints the probes to run again for the versions taken and, for an area no probe covers, the framework's starting probe (`core/reviews/harness/starting-probes.md`); `harness check probes` holds the area names.
- reports from users are taken in and sent upstream by procedures, set by switches in the profile file. `reports.intake` (`off`, `notify`, `auto`) and `reports.triageLimit`: the session start lists the open reports and those not triaged yet, and with `auto` the agent triages at most the limit before other work by the procedure `triage-reports`, which looks for the same or a close problem in the issue queue, its archive and the open tasks before adding a new issue. `reports.upstream` (`off`, `ask`, `post`): the procedure `report-upstream` drafts and posts a suspected defect of the framework. `harness reports …` reaches the host through its adapter's new `reports` role (GitHub: `gh`); answering, closing and creating need the owner's approval. A local, ignored `harness-profile.local.json` overrides the switches at once. A switch that is on adds one line to the entry file's Git rules; one that is off adds nothing, no skill and no row of the reading map.
- a backlog for the feature requests, beside the issue queue and optional like it. It is the place for what the owner has not approved: an item is a proposal, never started as it is. The profile role `paths.backlog` names a folder with an index of the proposed items (generated by `harness plan summary` and counted in the plan index), a file per item (`B-<n>.md`, from the new backlog template), and `archived/` for the promoted ones. An item is `Proposed` or `Promoted` (with `Promoted to:`), has no branch, no claim and no log, and has a `Source:` set to `report` and the link of each report, `owner` or `agent`. The owner's decision is `harness plan promote <B-n> --phase <n> [--agent <marker>] [--size <n>] --approved`, which writes the next task of the phase from the item, sets the item to `Promoted`, moves it to the archive and updates the size of the phase; an order of development, an execution order or a `Needs` that names a proposed item is a problem of `check plan`. `harness reports plan` has the relation `feature`, `reports candidates` compares the backlog too, the session start says how many proposals wait, and an issue that moves to the backlog keeps its number (`B-1, formerly I-6`), which the issue queue never gives again. A project without the role has no backlog; a project that sets `paths.backlog` gets the folder, its indexes and the block of the plan index from the next `harness plan summary`.
- a project can have procedures of its own. The new profile role `paths.procedures` names a folder of procedure files in the format of `core/procedures/`; the skill generators package them for the selected agent runtimes (the note of origin in a skill names the project's file), the `procedures` block of the entry file lists them after the framework's, and `harness check generated` fails on a stale skill of one. A name that the framework's procedures have too is an error. The CORE scan does not read the folder; the project classifies it in its layer map. Nothing to do for a project that does not set the role.
- the procedure `change-plan` (invocation `auto`, so an agent loads it as a skill on its own): adding a task, adding a phase, recording a defect or an improvement found in use as an issue, and splitting a phase. It tells the agent to read the plan method, the rules of a phase file and the template first, never to copy an old phase, task or issue, and to leave every generated block to `harness plan summary`. Its row is in the procedures block of the entry file and its skill is written by the next `sync`.
- the procedure `update-framework` (explicit: a person asks for it, as for `release`): taking a version of the framework from the one in the lock to the target across any number of versions. The branch of its own, `sync` and `migrate` (run by hand after the `sync` of a version before 0.2.0), the migration notes of every version in order with the check of each required action, `check all` and the project's gate, the probes that `harness probes <from> <to>` selects compared with the last review, what the notes missed written in the pull request and reported upstream, `harness rollback` when it fails, and the pull request. It also says how to adopt a project that copied the first harness and how to report a defect found in the framework. Its skill is written by the next `sync`.
- templates for a risk register and for design records (RFCs), the two cross-cutting documents the plan method names but the framework shipped nothing for. The bootstrap writes them once into a new project, at the new optional roles `documents.riskRegister` and `documents.rfcs` (the starter values are `docs/development-plan/cross-cutting/risk-register.md` and `.../decisions/README.md`): the register with its rules and its table (likelihood, impact, mitigation, owner, status, date reviewed), and the index of the records with the rules (immutable after acceptance, superseded by a new record, cited by the task) and the template of a record. Both appear in the document map of the profile document. No check reads them. A project that already has such documents, or leaves the roles empty, gets nothing; to take the templates, set the two roles and copy the files from `harness/core/templates/scaffold/`.
- `probes.run` in the profile file (`auto`, `ask`, the default, or `disabled`; the ignored `harness-profile.local.json` overrides it on one machine) for how taking a version handles the cold-start probes of the project, which are a session each and read thousands of words. The end of the output of `harness migrate` and of `harness probes` says what the mode asks of whoever takes the version: run them (`auto`), ask the owner first and run them only on a yes (`ask`), or leave them (`disabled`). The procedure `update-framework` follows the mode. No command starts a probe itself yet, so `auto` and `ask` are instructions; a project that takes the version and wants no probes sets `disabled`.

### Changed

- a phase of the plan is a folder, `phases/phase-<n>-<slug>/`: `README.md` is its index (goal, order, exit criteria, and a task table that `harness plan summary` generates from the task files), `<id>.md` is a task, `<id>.log.md` is its log beside it, and `log.md` is the phase-wide log. A resuming agent reads the index and one task file instead of the whole phase, and a finished task writes only its own log. `harness check plan` holds the layout, the session-start hook prints the newest next step across the logs and the open tasks, and `harness plan split <phase>` (and the migration script of this version, for the open phases) splits a one-file phase and rewrites every link into it. The tools still read the one-file layout. The phase template became a phase-index template and a task template.
- the defects and improvements found in use are no longer a phase that never ends. They are an issue queue, `paths.issues`: a file per issue (`I-<n>.md`, with `Area:`, `Reported:` and its log beside it), an index of the open ones, and `archived/` where `harness plan summary` moves the finished ones. Branches are `bugfix/I-<n>-<slug>`; "Work the issue queue" and "Fix I-<n>" approve their pull requests. The migration script of this version turns a project's open-ended phase into a normal phase that keeps every id, makes only its defects that have not started into issues (`I-1, formerly 12.5`), and replaces `plan.openEndedPhase` and `plan.openEndedPhaseNumber` of the profile file with `paths.issues`. `harness check plan` fails when an order names an id that exists nowhere.
- `harness check plan` holds the structure of a phase kept as a folder, as `core/plan/phases.md` section 9 states it: the parts of the phase index present and in order (the exit criteria as the line `**Exit criteria:**`, not a heading), the back-links of the index, the task files and the logs, a work-log link that resolves, a log of its own (or a row of the implementation log) for every done task and the tasks that a task `Needs`, which must exist and not be in a later phase. A phase of the older layout is checked as before. A project whose phase folders (the ones `harness plan split` or the migration of this version wrote, or its own) lack a part reports it; the message names the part and the template.
- the procedures that the method requires of every agent unasked can be loaded by the agent: `start-task`, `end-session`, `finish-phase` and `triage-reports` are `invocation: auto`, so the Claude Code preset (and Cursor) no longer writes `disable-model-invocation: true` into their skills. The procedures a person starts or that act outside the repository stay `explicit` (`release`, `code-review`, `harness-review`, `new-adapter`, `update-framework`, `report-upstream`). The format says it: `explicit` is only for a procedure that an agent must not start on its own judgment (design §8.1). A project takes the change with the next `sync`, which rewrites the four skills; nothing else to do. A procedure of the project's own folder (`paths.procedures`) follows the same rule.
- the harness review method counts the `procedures` block of the entry file apart (its rows and words, in M6, and its rows in the rule load M20) and the bindings of a project set a ceiling for both; the bindings stub of a new project has a `Budgets` section for them. The cold-start probes of a project include the extension of a document (add a phase to the plan; put a defect found in use into the plan): the stub ships them as P5 and P6 beside the routine ones, and `starting-probes.md` says what to record. The method also says how a probe runs: a probe of another repository, or one that depends on the session start, runs as a separate session started in that repository, because a subagent of the reviewing session inherits that session's entry file and gets no session-start hook. A project that already has bindings adds the two probes and its budget at its next review; nothing else to do.
- every version has a migration note, a development version included: `migrations/<x.y.z>-dev.<n>.md` says what a project does when it takes that development version from the previous one (the previous development version of the same `x.y.z`, else the previous final version) and is frozen once the version ships; the final note stays the complete story. `harness migrate` and `harness probes` read the notes of the versions after the project's own up to the target, leaving out the development notes of an `x.y.z` when its final note is among them. `harness release --dev` now refuses a version without its note, as the final release does, and writes a stub (the changelog fragments added since the previous release, the areas, and a `TODO` in the required actions) when the note is missing; a `TODO` left in the required actions stops any release. The release guide and the procedure `release` put the note before every cut. A project with its own release flow adds the note of the development version before it tags it; nothing else to do.

### Fixed

- after `harness sync` to a new version `check generated` could fail until `sync --local` ran again, because the sync generated the managed files with the tools of the old version. `sync` now only places the files and updates the lock, then starts the new command `harness migrate` of the new version in a new process, which regenerates them. A project whose `sync` is older than this version runs `node harness/tools/harness.mjs migrate` itself after the sync.
- `harness sync` no longer copies the framework's tests (`*.test.mjs`) into a project. They prove the framework against its own repository (its profile file, every preset, its documents), so in a pinned project 20 of 428 failed for what the project does not have, and nothing in a project runs them. `framework.json` lists the file name endings a sync leaves out in `excluded`; the next sync removes the test files from `harness/`.
- `harness migrate` took a project that an older `sync` (before `0.2.0`) had updated for `0.1.0`, because that `sync` replaces the version in the lock and keeps no record of where the project was: the start recorded for `harness rollback` named `0.1.0`, and the notes of the versions the project had already taken were printed again. `migrate` now reads the version from the lock of the last commit (the commit the migration starts from) when the lock has no record; a lock that no commit holds still counts as `0.1.0`. Nothing to do for a project.
- the migration script of `0.2.0` adds the phase folders and the issue queue to the layer map of a project that has one of its own. Such a project listed `<phases>/phase-*.md` in a layer and not the folders, so `harness check layers` failed on every file of a phase folder and of the queue, and `check paths` read the finished tasks the one-file phases were exempt from as state documents. The script adds `<phases>/phase-*/**` and `<issues>/**` as lines of the layer that claims the one-file phases, where no layer claims the folders already, and says what it added (or what to add by hand, when the file cannot be edited safely). A project that did this by hand is left as it is.
- the migration script of `0.2.0` no longer moves a task that a branch claims to the issue queue. A task in hand (claimed by a draft pull request) that was still ⬜ was read as not started, so it became an issue under a new id and the phase was closed without it. The script now keeps a ⬜ task for which a branch of the repository, local or remote-tracking, is named `<type>/<task id>-<slug>`, and says which it kept. The procedure `update-framework` says to set the task in hand to 🟡 before the `sync`, because the task is then never read as not started. Nothing else to do.
- `harness check probes` now says once which columns the table of the probes has and which it needs (`Probe | Scenario | Areas | Words read at the last review`) when the third column of the table is not "Areas". A project whose bindings kept the older table (`Id | Scenario | Expected`) got a line for each probe, naming the text of its third cell as an area that does not exist. If your table has other columns, make it the four columns above and move what the others held to a list below the table; the note of the version that carries this change lists the step.

## [0.1.2] - 2026-11-03

Migration note: [migrations/0.1.2.md](migrations/0.1.2.md)

### Added

- auto-merge for the pull requests an agent may merge without asking. The profile switch `host.autoMerge` is on where `host.protection` is `true` and off where it is `false`; on, the core rule has the agent enable the host's auto-merge (squash) as the last step of a task, the shell guard refuses `gh pr merge --auto` into the production branch, on a release or hotfix branch, on a pull request not into the integration branch and where the switch is off, and the rule `agent.no-auto-merge` (ask first) applies where it is off. `harness host protect` allows auto-merge on the repository, the GitHub adapter scaffolds `update-branches.yml` (it brings the integration branch into the pull requests waiting on auto-merge) and the trigger `workflow_dispatch` of the CI template, `harness branch update [--previous <branch>]` merges the integration branch into a stacked task after the squash merge and resolves the conflicts only that squash causes, and the bootstrap asks the host what it offers and sets `host.protection` and the host (`--no-host-setup` skips it). The runtime adapter says how a session waits for a pull request, and the final message lists the pull requests that wait for the owner. See the migration note of the version for what an existing project does.

### Changed

- a claim belongs to its session while that session works, and a session that resumes a phase continues a claimed task when the task's log or the phase's work log records a pause or a "next step" that names it, or when the owner says so; otherwise it asks (method §6 and §7, the claim rule of the entry file, the resume step of the procedure `start-task`). `start-task` chooses the next task by the order the plan says (the phase's `Execution order`, the plan index's order of development when the phase points there), the order of the table only when neither exists. Added: when no phase is in progress, the session-start hook prints the next task by that rule (`tools/lib/next-task.mjs`).

### Fixed

- `harness release` writes the version into a JSON version file without reformatting the file, so that the project's formatter check does not fail on a release commit; the profile role `host.autoMerge` has a plain default as well as `x-sameAs`, so that a sync run by the tools of the earlier version (which do not know `x-sameAs`) no longer stops half way on the entry-file rules of this version.
- the bootstrap fills `repository.url` of a new project's profile file from the repository's slug, through the new optional role `repository-address` of the host adapter (`repositoryUrl({ slug })`; GitHub: `https://github.com/<slug>`), so that `harness release` no longer writes `undefined` into the compare and tag links of the changelog. An address already in the profile file is kept.
- the Git guard of the agent runtime (`guard-shell`) judges each Git command by the branch of the repository the command acts on, not by the branch of the project directory. It follows a `cd` before the command (a `cd` inside parentheses ends with them), `-C`, `--git-dir` and the variables `GIT_DIR`, and a repository it cannot resolve (an unknown directory, a variable, `--work-tree` alone) is judged as a protected branch. A commit in another clone's task branch is no longer refused while the project is on its integration branch, and a commit or push in another clone's integration branch is no longer allowed while the project is on a task branch.
- `harness branch update --previous <branch>` took this branch's side of a conflict even when the branch was made from an older commit of the previous one, and so dropped what the previous branch had gained since. It now takes the previous branch's tip into this branch first, and stops with the merge in progress when that conflicts.
- a new Python project is green in its static checks, and says what it still needs. The python stack scaffolds a `pyproject.toml`, a typed first module and a test in each package (at the root when the project has none), so that `uv lock` finds every workspace member and `mypy .` finds a source file. The lock file cannot be written by the scaffold, so the new manifest field `firstSteps` of an adapter lists what a project does once by hand (the python stack: run `uv lock` and commit `uv.lock`, without which CI, which installs with `uv sync --locked`, is red): the bootstrap prints those steps and the scaffolded stack file lists them.
- the command line and the runtime hooks (`guard-shell`, `guard-edit`, `format-edited`, `session-start`) did nothing, with exit code 0, when started through a symbolic link, because `process.argv[1]` is the link and `import.meta` the real path. A project under a linked folder had its hooks switched off without a message. They now compare real paths (`tools/lib/main-module.mjs`).

## [0.1.1] - 2026-11-03

Migration note: [migrations/0.1.1.md](migrations/0.1.1.md)

### Added

- a migration note for every version, `migrations/<version>.md` (from `0.1.1`), in a fixed shape: what changed for a project, the areas touched, the required actions with their checks, the optional actions, how to verify. `migrations/` is distributed with the framework. With `release.migrations` in the profile file, `harness release` refuses a version without its note, writes the areas the version touched into it (derived from the files that changed in `core/`, `tools/`, `adapters/` and `profile/` since the previous tag, by `migrations/areas.json`) and links the note from the changelog entry. The README says how a project takes a version, also across several.
- `core/vocabulary.json`, the words the framework's core uses on purpose (task, phase, plan, release, review, session, agent, …). The CORE scan never reports one of them, whatever the term lists of a project say.
- `terms.exceptions` in the profile file records a hit of the CORE scan in the vendored `core/` (the file, the word, the link to the upstream report, and the framework version it holds for). `harness check core` accepts it while the lock is at that version, and fails on the exception after a sync to another version or when the hit is gone, so an exception cannot outlive the fix.
- `harness release --dev` sets the next development version of a release (`<x.y.z>-dev.<n>`, the changelog and its fragments untouched), and the release procedure tags it before the final tag, so that a project can sync it and run its checks, the CORE scan included.
- the issue template "A word found in core" and a section of the README on what to do with a word the scan reports in `core/`: an ordinary word is answered in the project (`terms.productGeneric`, and `core/vocabulary.json` when the core uses it on purpose), a leak is a defect fixed in a patch release.

### Changed

- the framework's own CORE scan refuses the names of tools that no adapter covers: databases, ORMs, web and test frameworks, containers and cloud services, and other hosts and agent runtimes (`terms.stack` of its profile file). Neutral words such as "database" or "container" stay allowed.
- `harness check core` in a pinned project scans the vendored `core/` with the project's own `terms` and the adapters' terms, so a product or tool word of the project that reached the framework's core is found before a release is taken. A hit names the file, the line and the word, and the two ways out: add an ordinary word to `terms.productGeneric`, or report a product or tool word upstream and stay on the current version.

## [0.1.0] - 2026-11-02

### Added

- `harness adopt` (design §6.4; task 1.1): the bootstrap for a repository that copied the first harness. The agent-runtime contract gains the optional role `hook-adoption` (`adoptConfiguration`), which the Claude Code preset fills: it adds the framework's hook entries and read exclusions to the project's own `.claude/settings.json` and names the hook commands that are the project's own.
- The framework is its own project (design §11): lock mode `self` with the profile role `paths.frameworkDir` (`.`), `harness init --self` and `harness bootstrap --self`, its own plan (Phases 1 to 3), CI and rules. The first tagged development version is `0.1.0-dev.1`.
- The skeleton of the framework: the folders of the layout, `framework.json` at `0.1.0-dev`, the MIT license, this changelog and the
  README. The core documents, the tools and the adapters follow in the build tasks of the design.
- Vendoring (design §1): `harness sync` (from a folder or a Git tag, with the selected adapters only), `sync --local`, `check vendored`,
  `diff`, `override` and `detach`, with `harness.lock.json` in the modes `pinned`, `detached` and `self`. Plain Node, no dependencies.
- The generic tools (design §3.4), merged from both copies that existed: `check all`, `check links` (anchors keep `_` as the host does),
  `check paths` (new), `check core`, `check plan` with `plan summary` and `plan log`, `check changelog` with `release` and `release notes`,
  `check product-knowledge` (its file names and exceptions in the profile's `productKnowledge`), and `ci changes` with
  `checks.documentationPaths`. The profile gains `checks`, `productKnowledge`, `release` and `paths.entryFile`.
- The two features of the second source (design §3.4): the link check's index rule (`checks.indexedFolders`: the README of an indexed folder
  links every file and subfolder that Git tracks in it) and the agent-complexity markers of the plan (`plan.complexity`: the scale and the
  model of each marker; every open task carries one in an `Agent` column before `SP`, done tasks are exempt, and the plan index shows each
  phase's range). Without `plan.complexity` the plan has no markers.
- The core documents (design §3.2): the engineering method (`core/method/`), the plan method with the index, phase and task-log templates,
  the definition of done and the guiding principles (`core/plan/`), the review methods with their report templates (`core/reviews/`) and
  the changelog-fragment format (`core/templates/`). Their links to project documents are role names, and none leaves `core/`.
- The entry file's rules as managed blocks: `core/rules/non-negotiables.md` and `core/rules/git.md`, rendered into the blocks
  `non-negotiables` and `git-rules` with the Role binding line from the profile (`plan.openEndedPhaseNumber`,
  `repository.protectionScript`), each rule with a stable id; the lock keeps one hash per block (`<path>#<block>`), and the layer map
  counts the blocks as CORE, so `layers.core` is empty for a project that uses the framework.
- `check generated`: every managed file and block rendered again and compared, in every mode.
- The plan method describes the agent-complexity markers as a standard, optional task property (its section 7): the `Agent` column of the
  phase template, the range column of the index template, the conformance rule and the exemption of done tasks.

- The adapter contracts (design §4): `core/contracts/{stack,runtime,host}.md`, their machine form `profile/manifest.schema.json` (`x-roles`),
  `harness check adapters` (a manifest filled to its contract), and the adapters' `terms` joined into the CORE scan. `adapters.stacks`
  entries may list the `packages` they own, and `check profile` fails when two stacks claim one folder or a project with several stacks
  leaves one without folders.
- The GitHub host adapter (`adapters/host/github/`): `protect.mjs` (`harness host protect`, the ruleset of the protected branches, now on
  Node, with the detection of whether the host can protect the repository and the new profile role `host.protection`, which must agree
  with it), `workflows.mjs` (the triggers and job names of the workflow files) and the workflow templates `ci.yml` and `release.yml`
  (the pull-request title check, change detection, the aggregator, coverage packages read from the profile).
- `harness check values` (replaces a project's profile test): the host's CI triggers equal the protected branches; every required check is a
  job; no branch, repository or plan path of the profile is spelled out in the files of `checks.roleOnlyPaths`, and no workflow names a
  protected branch outside its triggers or lists the coverage packages.
- `{{#unless …}}` blocks in the template engine.

- The node-ts stack preset (`adapters/stack/node-ts/`): `gate.mjs` (the plan of the local gate: typecheck, lint and format of the touched
  packages, the tests related to the changed files, the whole package for a change that cannot be followed, the changed-file coverage),
  `coverage.mjs` (the merge of Istanbul shards and the neutral coverage summary, without a dependency), `ci-jobs.mjs` (a static job and a
  coverage job per package for the host's workflow frame) and its manifest, with the stack role "ignore files".
- The gate driver `harness gate` (the local gate of a push): it routes each changed file to the stack that owns it, runs the documentation
  checks for a push that changes documentation, and adds the project's own steps (the profile role `gate`: `outside`, `isolated`, `needs`,
  `prepare`, `steps`). `harness coverage check-changed` and `harness coverage merge` apply the coverage gate to the neutral summary.
- `harness check scaffold`: the stack's ignore files exclude the vendored framework.

- The runtime hooks (`tools/runtime-hooks/`): `guard-shell` (the Git rules of the entry file, `--no-verify`, and the merge guard of a host
  without protection), `guard-edit` (environment files, and the vendored framework in pinned mode), `format-edited` (the formatter of the stack
  that owns the file, from the project's installation, never downloaded) and `session-start`, with `io.mjs`, which reads the event of Claude Code
  or Cursor (recognised by `cursor_version`; native and compat modes) and answers in its form. Recorded event samples of both runtimes are in
  `tests/fixtures/events/` (the Cursor ones are written from its documentation, not recorded in a live session).
- The Git hooks `tools/git-hooks/pre-commit` (no commit on a protected branch, except the root commit of a new repository) and `pre-push` (the
  vendored check, a protected or deleted remote ref, the project's setup script `hooks.prePushSetup`, then `harness gate`), and `harness guard`.
- The Claude Code preset (`adapters/runtime/claude-code/`): `CLAUDE.md` that imports the entry file, `.claude/settings.json` from the profile
  (`settings.mjs`: the hook entries and the `Read(...)` deny rules of the new profile role `access.denyRead`), and the scaffold invariants
  (`harness check scaffold` fails on a missing hook entry or deny rule).
- The merge guard of the GitHub host adapter (`gh pr merge` while a required check is not green), used when `host.protection` is false.
- The core rows of the rule-to-check map, generated from the `enforces` declarations of the adapters and the Git hooks, for both protection cases
  (a managed block in the rule-map document); the manifest gains `enforces`.

- The neutral procedures (B6): `core/procedures/` with `start-task`, `end-session`, `open-pull-request`, `finish-phase`, `release`, `harness-review` and
  `code-review` (frontmatter `name`, `description`, `invocation`; a body that names roles and commands as `{{commands.lint}}`). The Claude Code preset
  packages each as `.claude/skills/<name>/SKILL.md` (explicit ones with `disable-model-invocation`), generated by `harness sync` and held by
  `harness check generated`; the entry file's managed block `procedures` lists them for every agent: "when …, follow
  `harness/core/procedures/<name>.md`". `new-adapter` follows with the conformance suite.
- The bootstrap (design §6): `harness init` (interactive, or with flags and `--set`), `harness bootstrap`, `harness template <dir>` (the
  template repository, built by the engine) and `BOOTSTRAP.md`, all through one engine that completes the profile file from the answers,
  `profile/starter.json` and the new `defaults` of the adapters' manifests. The scaffold is the core templates of `core/templates/scaffold/`
  and the new optional `scaffold-files` role of each axis (node-ts: the Node version, the ignore file, a package manifest and an empty lock
  file; claude-code: `CLAUDE.md` and the settings; github: the CI and release workflows). The bootstrap commits the root commit of the
  integration branch, makes the production branch, installs the Git hooks and runs `check all`; `--detached` equals a pinned bootstrap
  followed by `detach`. `documents.harnessBindings` is optional.
- The conformance suite (design §5): `harness adapter test <path>` runs the checks of an adapter's axis (`tools/conformance/`), and the presets pass it in
  the framework's tests, with deliberately broken copies of them failing the check that names what is broken. Every adapter has a `conformance.json` of
  samples; the skeleton of each axis (`adapters/<axis>/_skeleton/`, vendored) starts red with `TODO` markers; the guide `core/contracts/new-adapter.md` and the
  procedure `new-adapter` (packaged as a skill) say how to write an adapter.
- the Cursor preset (`adapters/runtime/cursor/`; task 1.2), **unverified in a live session**: it is written from Cursor's documentation and passes the conformance suite, but has not run in a real Cursor session (the owner has no Cursor access yet, decision of 2026-11-02). The checklist for such a session is in the preset's README; a fix found there ships as `0.1.1`. Native mode (Cursor is the only runtime): `.cursor/hooks.json` for `sessionStart`, `beforeShellExecution`, `preToolUse` on `Write` and `afterFileEdit`, and the skills in `.cursor/skills/`. Compat mode (next to Claude Code, which Cursor already loads from `.claude/`): no hook file and no skills of its own, so nothing runs twice, and `harness check scaffold` fails on a framework hook in `.cursor/hooks.json`. Both modes keep the `access.denyRead` patterns in a block of `.cursorignore`. Cursor reads `AGENTS.md` itself, so the entry file must be `AGENTS.md`. The recorded-form samples of the Cursor events moved from `tests/fixtures/events/` into the adapter (`events/`), marked as written from the documentation.
- the optional runtime role `managed-blocks` (`managedBlocks(profile) → [{ path, block, content }]`) for blocks of a file of the project that the sync keeps up to date between `# harness:begin <block>` and `# harness:end <block>` lines, as an ignore file needs (an HTML comment would be a pattern). The sync adds the block at the end of the file when the file lacks it and makes the file when it is missing, so the project's own lines stay; `check generated` and the lock hold the block like any other. The packaging of a procedure may now return no path for a profile (`skillPath(procedure, profile)`). A project that wrote an adapter of its own needs no change.
- the Python stack preset (`adapters/stack/python/`; task 1.3), written by following the new-adapter procedure: uv workspaces, pytest with coverage.py (branch coverage; the raw report is merged and turned into the neutral summary by `coverage.mjs`), ruff for lint (E, F, I, B, UP, ANN, T20) and format, mypy in strict mode; the local gate plan (`gate.mjs`), the CI jobs, and a scaffold with a root `pyproject.toml`, `.python-version` and `.nvmrc`. A project selects it with `adapters.stacks`, alone or next to `node-ts`. The project creates `uv.lock` once with `uv lock` and commits it: CI installs with `uv sync --locked`.
- the examples (task 1.4). `examples/profile/` is a filled profile of a fictitious project, `examples/product/` its product specification, and `examples/plan/` a sample plan with one phase and two tasks with their logs; the framework's tests hold each to the check it exercises, and `examples/README.md` explains them. The bootstrap now writes the **product-knowledge skeleton** into a new project's `docs/product/` (an index, a glossary, a register of open questions and a backlog, from `core/templates/scaffold/product-*.md`), sets `productKnowledge` and the document roles `specification` and `glossary` in its profile file, and adds a row for the specification to the reading map of its entry file, so `harness check product-knowledge` runs on every new project. A project that bootstrapped before has no such files and no `productKnowledge`, and nothing changes for it.
- the proof of the design on a scratch project for every combination (task 1.5), repeatable with `tests/proof/proof.sh <directory>`: (A) node-ts with Claude Code, (B) python with Cursor in native mode, (C) node-ts and python together with both runtimes (Cursor in compat mode), (D) a detached project with a core rule edited, and (E) a repository that copied the first harness, adopted with `harness adopt`. On each, `harness check all` passes (run from the project's own copy of the tools), the stack's commands pass (`npm ci`, lint, tests and the documentation check; `uv lock`, `uv sync --locked`, ruff, mypy, pytest with coverage.py and `harness coverage summarize`), and the files of the runtime are as the design says (62 checks in all). A short targeted harness review (`tests/proof/review.mjs` gives the measurements) scores D1 layer integrity 5 (no stack or product term and no link out of CORE in 24,000 words of core), D3 injection 5 (no profile value written outside the profile) and D6 routing 4 (no orphan document; the always-loaded entry file is about 1,650 words, because it carries the rules every task needs). **The Cursor preset is unverified in a live session**: the proof runs its files and hooks against samples written from Cursor's documentation, not Cursor; the checklist in its README stays open, and a fix found there ships as `0.1.1`.

### Changed

- The total line of the plan summary starts at the plan's first phase (`Phase 1` for a plan of one phase), not at Phase 0.
- The protection rule of the entry file no longer names a script: the host enforces it with the ruleset `harness host protect` sets, and
  when `host.protection` is off the rule falls back to the hooks. The profile role `repository.protectionScript` is gone, and so is the
  clause from the Role binding line.
- Two rules of the non-negotiables are worded without a stack: "no new untyped public boundaries" (the stack's lint rule names them) and
  "no debug printing" (use the logger).
- The method's local-database step applies only where the profile has the database commands (`commands.dbUp`, `dbMigrate`, `dbSeed`), an
  optional role group; `documents.method` defaults to the vendored method.
- The host command line of the host adapter's logic roles is the seam `cli` (was `gh`), so one conformance check can pass a stand-in to any host. The
  claude-code event samples moved from `tests/fixtures/events/` into the adapter (`adapters/runtime/claude-code/events/`), where the suite replays them.
  A sync also vendors the three skeletons.
- the stack contract grew where the Python preset needed it, all additive for a stack that exists: `harness coverage summarize` writes the neutral summary from the raw report of one local run (for a tool that does not write it itself); `coverage-merge` gets `{ root, pkg }` as a second argument; an `ignore-files` entry may carry a `pattern` and an `example` for a tool that excludes paths with a setting; the release tool reads and writes the `version` of the `[project]` table of a TOML file; and `.nvmrc` is a file of lines in the node-ts preset, so that a project with two stacks bootstraps. A stack adapter of your own needs no change. The new-adapter guide has a section on what a stack learns the hard way.

### Fixed

- three defects the proof found. (1) A project with two stacks got a CI workflow with the same job ids twice (`static`, and each coverage package): each stack now names its static job after itself, runs its own commands, runs the documentation check only in the first, and keeps the coverage jobs of its own packages (`ciJobs(profile, context)` in the stack contract). (2) The document map of the profile document dropped a row when any role in it had no value, which hid the releases guide, the changelog and the plan method from every new project: each document has a row of its own now, and the starter profile names the changelog. (3) An orphan: the documents the map dropped were not reachable from the entry file; with the map fixed, a new project has none.
- `harness release` could not release from a development version such as `0.1.0-dev.1` (it did not parse it); a development version is now below its own release, so `0.1.0` and `patch` both give `0.1.0`. Found cutting `0.1.0`.
