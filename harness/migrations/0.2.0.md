# Migration to 0.2.0 from 0.1.2

The second minor version. It changes how a version is taken (`sync` places the files, `migrate` brings the project to the version, and one commit undoes it), how the plan is laid out (a folder per phase, a file per task, an issue queue in place of the phase that never ends), and it adds the intake of the reports of users, the areas of the probes, a note for every version, procedures of a project's own and an optional backlog.

This note is the whole story from `0.1.2`. It replaces the notes of the development versions (`0.2.0-dev.1`, `0.2.0-dev.2` and `0.2.0-dev.3`): `harness migrate` leaves them out when this note is among the notes to read. A project that followed the development versions has done their required actions and needs nothing more: the code of `0.2.0` is that of `0.2.0-dev.3` with the final version numbers and the changelog.

## What changed for a project

- **`sync` only places the files; `harness migrate` brings the project to the version** (3.5). `sync` writes the files and the lock, then starts `harness migrate` of the new version in a new process, which regenerates the managed files with the new tools (before, `check generated` could fail after a `sync`). A project whose `sync` is the `0.1.2` one does not start it: run `node harness/tools/harness.mjs migrate` yourself after the `sync`.
- **Migration scripts and the record of them** (3.12). A version may ship `migrations/<version>.mjs`; `migrate` runs the scripts of every version after the project's own up to the target that the lock (`migrations.applied`) does not record, in version order, and prints the migration notes of the versions. This version ships the script of `0.2.0` (below). `migrate` finds the version a project was at even after the `sync` of an older version, which keeps no record of it: it reads the lock of the last commit (issue I-2, report 61).
- **A migration is one commit that `harness rollback` undoes** (3.14). `sync` refuses to start on the production or the integration branch and with uncommitted changes, and records the commit and version it starts from in the lock; `migrate` commits the migration (the sync's changes included) as `chore(framework): migrate to <version>`. `harness rollback` puts back every file that commit changed and removes the files it added, and nothing else.
- **A phase of the plan is a folder** (3.10). `phases/phase-<n>-<slug>/` holds `README.md` (the index: goal, order, exit criteria, a task table that `harness plan summary` generates), a file per task, the task's log beside it, and the phase's own `log.md`. The script splits the open phases of your plan into folders and rewrites the links into them (`harness plan split <n>` does it for a finished one, by choice; the tools read both layouts). The phase template became a phase-index template and a task template.
- **The structure of a phase folder is checked** (4.2). `harness check plan` holds the parts of the phase index and their order, the back-links of the index, the tasks and the logs, a log of its own (or a row of the implementation log) for every done task, and the tasks a task `Needs`. A folder that lacks a part reports it, and the message names the part and the template. A phase of the older layout is checked as before.
- **The defects found in use are an issue queue, not a phase** (3.13). A file per issue (`I-<n>.md`) in `paths.issues`, an index of the open ones, and `archived/` for the finished; branches `bugfix/I-<n>-<slug>`; "Work the issue queue" and "Fix I-<n>" approve their pull requests. The script turns your open-ended phase into a normal phase that keeps every id, makes its defects that have not started into issues (`I-1, formerly 12.5`), and replaces `plan.openEndedPhase` and `plan.openEndedPhaseNumber` of the profile file with `paths.issues`. **A task that a branch claims is kept in its phase** though it is still ⬜ (I-4, report 63), and the script adds the phase folders and the issue queue to the layer of the one-file phases in your `layers`, or prints the line to add by hand (I-3, report 62).
- **Reports from users** (3.16). The switches `reports.intake` (`off`, `notify`, `auto`) and `reports.upstream` (`off`, `ask`, `post`) add the procedures `triage-reports` and `report-upstream`, and a line to the Git rules of the entry file, only where they are on. The script removes the skill files of the procedures whose switch is off, which a sync by an older version wrote for every procedure.
- **Probes name the areas they exercise** (3.15, 4.5). Each probe of the harness-review bindings has an `Areas` column and the words read at the last review; `harness probes <from> <to>` lists the probes to run again for the versions taken, and the framework's starting probe of an area no probe covers. The table is `Probe | Scenario | Areas | Words read at the last review`; a table of another shape gives one problem of `check probes` that names the columns it has and the ones it needs (I-5, report 64). The review method counts the `procedures` block of the entry file apart (rows and words) and a project's bindings set a ceiling for both; the bindings stub has probes P5 and P6 (add a phase; put a defect into the plan) and a `Budgets` section.
- **A profile switch for the probes of a migration** (3.22, report 65). Running the probes costs a session each, thousands of words every one. `probes.run` is `auto`, `ask` (the default) or `disabled`, and the ignored `harness-profile.local.json` overrides it on one machine. The end of the output of `harness migrate` and of `harness probes` says what the mode asks of whoever takes the version, and the procedure `update-framework` follows it. No command starts a probe itself yet, so `auto` and `ask` are instructions: with `ask`, the one who takes the version asks the owner first and runs the probes only on a yes. This changes what a project's agent does when it takes a version: before, it ran every probe; now it asks.
- **New and changed procedures** (4.3, 4.4, 4.4a). `change-plan` (adding a task or phase, recording an issue, splitting a phase) and `update-framework` (taking a version of the framework) are new; `start-task`, `end-session`, `finish-phase` and `triage-reports` are now loaded by the agent on its own (`invocation: auto`, no `disable-model-invocation` in their skills). The next `sync` writes the skills. `update-framework` says to set the task you have in hand to 🟡 before the `sync`.
- **Every version has a migration note, a development version included** (4.8). `migrate` and `harness probes` read the notes of the versions after the project's own up to the target, leaving out the development notes of an `x.y.z` when its final note is among them. `harness release --dev` refuses a version without its note. It changes nothing a project configures.
- **A project can have procedures of its own** (4.1). The profile role `paths.procedures` names a folder of procedure files in the format of `core/procedures/`; they become skills and rows of the `procedures` block after the framework's. A name the framework's procedures have too is an error. The CORE scan does not read the folder.
- **The bootstrap writes a risk register and the index of design records** (4.7). Two scaffold templates, `risk-register.md` and `rfc-index.md`, at two new optional roles of the document map, `documents.riskRegister` and `documents.rfcs`. They are written only when a project is bootstrapped; a project that exists is untouched, and no check reads them.
- **An optional backlog for feature requests** (3.20, 3.21). The profile role `paths.backlog` names a folder (a project without the role has no backlog): an index of the proposed items that `harness plan summary` generates and the plan index counts on a line of its own, a file per item (`B-<n>.md`, from the backlog template), and `archived/` for the promoted ones. The backlog is the place for what the owner has **not approved**: an item is `Proposed` (or `Promoted`), has no phase, no marker, no branch and no claim, and **is never started as it is**. The owner's decision is `harness plan promote <B-n> --phase <n> [--agent <marker>] [--size <n>] --approved`, which writes the next task of the phase from the item, sets the item to `Promoted`, moves it to the archive and updates the size of the phase. An order of development, an execution order or a `Needs` that names a proposed item is a problem of `check plan`. Every item has a `Source:`, which is `report` followed by the link of each report that asks for it, `owner` or `agent`. `harness reports plan` has the relation `feature` for a report that asks for something new, and `harness plan summary` creates the folder, its two indexes and the block of the plan index where a project sets the role later. A project that does not set the role is not affected.
- **`sync` no longer copies the framework's tests into `harness/`** (I-1, report 30). They prove the framework against its own repository, so in a project 20 of 428 failed for what the project does not have, and nothing in a project runs them. `framework.json` lists the file name endings a sync leaves out (`excluded`). The `sync` that takes this version is made by the tools of the version you leave, which still copy them; the next `sync` removes them, and `check vendored` accepts a copy that still holds them.

## Required actions

1. **Take the migration.** Set the task you have in hand (claimed by a draft pull request) to 🟡 in its task file, so that the migration of the plan keeps it in its phase. Run `sync` on a branch of its own (it refuses on a protected branch and with uncommitted changes), and `node harness/tools/harness.mjs migrate` where the `sync` of `0.1.2` did not start it. The script of `0.2.0` splits the open phases, converts the open-ended phase into a normal phase and an issue queue, adds the plan folders to your layer map where it has one, and removes the skills of the procedures whose switch is off.
   Check: `node harness/tools/harness.mjs check generated` exits 0, and `migrations.version` in `harness.lock.json` is `0.2.0` with `migrations.applied` listing `0.2.0`.
2. **Make your phase folders pass `check plan`.** The new structure checks apply to every phase kept as a folder, the ones the script wrote and those you wrote yourself; each message names the missing part (a part of the phase index, a back-link, a log, a work-log link) and the template to start from (`harness/core/plan/phase-index-template.md`, `task-template.md`, `task-log-template.md`).
   Check: `node harness/tools/harness.mjs check plan` exits 0.
3. **Make the table of your probes `Probe | Scenario | Areas | Words read at the last review`**, when your harness-review bindings have a probe table of another shape (for example `Id | Scenario | Expected`): the third cell of a probe names its areas of the migration notes (the list is in `harness/migrations/areas.json`), separated by commas; move what the other columns held (the expected behaviour) to a list below the table. Copy the table of `harness/core/templates/scaffold/harness-bindings.md` as the starting shape.
   Check: `node harness/tools/harness.mjs check probes` exits 0.
4. **Have every file of the plan in a layer.** When the script printed a line telling you to add a glob to your layers by hand, or your layers claim the phase folders and the queue in another way than a glob of the one-file phases, add `<phases>/phase-*/**` and `<issues>/**` to the layer of your plan state.
   Check: `node harness/tools/harness.mjs check layers` and `check paths` exit 0.
5. **Bring your own plan documents to the new layout.** A document of the project that describes the open-ended phase, the one-file phase layout, or how a defect found in use is recorded (its plan bindings, its method notes, the project-specific section of the entry file) now restates a changed rule: replace it with the issue queue and the phase folder, or with a link to the core document. An id the script gave an issue keeps its old id (`I-1, formerly 12.5`), so links by the old id still resolve.
   Check: `grep -rn "openEndedPhase" harness-profile.json docs` prints nothing, and `node harness/tools/harness.mjs check all` exits 0.

## Optional actions

- **Choose how the probes of a migration run.** Set `probes` to `{ "run": "auto" }`, `{ "run": "ask" }` (the default, when the key is absent) or `{ "run": "disabled" }` in the profile file, or only on this machine in `harness-profile.local.json`. Taking a version costs a session per probe that its areas touch, so a project that does not want that sets `disabled`.
  Check: `node harness/tools/harness.mjs probes 0.1.2 0.2.0` ends with the line for the mode you chose.
- Turn on the reports of users: set `reports.intake` (`notify` or `auto`) and `reports.upstream` (`ask` or `post`) in the profile file, then `sync --local`. They are off by default; a local `harness-profile.local.json` overrides them for one machine.
- Add procedures of your own: set `paths.procedures` to a folder (this repository uses `docs/procedures`), write them in the format of `core/procedures/`, classify the folder in your layer map, and run `sync --local`.
- Add probes P5 and P6 and a `Budgets` section to your harness-review bindings (copy them from `harness/core/templates/scaffold/harness-bindings.md`), with the ceilings for the `procedures` block that suit your entry file.
- Give a project that exists a risk register and design records: set `documents.riskRegister` and `documents.rfcs` in the profile file (the starter values are in `harness/profile/starter.json`), copy `risk-register.md` and `rfc-index.md` from `harness/core/templates/scaffold/` to those paths, and run `sync --local`.
- **Start a backlog.** Add `"backlog": "docs/development-plan/backlog"` (or another folder) to `paths` in the profile file, run `node harness/tools/harness.mjs plan summary` (it creates the folder and the block of the plan index), then `node harness/tools/harness.mjs sync --local` (the procedures `change-plan` and `triage-reports` now carry the backlog's text). A project with its own `layers` puts the folder in the layer of the issue queue. Move a feature request that is in your issue queue there by hand: a new item with `Status: Proposed`, `Source:` and `Formerly: I-<n>`, and remove the issue's file (the number stays taken). When the owner decides to do an item, `harness plan promote <B-n> --phase <n> --approved` makes it a task.
  Check: `node harness/tools/harness.mjs check plan`, `check layers` and `check links` exit 0.
- Split a finished one-file phase into a folder with `harness plan split <n>`.
- Run `node harness/tools/harness.mjs sync` once more on a branch of its own to drop the copied tests from `harness/` (`find harness -name '*.test.mjs'` then prints nothing).
- Run `node harness/tools/harness.mjs probes 0.1.2 0.2.0` and the probes it lists as separate sessions, as `probes.run` says; compare what each reads with the last review, and report a probe that reads more (the procedure `update-framework` has the steps).

## How to verify

`node harness/tools/harness.mjs check all` exits 0, your gate (lint and tests) passes, and `version` in `harness.lock.json` is `0.2.0`. `node harness/tools/harness.mjs rollback` undoes the migration commit if a step cannot be done now.
