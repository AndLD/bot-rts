# Migration to 0.2.0-dev.1 from 0.1.2

The first development version of `0.2.0`. It is for trying the version before its final tag: the note of the final version, `0.2.0.md`, is written with that version and tells the whole story from `0.1.2`, so a project that takes `0.2.0` after this one reads that note, and this one stays as it is.

## What changed for a project

- **`sync` only places the files; `harness migrate` brings the project to the version** (3.5). `sync` writes the files and the lock, then starts `harness migrate` of the new version in a new process, which regenerates the managed files with the new tools (before, `check generated` could fail after a `sync`). A project whose `sync` is the `0.1.2` one does not start it: run `node harness/tools/harness.mjs migrate` yourself after the `sync`.
- **Migration scripts and the record of them** (3.12). A version may ship `migrations/<version>.mjs`; `migrate` runs the scripts of every version after the project's own up to the target that the lock (`migrations.applied`) does not record, in version order, and prints the migration notes of the versions. This version ships the script of `0.2.0` (below); a development version runs it and does not record it as applied.
- **A migration is one commit that `harness rollback` undoes** (3.14). `sync` refuses to start on the production or the integration branch and with uncommitted changes, and records the commit and version it starts from in the lock; `migrate` commits the migration (the sync's changes included) as `chore(framework): migrate to <version>`. `harness rollback` puts back every file that commit changed and removes the files it added, and nothing else.
- **A phase of the plan is a folder** (3.10). `phases/phase-<n>-<slug>/` holds `README.md` (the index: goal, order, exit criteria, a task table that `harness plan summary` generates), a file per task, the task's log beside it, and the phase's own `log.md`. The script splits the open phases of your plan into folders and rewrites the links into them (`harness plan split <n>` does it for a finished one, by choice; the tools read both layouts). The phase template became a phase-index template and a task template.
- **The structure of a phase folder is checked** (4.2). `harness check plan` holds the parts of the phase index and their order, the back-links of the index, the tasks and the logs, a log of its own (or a row of the implementation log) for every done task, and the tasks a task `Needs`. A folder that lacks a part reports it, and the message names the part and the template. A phase of the older layout is checked as before.
- **The defects found in use are an issue queue, not a phase** (3.13). A file per issue (`I-<n>.md`) in `paths.issues`, an index of the open ones, and `archived/` for the finished; branches `bugfix/I-<n>-<slug>`; "Work the issue queue" and "Fix I-<n>" approve their pull requests. The script turns your open-ended phase into a normal phase that keeps every id, makes its defects that have not started into issues (`I-1, formerly 12.5`), and replaces `plan.openEndedPhase` and `plan.openEndedPhaseNumber` of the profile file with `paths.issues`.
- **Reports from users** (3.16). The switches `reports.intake` (`off`, `notify`, `auto`) and `reports.upstream` (`off`, `ask`, `post`) add the procedures `triage-reports` and `report-upstream`, and a line to the Git rules of the entry file, only where they are on. The script removes the skill files of the procedures whose switch is off, which a sync by an older version wrote for every procedure.
- **Probes name the areas they exercise** (3.15, 4.5). Each probe of the harness-review bindings has an `Areas` column and the words read at the last review; `harness probes <from> <to>` lists the probes to run again for the versions taken, and the framework's starting probe of an area no probe covers. The review method counts the `procedures` block of the entry file apart (rows and words) and a project's bindings set a ceiling for both; the bindings stub has probes P5 and P6 (add a phase; put a defect into the plan) and a `Budgets` section.
- **New and changed procedures** (4.3, 4.4, 4.4a). `change-plan` (adding a task or phase, recording an issue, splitting a phase) and `update-framework` (taking a version of the framework) are new; `start-task`, `end-session`, `finish-phase` and `triage-reports` are now loaded by the agent on its own (`invocation: auto`, no `disable-model-invocation` in their skills). The next `sync` writes the skills.
- **Every version has a migration note, a development version included** (4.8). This is the first development note. `migrate` and `harness probes` read the notes of the versions after the project's own up to the target, leaving out the development notes of an `x.y.z` when its final note is among them, so a project that follows the development versions reads each note once and the final note stands for them. `harness release --dev` refuses a version without its note. It changes nothing a project configures.
- **A project can have procedures of its own** (4.1). The profile role `paths.procedures` names a folder of procedure files in the format of `core/procedures/`; they become skills and rows of the `procedures` block after the framework's. A name the framework's procedures have too is an error. The CORE scan does not read the folder.

## Required actions

1. **Take the migration.** Run `sync` on a branch of its own (it refuses on a protected branch and with uncommitted changes), and `node harness/tools/harness.mjs migrate` where the `sync` of `0.1.2` did not start it. The script of `0.2.0` splits the open phases, converts the open-ended phase and removes the skills of the procedures whose switch is off.
   Check: `node harness/tools/harness.mjs check generated` exits 0, and `migrations.version` in `harness.lock.json` is `0.2.0-dev.1` with `migrations.applied` not listing `0.2.0` (a development version does not record it).
2. **Make your phase folders pass `check plan`.** The new structure checks apply to every phase kept as a folder, the ones the script wrote and those you wrote yourself; each message names the missing part (a part of the phase index, a back-link, a log, a work-log link) and the template to start from (`harness/core/plan/phase-index-template.md`, `task-template.md`, `task-log-template.md`).
   Check: `node harness/tools/harness.mjs check plan` exits 0.
3. **Bring your own plan documents to the new layout.** A document of the project that describes the open-ended phase, the one-file phase layout, or how a defect found in use is recorded (its plan bindings, its method notes, the project-specific section of the entry file) now restates a changed rule: replace it with the issue queue and the phase folder, or with a link to the core document. An id the script gave an issue keeps its old id (`I-1, formerly 12.5`), so links by the old id still resolve.
   Check: `grep -rn "openEndedPhase" harness-profile.json docs` prints nothing, and `node harness/tools/harness.mjs check all` exits 0.

## Optional actions

- Turn on the reports of users: set `reports.intake` (`notify` or `auto`) and `reports.upstream` (`ask` or `post`) in the profile file, then `sync --local`. They are off by default; a local `harness-profile.local.json` overrides them for one machine.
- Add procedures of your own: set `paths.procedures` to a folder (this repository uses `docs/procedures`), write them in the format of `core/procedures/`, classify the folder in your layer map, and run `sync --local`.
- Add probes P5 and P6 and a `Budgets` section to your harness-review bindings (copy them from `harness/core/templates/scaffold/harness-bindings.md`), with the ceilings for the `procedures` block that suit your entry file.
- Split a finished one-file phase into a folder with `harness plan split <n>`.
- Run `node harness/tools/harness.mjs probes 0.1.2 0.2.0-dev.1` and the probes it lists as separate sessions started in your repository; compare what each reads with the last review, and report a probe that reads more (the procedure `update-framework` has the steps).

## How to verify

`node harness/tools/harness.mjs check all` exits 0, your gate (lint and tests) passes, and `version` in `harness.lock.json` is `0.2.0-dev.1`. `node harness/tools/harness.mjs rollback` undoes the migration commit if a step cannot be done now.
