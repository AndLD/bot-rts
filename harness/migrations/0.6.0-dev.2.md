# Migration to 0.6.0-dev.2 from 0.6.0-dev.1

This note is written against `0.6.0-dev.1`. A project that has not taken `0.6.0-dev.1` takes `0.6.0` when it ships and reads the note of that version, which tells the whole story from `0.5.0`.

## What changed for a project

- **`harness check layers` places the `SECURITY.md` of the scaffold** in the PROFILE layer when the project's layer map does not place it (I-46). A project with a layer map no longer edits its map for the file that `0.6.0-dev.1` asked it to add; the take of `0.6.0-dev.1` found that `check all` failed there with "belongs to no layer". A placement the project's own map gives still wins.
- **`harness check security` no longer reports S2-001 on a workspace manifest** that a lock file at the root of its workspaces covers (I-47). The stack's `dependency-audit` role may give each manifest a `members` function; the node-ts adapter reads the npm `workspaces` field. A manifest that no lock covers is still reported. A project on npm workspaces that saw one S2-001 finding for each workspace sees none now.
- **The count of scriptable probes is corrected** in the notes and the changelog: `harness check security` automates 14 of the 29 scriptable probes of the catalogue (the changelog entry of task 2.2 said 28).
- **What the take of `0.6.0-dev.1` found the note missing**, now said in the required actions below: the scan of the vendored core with the project's own product terms (action 2), and the actions a project pins by hand (action 3).
- Nothing else of `0.6.0-dev.1` changed: the security review, `check security`, the three security rules, the pinned actions, the narrower workflow tokens, the `SECURITY.md` and `harness init` are as the note of `0.6.0-dev.1` describes them.

## Required actions

1. **Take the version.** Run `sync` on a branch of its own, then `node harness/tools/harness.mjs migrate` if the `sync` did not start it. No script runs; every change has a safe default.
   Check: `node harness/tools/harness.mjs check all` exits 0, and `migrations.version` in `harness.lock.json` is `0.6.0-dev.2` (a check of this take only: after the next development version or the final one, the same jump leaves another value).
2. **List the ordinary words of the new probes in `terms.productGeneric`.** `check core` scans the vendored core, the probes and scenarios of the security review among it, with the project's own `terms`. A project whose product terms are ordinary words that the probes use (the consumer's `bot`, `bots`, `scanner` and `base` hit 14 lines) fails that check, and a vendored file is not edited. Add each such word to `terms.productGeneric` of the profile file; a word that is really your product's name is reported upstream and recorded in `terms.exceptions` for this version.
   Check: `node harness/tools/harness.mjs check core` exits 0. A project whose terms hit nothing has nothing to do.
3. **Pin by hand what the sync does not generate.** The sync brings the pinned `ci.yml`, `release.yml` and `update-branches.yml` of the preset. In every workflow you wrote yourself, pin each `uses:` line to the full 40-hex commit of its tag, with the tag in a comment (`owner/repo@<40 hex> # v1.2.3`). The preset pins only `actions/checkout` v4.4.0, `actions/setup-node` v4.4.0, `actions/upload-artifact` v4.6.2, `actions/download-artifact` v4.3.0 and `astral-sh/setup-uv` v6.8.0; copy those lines from the preset, and for any other action look the commit up yourself: `git ls-remote https://github.com/<owner>/<repo> 'refs/tags/<tag>^{}' 'refs/tags/<tag>'` (take the `^{}` line when there is one, since an annotated tag points at a tag object and the commit is behind it). Move any write grant from the top of the file to the job that needs it.
   Check: `node harness/tools/harness.mjs check security` reports no S2-004 and no S3-001 (it runs even while `checks.security` is off). A project that did this for `0.6.0-dev.1` has nothing more to do.

## Optional actions

- If you added `SECURITY.md` to your layer map for `0.6.0-dev.1`, keep the entry (your map wins) or remove it; `check layers` passes either way.
- Before turning `checks.security` on, run `harness check security` and list the files with test values that look like credentials (the consumer saw 32 S1-001 findings on test URLs) in `security.exclude`, or change the values.
- The optional actions of `0.6.0-dev.1` stay as its note gives them: the security review, `checks.security`, `--audit`, Dependabot for `github-actions`, `flows.permissions`.

## How to verify

`node harness/tools/harness.mjs check all` exits 0, and `version` in `harness.lock.json` is `0.6.0-dev.2`.
