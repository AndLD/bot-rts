# Phase 13 — Observability platform (48 SP)

**Status:** 🟡 In progress · **Branches:** see the [implementation log](#implementation-log) · **Work log:** [phase-13-log](./work-logs/phase-13-log.md)

**Approved by the owner 2026-10-15** (proposed by the owner, drafted, reviewed and extended with tracing and a shared collector gateway). The estimates are the plan's; a task is re-estimated when it starts if the code shows a different size.

Moves the logs of the game to **OpenTelemetry**, adds **tracing** so that everything that can be connected is connected by a trace id (the owner's wish: every log record carries one, and a request can be followed over the browser's call, the API, the engine and the notifications it causes), and stores both in **Elasticsearch**, so that the admin console can search the logs of
**every node** (every API node and the engine node), not only of the process that answers (the log search of 9.10 reads a
per-process in-memory buffer). The metrics of 8.3 (Prometheus) stay as they are unless task 13.6 decides otherwise. The phase is an
upgrade of operations, not of the game: the game works without it, but it is part of the plan and of the MVP count like every other phase.

**Depends on:** Phase 8 (the observability basics, 8.3), 9.10 (the admin logs and audit viewer), 9.17 (the engine's own setting channel, whose request pattern the trace propagation follows) is useful but not required, and 9.19 (retention from the console,
which the log retention joins). **Order:** after Phase 9 and **before Phase 10** (owner decision 2026-10-16: the tracing and the logs of every node help to build and debug the market, the escrow and the ledger, and the logger is replaced before Phase 10 adds its code); it can be moved by the owner.

**Execution order:** 13.1 → 13.2 → 13.3 → 13.4 → 13.5 → 13.8 → 13.6 → 13.7. 13.8 (13 SP, the largest task of the phase; split it when it starts if its parts are better reviewed apart: (a), then (b) to (d), then (e) to (g)) does not depend on OpenTelemetry and can run at any time after Phase 9, in parallel with 13.1 to 13.5; 13.6 needs 13.4 and 13.8; 13.7 stays last.

| 13.1 | **Logs and traces on OpenTelemetry (the core).** The `Logger` port keeps its shape; behind it the OpenTelemetry Logs SDK replaces log4js in the API, the engine thread (its own application context) and the MCP server, and the Tracing SDK is added next to it so that **every log record carries a trace id and a span id**. Spans: every HTTP request (the W3C `traceparent` header is read from the caller or the load balancer, a new trace starts otherwise, and the trace id is returned in the response headers and replaces the request id of 8.3, which stays as an alias), every Socket.IO event, every tick of the engine (with child spans for the world actions and the manual calls it applies), every scheduled job (the lifecycle pass, the monitoring sample, the write-behind flush), and the start and the end of a script execution (a long script is a span **link**, not a parent). The trace context is **propagated across our own boundaries**: in the messages between the API and the engine thread, over the Redis link of a scaled deployment, from the engine's events to the notifications they cause, and from the MCP server to the API. A record written outside any span in a request, tick or job path is a defect: a test fails on it. Sampling is parent-based with a ratio from the environment; a sampled-out span still has its ids, so the logs keep them. Records go to the console and the files as now (`LOG_FORMAT`, `LOG_FILE`, for development) and to OTLP when `OTEL_EXPORTER_OTLP_ENDPOINT` is set; the `LogBuffer` of 9.10 stays as the fallback. Includes unit tests of the mapping, of the propagation on every link (worker, Redis, disabled) and of the "no record without a span" rule | 8 | ✅ |
| 13.2 | **Shared collector gateway and Elasticsearch in Docker** (decided with the owner 2026-10-15: **one shared gateway collector for all nodes**, not an agent next to each node). `docker-compose.yml` gets an OpenTelemetry Collector (gateway mode) and a single-node Elasticsearch with pinned versions and health checks. Every process that logs (each API node, the engine node, the MCP server) sends OTLP to the gateway at `OTEL_EXPORTER_OTLP_ENDPOINT`, authenticated with a bearer token (`OTEL_EXPORTER_OTLP_HEADERS`; TLS in production); the gateway receives logs and traces, limits memory, batches, redacts again (13.5), and writes both to Elasticsearch. Because the gateway is one place that every node depends on: the SDK exporters keep a bounded queue and retry with a back-off, and drop the oldest records first when it is full (the log files of 13.1 keep every line, so nothing is lost for good); the gateway has a persistent queue on disk so that a restart or an Elasticsearch outage does not lose what it holds; it can run as two replicas behind a load balancer (the traces of one request must reach the same replica if tail sampling is ever used, which this phase does not do: sampling stays parent-based in the SDKs, 13.1); and its own health and queue size are metrics shown on the dashboard of 9.3. Index templates and mappings (the trace id and the span id are keyword fields); an index lifecycle policy whose retention comes from the environment (and later from the console, 13.5); the same containers in CI. `docs/operations/DEPLOYMENT.md` explains sizing, scaling, the token and the network (only the nodes may reach the gateway; Elasticsearch is reachable only from the gateway and from the API's read-only account), and what happens when the gateway or Elasticsearch is down | 5 | ✅ |
| 13.3 | **`LogStore` port and the Elasticsearch adapter.** A port with `search({ text, level, requestId, traceId, userId, botId, node, from, to }, page)`, an Elasticsearch adapter with a read-only account, time limits, a bound on the window and the page, and a clear error when the store is down; the Logs page of the console searches through it, with a node filter, "all nodes" and a trace id filter, and the answer keeps the shape of 9.10; `LOG_STORE=memory` keeps the old buffer for development. The slow ticks stay with the engine's metrics. Includes integration tests against a real Elasticsearch container, the update of the `authorization-matrix` and of the Cypress spec of the Logs page | 8 | ✅ |
| 13.4 | **Traces in the console.** A line of the log shows its trace id with an **Open trace** action, which shows the trace: its spans as a timeline (name, node, start, duration, status) and **every log of the trace from every node** in order, so one request can be followed from the browser's call through the API, the engine's tick and the notification it caused. Search by trace id (and by the request id of the old logs). A `TraceStore` port with the Elasticsearch adapter next to the `LogStore`; the permission is `logs.read` and the read of a trace is audited. Includes tests (an integration test that follows a request over the API and the engine in the store) and a Cypress spec | 5 | ✅ |
| 13.5 | **Privacy, access and retention.** Redaction of emails, tokens, passwords and API keys in the SDK and again in the collector, for the attributes of the spans as well as for the logs, with a test over a corpus of lines; every log search and trace read is written to the audit trail (who, what was asked); the retention of the log and trace indices becomes one more setting of 9.19 (the index lifecycle policy is updated through the admin API, with a floor and a reset to the default) | 3 | ✅ |

The work is the **trace links in the dashboard of 9.3**: a point of the tick-duration and request-latency charts offers **Open trace** (13.4) for the slowest sample of its bucket, read from the history stored by 13.8. Needs 13.4 and 13.8 | 3 | ⬜ |
| 13.7 | **Cutover, cleanup and runbook.** Production images stop writing log files by default, log4js and its file transports are removed, the deployment gate and the README table of environment variables (`OTEL_*`, `LOG_STORE`, `ELASTICSEARCH_URL`) are updated, the pages of the admin documentation about the logs and the traces are updated in English and Russian, and a runbook covers the size of the indices, a store that is down, and how to follow one request | 3 | ⬜ |
| 13.8 | **Persist the metrics history, ready for several nodes, and collect the metrics of design §25.5 that are still missing** (decided 2026-10-16; all of §25.5 except the Market row, which comes with Phase 10). **(a) History:** a history port with the in-memory fine tier (10-second steps, the live view of a node) and a PostgreSQL coarse tier (1-minute steps) written by **every node, the engine node included**, with a `node` column; Prisma model and migration, a batched upsert per minute, retention from the console setting of 9.19 and a cleanup job. Latencies and tick durations are stored as histogram bucket counts, so a percentile over several nodes comes from the buckets and never from averaging per-node percentiles; per bucket, the trace id of the slowest tick and request. The console reads all nodes with a node filter; the charts and the alerts of 9.3 keep working, and the in-memory implementation stays the default for tests and single-node development. **(b) Engine and world:** tick p50 and p99, world-flush duration and lag, ticks skipped, commands per tick, online players, active bots and bots per player, live scan areas and watchers, live-view diffs and events per second, map-chunk cache hit rate, conflict rate (`BLOCKED`, `EMPTY`). **(c) Scripts:** ops used against budget, scripts killed by the wall-clock slice, QuickJS contexts, scheduler fairness (the spread of wait times between players). **(d) API and sockets:** Socket.IO connections and reconnects, rate-limit hits, request latency p50 and p99. **(e) Database:** query latency (a Prisma extension that times queries, with the slow-query threshold from the balance config), slow queries counted and the last few kept without parameters, connection-pool use, table sizes and growth (a read-only size query every few minutes), flush transaction time. **(f) Jobs and notifications:** for the retention and cleanup jobs the last run, duration and failures, notification queue depth and delivery lag, email send failures. **(g) Infrastructure per node:** CPU (process and load average), memory, disk usage of the data and log volumes and of the database, and the age of the newest backup (read from a marker that the backup procedure of the runbook writes; shown as unknown when there is none). Each metric gets a default alert threshold where §25.5 gives one, tunable in the console. Tests: unit (the port, the percentile merge from buckets, each collector), integration against PostgreSQL (two nodes write and the console reads both; retention; the size and slow-query collectors), and the admin documentation page in English and Russian | 13 | 🟡 (a) to (d) done |

## Exit criteria

An admin can search the logs of every node from the console, by text, level, trace id, request id, user, bot, node and time, with the records
stored in Elasticsearch and sent through OpenTelemetry; every record of a request, a tick or a job carries a trace id, and a trace can be opened with its spans and the logs of all nodes; personal data is redacted; searching is audited; the retention of the logs is
set from the console; the game and the console still work with `LOG_STORE=memory`; the coverage gate (≥ 97 %) stays green.
