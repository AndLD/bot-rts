# Migration to 0.4.0-dev.1 from 0.3.0

The first development version of `0.4.0`. It adds three optional pieces to a project's tools (the off-plan record, `harness plan-write`, `harness review measure`) and one check (`markers`), changes how a flow starts its workers, and fixes a few things found in use. **No migration script runs** and nothing is required of a project beyond taking the version; the choices below are the project's.

## What changed for a project

- **Flows: executors and permissions** (a change of the meaning of the procedure `run-flow` and a minor addition to the agent-runtime contract, still version 2: an adapter without the additions still conforms).
  - The executor `cli` (a worker on the runtime's command line) joins `session` and `manual`, in an order: `session` is the default, `cli` its fallback for one step, `manual` the fallback of that; `subagent` stands outside the order. `harness flow dispatch` prints the next executor beside every start, and `harness flow check` refuses a "step started" line on another executor than the step's own without the fallback and its reason. A log line written before reads as before. The Claude Code preset splits its `session` executor into `session` (the desktop app) and `cli`; a project's own runtime adapter that offered the command line as a means of `session` may move it to a `cli` executor (optional).
  - A session a flow starts gets the flow's `permissions` mode through the app's `permission_mode`; the app's start takes no tools, so `harness flow dispatch` names the tools of `allow` for the project's settings, which the owner adds. A project whose flows set `permissions` and start sessions adds those tools to `.claude/settings.json` (or the local file), or its unattended sessions are refused the tools the mode does not allow. The "step started" line gains `· **Permissions:** <mode>` when the flow sets a mode.
  - The flow's `levels` gain the kind `contract.change` (D3 by default): a flow decides a change of the meaning of a contract below its `askAt` and asks from it up (with the default `askAt` D2 it still asks the owner); in seamless mode it decides and lists it in the digest. A flow that must keep asking for every contract change in seamless mode cannot: run it in brainstorm mode with `askAt` at D3 or below. A change of the meaning of a core rule or a non-negotiable stays the owner's.
  - A new flow setting `commands`: `any` (default, as before) or `plain` (workers write files with the edit tools, no heredocs or subshells, so a strict permission mode asks less). `harness flow check` refuses another value.
  - The usage table of the preset is calibrated for Sonnet on Pro (`consumer-take`, `cut`, and a row for `tasks`); `flow estimate` and `gate` give smaller estimates. Nothing to do.
  - `harness flow status` reads a consuming repository's pull request as the take of a version only when its title names the version as a whole token (I-14).
- **The off-plan record** (optional). A project with the new profile role `paths.offPlan` keeps one fragment per pull request for work that no task covers; `harness plan log --off-plan` prints them and `harness check off-plan` (part of `check all`) fails on an unreadable record and on merged pull requests with neither a `Plan: <task id>` line nor a record, counted from the commit that added the folder's `README.md`. A project without the role is unchanged. A new bootstrap now creates the folder and its `README.md` (I-22); an adopted project keeps its profile file as it is.
- **`harness plan-write on|off|state`** (optional). A new optional logic role `plan-write` of the runtime contract: the Claude Code preset writes `Edit(<folder>/**)` rules into `permissions.allow` of the tracked `.claude/settings.json`, so an agent writes the plan's files without a prompt. A new bootstrap turns it on (`--no-plan-write` leaves it off); a project that took an earlier version runs `harness plan-write on` once if it wants it.
- **`harness review measure`** (optional) prints the measurements of a harness review that a script can decide, against the ceilings of the project's harness review bindings, and exits 1 over a ceiling. The bindings stub has the new rows (all `—` until a review proposes ceilings); a project reads the rows it wants into its own bindings.
- **`harness check markers`** is part of `harness check all`: it fails on a line that starts with 7 or more `<` or `>` and a space or the end of the line, in a tracked Markdown or JSON file (a committed conflict marker). `harness branch update` leaves the merge in progress, naming the file, instead of committing a file that holds such a line. A file that holds one on purpose writes it inside a line or an indented block.
- **CI template**: the `pr-title` job also runs on `workflow_dispatch` (it reads the open pull request's title and asks the `pull-requests: read` permission), so a pull request the update workflow brings up to date no longer stays blocked on a skipped required check. A project that took the template runs `harness sync` to get it.
- **Git hooks**: `pre-push` and `pre-commit` use the worktree's own `harness.mjs` in a linked worktree instead of the main checkout's (I-19). Nothing to do.
- **Documents**: the procedure `release` and the releasing guide say to push the tag of a release or hotfix from a local branch at the merge commit, before the merge back (I-17); the notes of a migration say what they left out and `migrations/README.md` has the rules for notes (I-16). Nothing to do.

## Required actions

1. **Take the version.** Run `sync` on a branch of its own, then `node harness/tools/harness.mjs migrate` if the `sync` did not start it. No script runs; nothing else is required.
   Check: `node harness/tools/harness.mjs check all` exits 0, and `migrations.version` in `harness.lock.json` is `0.4.0-dev.1` (a check of this take only: after the next development version or the final one, the same jump leaves another value).
2. **If the project has a file that holds a line of 7 or more `<` or `>` characters followed by a space or the end of the line** (a document about merge conflicts, for one), write it inside a line or an indented block, or `check markers` fails.
   Check: `node harness/tools/harness.mjs check markers` exits 0. A project with no such file has nothing to do.

The note of the final version, `0.4.0.md`, will tell the whole story from `0.3.0`; it is written with that version, and a project that takes `0.4.0` after this one reads it then (`harness migrate` prints it too, marked as not yet taken, when the tree holds it).

## Optional actions

- Turn on the off-plan record: add `paths.offPlan` to the profile file, a folder with a `README.md` in the format of this repository's `docs/development-plan/off-plan/README.md`, and run `harness sync`.
- Run `harness plan-write on` to let agents write the plan's files without a prompt.
- Add the tools of the flows' `allow` lists to the project settings if its flows start sessions with `permissions`; set `"commands": "plain"` for flows whose workers run in a strict mode.
- Run `harness review measure` and read its rows into the project's harness review bindings.

## How to verify

```bash
node harness/tools/harness.mjs check all
node harness/tools/harness.mjs probes 0.3.0 0.4.0-dev.1
```

The first exits 0 on a healthy project, and `version` in `harness.lock.json` is `0.4.0-dev.1`; the second lists the probes whose areas this version touched.
