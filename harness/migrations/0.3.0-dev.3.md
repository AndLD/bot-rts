# Migration to 0.3.0-dev.3 from 0.3.0-dev.2

The third development version of `0.3.0`. It fixes what the take of `0.3.0-dev.2` found in the migration of `0.3.0` (I-15) and adds nothing else. The note of the final version, `0.3.0.md`, tells the whole story from `0.2.0` and is finished with that version, so a project that takes `0.3.0` after this one reads that note, and this one stays as it is. A project that takes this version straight from `0.2.0` reads `0.3.0.md` for what the version is, and this note only for what differs from `0.3.0-dev.2`.

## What changed for a project

- **The releases table the migration writes takes its ids from the listing part of a cell only** (I-15). In a cell of the old table, the ids that go into "Tasks, in order" are read from where the cell lists tasks: its start, made of ids, separators, "then", "and" and notes in brackets. Three things follow:
  - a cell that opens with words (not with a list of tasks) gives no id, so the release has an empty "Tasks, in order" and **you add its ids by hand**; the whole cell is kept in "Notes";
  - a phase or a task that the words later in the cell only mention ("Phase 17 is closed") is no longer taken, so it is not written under a release that does not hold it;
  - the sentence that stood before the old table and ended in its colon is closed with a full stop, so it is not left broken in "Notes".
  The migration of the earlier versions (`0.2.0` and before) is unchanged. **This is a change of the script, and `0.3.0-dev.1` and `0.3.0-dev.2` already wrote your table**: the script does not write a table that exists, so what they wrote stays (see required action 2).

## Required actions

1. **Take the version.** Run `sync` on a branch of its own, then `node harness/tools/harness.mjs migrate` if the `sync` did not start it. A project that comes from `0.2.0` gets its releases table from the fixed script; a project that comes from an earlier development version keeps the table it has.
   Check: `node harness/tools/harness.mjs check all` exits 0, and `migrations.version` in `harness.lock.json` is `0.3.0-dev.3`.
2. **If you took `0.3.0-dev.1` or `0.3.0-dev.2`, review the releases file they wrote, by hand** (the way the note of `0.3.0-dev.2` says: only task ids stay in "Tasks, in order", the words go to "Notes", a skipped release has the status ⏭). In addition, for each row look at the ids: an id that the words of the cell only mention, and that the release does not hold, is removed from "Tasks, in order"; a row whose cell opened with words and got ids from them is given the ids it holds, by hand. A project that already repaired the table by hand, or whose cells hold only ids, has nothing to change. To see what the fixed script writes, run it on a scratch branch taken from the state before the take (a fresh take from `0.2.0`); do not replace a table you have repaired with it.
   Check: `node harness/tools/harness.mjs check plan` exits 0, and `node harness/tools/harness.mjs plan summary` names the release you expect as the next one.

## Optional actions

None.

## How to verify

```bash
node harness/tools/harness.mjs check all
node harness/tools/harness.mjs probes 0.3.0-dev.2 0.3.0-dev.3
```

The first exits 0 on a healthy project, and `version` in `harness.lock.json` is `0.3.0-dev.3`; the second lists the probes whose areas this version touched (the first gate after the take runs every suite of the project, as `0.3.0.md` says, because a take changes `harness/**`).
