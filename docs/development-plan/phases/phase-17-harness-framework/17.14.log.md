### 2026-11-02 — the suite, `harness adapter test`, the guide and the skeletons
- **Branch:** `chore/17.14-conformance` — done. The claim was opened before the work.
- **Decisions / deviations from the plan:**
  - **Where the suite lives.** `tools/conformance/` (`suite.mjs`, `common.mjs`, `stack.mjs`, `runtime.mjs`, `host.mjs`, `fixture.mjs`), not `tests/conformance/`:
    `tests/` is not distributable (the skeleton test says so), and `harness adapter test` has to run in a project's vendored copy. `tests/conformance/` holds the
    framework's tests of the suite. A check passes by returning, fails by throwing, and is skipped by throwing `Skip` (an optional role left empty). Design §5
    and §10 say so.
  - **What a check runs.** The adapter's logic, through the framework's own gate driver (`planPush`), coverage gate (`changedFileFailures`) and hooks
    (`guard-shell`, `guard-edit`, `session-start`, `format-edited` fed the recorded samples). Each run builds a copy of the framework that holds the adapter and
    bootstraps a project from it with `harness init`, so an adapter the running framework does not ship is judged by the tools that would load it; the other
    axes are filled by the presets. The bootstrapped project passing `harness check all` is the "fixture project" of the design.
  - **What it does not run.** A stack's tools (formatter, test runner), the host, the runtime. So "never downloads a formatter" is a rule on the command the
    adapter returns (`npx` without `--no-install`, `dlx`, `uvx`, `pipx`, `bunx` fail), and "a failing test fails the push" is the plan holding a test step plus
    the coverage step. The guide says this in its last paragraph before the `conformance.json` table. A formatter run with no network and an empty cache is
    left to the framework's proof (task 1.5 of its plan).
  - **Samples.** Each adapter has a `conformance.json` for what the suite cannot derive (design §5): a source file and the formatted/ignored file types and two
    raw coverage shards (node-ts), six event samples (claude-code), a merge command (github). The claude-code event samples moved into the adapter
    (`adapters/runtime/claude-code/events/`) because `tests/` is not vendored; the Cursor ones stay in `tests/fixtures/events/` until its adapter exists.
  - **A seam named for any host.** The host adapter's `protect`, `detectProtection` and `checkMerge` took `gh`; they take `cli(args, input) → { status, stdout, stderr }`
    now, so one check passes a stand-in to any host. The host contract states the signatures as built (`checkMerge`, not `checksGreen`) and the stack contract the real
    `merge(shards) → { artifacts, summary }` with `SHARD_FILE`.
  - **Skeletons** (`adapters/<axis>/_skeleton/`) are real: a manifest with every required role and `TODO` markers, stub modules that throw `TODO`, `conformance.json`,
    a README. A test copies each and checks the suite fails on a `TODO`. `selectFiles` now vendors the three skeletons, since the guide copies them.
  - **The guide** is `core/contracts/new-adapter.md` (steps, what each axis's checks are, the `conformance.json` fields); the procedure `new-adapter`
    (`core/procedures/`) is the short form, packaged as a skill and listed in the entry file's reading map.
  - **Broken fixtures** are copies of a preset edited by the test (a plan with no test step, a plan that names another package, a formatter that may download,
    CI jobs that skip `changes`, a merge that reports an unknown metric, a missing required role, a refused-push sample that is `ls`, a packaging that loses the
    trigger, a protection request without the required checks, a merge guard that accepts everything). Each fails the check that names the defect.
- **Problems / blockers / findings:**
  - **Found by the suite.** `node <path>/tools/harness.mjs …` does nothing, silently, with exit code 0, when `<path>` is behind a symbolic link (the temporary
    folder of macOS): `process.argv[1]` is the link, `import.meta.filename` the real path, and the check `resolve(process.argv[1]) === resolve(import.meta.filename)`
    is false. The runtime hooks (`guard-shell`, `guard-edit`, …) have the same guard, so a project under a linked path would have its hooks switched off without a
    message. The fixtures use real paths. Not fixed here; it is a task of the open-ended phase of this repository and of the framework (a `realpathSync` on `argv[1]`
    in `harness.mjs` and the hooks, with a test that runs the CLI through a link).
  - Selecting an adapter that lives in a project's own repository (`local:harness-adapters/…`, design §5 step 1) is not built; the guide says a new adapter is
    developed in a checkout of the framework and offered upstream. To decide for the framework's plan (task list of design §10, Phase 1).
  - The suite has run on the three presets only. The python preset (task 1.3 of the framework's plan) is its first real use as a new-adapter exercise.
