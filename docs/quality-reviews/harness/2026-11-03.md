### H-20261103-01 — Nothing automated scans the framework's core with this project's terms any more

- **Severity:** 🟡 · **Dimension:** D1, D7 · **Effort:** S · **Export impact:** helps
- **Evidence:**
  - `npm run docs:check` here prints "Checked 0 CORE files for stack terms, product terms and project values".
  - In pinned mode `frameworkCoreFolder` returns null ("pinned to a Git source … scanned upstream", `harness/tools/lib/core-scan.mjs:110-118`). This
    repository has no `layers.core` entries of its own.
  - Upstream, the framework's profile file has `terms.product: "(?!)"` (matches nothing). Its `terms.stack` lists `jest`, `npm`, `typescript`,
    `eslint`, `prettier`, `istanbul`, `node_modules` and `package.json`, and none of this project's stack terms.
  - The previous report measured "0 CORE problems in 14 files" in `docs:check`. `bindings.md:40-41` still says the scan runs here.
- **Why it matters:** the framework was extracted from this repository, so a leak of this product's words or tools is the likeliest leak. A future
  framework change could write "bot", "credits" or "Prisma" into `core/` and pass the framework's CI, the sync pull request and `docs:check` here.
  The first exit criterion of §3.5 holds today only because this review checked it by hand.
- **Fix (framework, open-ended phase):**
  - `harness check core` also scans the vendored `core/` in pinned mode, with the consuming project's `terms` and the adapters' terms. `check vendored`
    already proves the files are the tag's, so the scan costs milliseconds and runs on every push and every sync pull request.
  - A test: a pinned fixture whose profile lists a term that the vendored core contains fails `check core`.
  - Here: `bindings.md` §1 names the scan as the one that holds M1 and M2. That bindings text is part of H-04.

### H-20261103-02 — The claim rule does not say who owns a claim after its session ends

- **Severity:** 🟡 · **Dimension:** D9, D10 (coordination gap, D14) · **Effort:** S · **Export impact:** helps
- **Evidence:**
  - Method §6 (`harness/core/method/method.md:127-128`): "a task that has an open pull request belongs to the session that opened it, and nobody else
    starts it". Method §7 (lines 155–156): "An agent never starts a task that has an open pull request".
  - The same section §6 tells a session that continues a phase to "continue from the latest 'next step'", which is often a task that a paused
    session claimed. That is how every resumed task of this plan looks.
  - Probes on the same state (draft #283 open on the checked-out branch): P2 concluded "this session now continues it". P1 and P9 concluded "it belongs
    to another session; I must not touch it".
  - No document says how a session tells its own earlier claim (the session ended or paused) from a live claim of another agent.
- **Why it matters:** with one agent, a resumed session that obeys the rule literally refuses its own paused task, and the plan stalls. With several
  agents, a session that resolves it P2's way takes over a live task. Both readings are defensible from the text, so the outcome depends on the run.
- **Fix (framework, core method §6 and §7):** one rule. A claim belongs to its session while that session works. A session resuming a phase continues
  a claimed task when:
  - the task's log or the phase log records a pause or a "next step" that names it; or
  - the owner says so in the request.

  In every other case it asks. Also add the claimed-task case to the resume step of `start-task`.
