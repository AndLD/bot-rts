# Migration to 0.1.1 from 0.1.0

The notes of the framework's versions, one for each version from `0.1.1` on, for a project that takes a version from the previous one (several versions in a row: read each note, in order). A note says what needs a person's judgment; a change a tool can make is made by the tool.

## What changed for a project

- **The scan of the core runs in your project.** In a pinned project `harness check core` now scans the vendored `core/` with the project's own `terms` (stack, product, project values) and the terms of its adapters. Before, it scanned nothing there, so a word of your product or a tool name that reached the framework's core was seen by no one. It is part of `check all`.
- **The words the core uses on purpose are never reported.** `core/vocabulary.json` lists them (task, phase, plan, release, review, session, agent, and others); the scan skips them, and their plurals, whatever your term lists say.
- **A hit names the file, the line, the word and the ways out:** an ordinary word goes into `terms.productGeneric` (or a narrower `terms.stack` or `terms.projectValues`); a product, tool or project word is a leak of the framework, which you report and record as an exception.
- **Exceptions.** `terms.exceptions` of the profile file records such a hit: `{ "file", "word", "report", "version" }`, with the file as the scan prints it, the link to your report, and the framework version it holds for. `check core` accepts the hit while the lock is at that version, and fails on the exception after a sync to another version or when the hit is gone.
- **The report path.** The framework's repository has an issue template, "A word found in core", and its README says what happens to a report: a leak is a defect fixed in a patch release; an ordinary word is answered in your project.
- **Development versions.** The framework tags `<x.y.z>-dev.<n>` before the final tag of a release, so that you can sync it (`sync --to <version>`) and run `check all` before the release exists. `harness release --dev` sets such a version.
- **Migration notes.** This folder. The profile gains `release.migrations` (the folder of notes; `harness release` then refuses a version without its note, writes the areas into it and links it from the changelog), for a project that wants notes for its own releases.
- **The framework's own scan** (the profile of the framework repository) names more tools. It changes nothing in your project.

## Required actions

1. **Regenerate the managed files.** The procedure `release` changed, and a sync generates with the tools of the version you leave, so the skill of the procedure can be stale.
   Run `node harness/tools/harness.mjs sync --local`.
   Check: `node harness/tools/harness.mjs check generated` exits 0.
2. **Clear what the scan of the core reports.** Run `node harness/tools/harness.mjs check core`. For each hit:
   - an ordinary word of your product (a word that is not a name): add its alternative, spelled as in `terms.product`, to `terms.productGeneric`; for a stack term or a project value, make the term narrower;
   - a product, tool or project word that names something real: open an issue with the template "A word found in core", record `{ file, word, report, version }` in `terms.exceptions` (the version is the `version` of `harness.lock.json`), and stay on this version until a patch release fixes it.
   Check: `node harness/tools/harness.mjs check core` exits 0, and every entry of `terms.exceptions` has the link to its report.

## Optional actions

- Add `release.migrations` to your profile file if your project releases versions of its own and wants a note for each.
- To see a coming version early, sync its development tag in a scratch branch (`sync --to <x.y.z>-dev.<n>`), run `check all`, and report what it finds.

## How to verify

`node harness/tools/harness.mjs check all` exits 0, and `version` in `harness.lock.json` is `0.1.1`.
