# Migration to 0.3.0 from 0.2.0

The third minor version. It moves the order of the releases out of the plan index into a file of its own, adds **flows** (files of the plan that an orchestrator agent runs, step by step, to deliver releases), lets a project keep **adapters in its own repository**, and fixes defects found in use (four issues, I-8 to I-11). A project that ships no versions and starts no flow needs almost nothing from this version; the actions below say who needs what.

## What changed for a project

- **The release order has a file of its own** (5.1). A project that ships versions names it in the new profile role `paths.releases` (this repository uses `docs/development-plan/releases.md`): one table `Release | Status | Tasks, in order | Consumers | Notes` and a list "Not scheduled", from the template `core/plan/releases-template.md`. The tools read the order of the tasks from it instead of the section "Order of development" of the plan index; the index shows the current and the next release in a generated block that links to the file. The script of this version moves a table of the section into the file, sets the role and leaves the block in the index. **An order written as prose** (arrows of phase numbers) cannot be read by a tool and is left as it is, with a message. `check plan` refuses a backlog item and an unknown id in the file.
- **Flows** (5.2, 5.4). With `paths.flows` (default `docs/development-plan/flows`, and only where there is a releases file), a flow is a file `flow-<n>-<slug>.md` — a settings block and a table of steps (`tasks`, `cut`, `consumer-take`, `triage-fix`, `decision`, `custom`) that delivers one or more releases — with its append-only log beside it. The new procedure `run-flow` (and its skill) says how an orchestrator runs one: decision levels D0 to D4, the modes `brainstorm` (asks the owner from `askAt` up, D2 by default) and `seamless`, the hard limits no mode crosses, the step report a worker ends with, and the unbiased analysis. `harness flow check` (also in `check all`), `status`, `next` and `prompt` read a flow against the repository, not against its State column. The resume phrases may name flows ("Run flow N").
- **The authority of a flow** (5.3, a change of the meaning of core rules, approved by the owner). A flow the owner started may cut releases and answer or close reports at the levels its settings give them (a development version D1, a final release or a hotfix D3, reports D4 by default), for its home repository only. The rule `agent.ask-merge` of the entry file lets such an orchestrator approve the merge of a release or hotfix pull request by merge commit once the required checks are green; the shell guard still refuses auto-merge and an administrator's bypass there. Nothing changes outside a flow.
- **Executors: the runtime-adapter contract is at version 2** (5.5). The new **required logic role `executors`** (`executorsFor(profile)`) says how an orchestrator starts a worker with a model and an effort, continues it, fetches its full report and reads its context: `session`, `subagent` or `manual`. The Claude Code preset maps the desktop app's sessions and the command line; the Cursor preset offers `manual` only. `harness flow dispatch` picks the executor, decides whether the previous step's worker continues it (`reuse: auto`, within `reuseLimits`), and prints the means. **A local runtime adapter must now fill the role** (below).
- **Usage** (5.6, 5.7). The optional runtime role `usage` reads the account's windows and carries a table of coefficients (provisional until measured). `harness flow estimate`, `gate` (GO, WAIT until a reset, STOP, ASK) and `sample` (appends to the flows' `usage.jsonl`), and `harness flow calibrate`, which proposes new coefficients and whether a warm start pays off and writes nothing. The flow settings `usage` gain `safetyFactor` and `maxWaitMinutes`.
- **Flows across repositories** (5.8). A flow's `repos` setting names external repositories as rows (`remote`, `role`, `kinds`); their folders are in the ignored `harness-profile.local.json`. The orchestrator only starts a worker there, and `flow status` reads the consumer's lock and pull requests through the **new optional host role `remote-state`** (the GitHub preset reads them with `gh`). The `repos` setting of 5.4 (a map of aliases to paths) is gone; nothing used it.
- **Adapters of a project's own repository** (3.4). A folder `harness-adapters/<axis>/<name>/` that the profile file selects as `local:<name>` is loaded like a preset; a sync and `migrate` leave it alone, `check adapters` holds its manifest to the contract, and the new check `local-adapters` runs the conformance suite on it. `harness migrate` stops before it commits when a local adapter no longer meets the contract.
- **Fixes.** A push from a linked Git worktree no longer lets the gate's tests rewrite the repository's Git config (I-8; a repository already damaged needs `git config core.bare false` and its `core.hooksPath` set back by hand). A condition inside a line of a procedure is rendered instead of copied into the generated skills (I-9). A flow continued from another account no longer resumes a worker that account cannot find (I-10): the log's "step started" line gains an `Account:` field. A worker that a flow starts on the command line is no longer refused every edit and command (I-11): the flow settings gain `permissions` (`{ "mode": "<a mode of the runtime>", "allow": ["<a tool by name>"] }`, in the runtime's own words, absent by default), which the Claude Code preset turns into `--permission-mode` and `--allowedTools`; `harness flow dispatch` prints what a worker will be allowed and warns when nothing is set, and `harness flow check` checks the setting. A session the desktop app starts runs under the app's own permission settings and is not affected. Smaller fixes of the flow tools: after a step that the orchestrator ran itself the next step may continue the previous worker, and `harness flow status` counts a pull request of an external repository as taking a version only when its title names it.

## Required actions

1. **Take the migration.** Run `sync` on a branch of its own, then `node harness/tools/harness.mjs migrate` if the `sync` did not start it. The script of this version moves a table of the "Order of development" section of your plan index into the releases file and sets `paths.releases`. If you ship no versions, it changes nothing.
   Check: `node harness/tools/harness.mjs check generated` exits 0, and `migrations.version` in `harness.lock.json` is `0.3.0`.
2. **If your order of development is prose** (arrows of phase numbers, not a table), write it as the table of `harness/core/plan/releases-template.md` in the file named by `paths.releases` (`docs/development-plan/releases.md` by default), set the role, and run `node harness/tools/harness.mjs plan summary`. The migration says when this applies and leaves the section as it was.
   Check: `node harness/tools/harness.mjs check plan` exits 0.
3. **If you have a local runtime adapter** (`harness-adapters/runtime/<name>/`): fill the new required role `executors`. Copy `executors.mjs` from `harness/adapters/runtime/_skeleton/` and return `{ manual }` when the runtime offers no automation; add the role to the manifest and set `"contract": 2`. A local stack or host adapter needs nothing.
   Check: `node harness/tools/harness.mjs check local-adapters` exits 0.
4. **Say your resume phrases and your plan documents.** If you will use flows, add "Run flow N", "Run flows N–M" and "Continue flow N" to `plan.resumePhrases` of the profile file, and `paths.flows` (the index is created by `plan summary`); a document of yours that restates the order of development as a section of the plan index, or the rule that every release cut and every answer to a report is the owner's, now restates a changed rule: link to the core document instead.
   Check: `node harness/tools/harness.mjs check all` exits 0.

## Optional actions

- **Start your first flow.** Copy `harness/core/plan/flow-template.md` to `<paths.flows>/flow-1-<slug>.md` and its log from `flow-log-template.md`, name the releases it delivers (each a row of your releases file, declared by at most one flow), list the steps, and run `node harness/tools/harness.mjs flow check`. The defaults (brainstorm mode, session executor, `reuse: auto`) are the safe ones. Then say "Run flow 1". A step in another repository (a consumer taking a version) needs a `Repo` column, a row in `repos`, and the folder in the ignored `harness-profile.local.json` (`{ "repos": { "<alias>": "../<folder>" } }`).
  Check: `node harness/tools/harness.mjs flow status 1` prints the next step.
- **Tell the tools your subscription**, so that `harness flow estimate` and the check of oversized steps use your table: `{ "usage": { "subscription": "pro" } }` in the ignored `harness-profile.local.json` (`pro`, `max5x`, `max20x` or `api` for Claude Code).
  Check: `node harness/tools/harness.mjs flow estimate 1` names the subscription.
- **Say what a worker of a flow may do.** If a flow starts workers on the command line (`claude -p`), set `permissions` in its settings block (for the Claude Code preset, for example `{ "mode": "acceptEdits", "allow": ["Bash(git *)", "Bash(gh *)", "Bash(npm *)", "Bash(node *)"] }`): without it such a worker has no one to answer a permission prompt and reports itself blocked at its first edit. The choice is the owner's. A local runtime adapter may add an optional `permissions` operation to an executor.
  Check: `node harness/tools/harness.mjs flow dispatch 1 1` prints what the worker will be allowed, and no warning that it will be refused.
- Adapters of your own repository: see the guide `harness/core/contracts/new-adapter.md` and the procedure `new-adapter`.

## How to verify

```bash
node harness/tools/harness.mjs check all
node harness/tools/harness.mjs flow check
node harness/tools/harness.mjs probes 0.2.0 0.3.0
```

The first two exit 0 on a healthy project; the third lists the probes whose areas this version touched (the mode of `probes.run` decides whether to run them).
