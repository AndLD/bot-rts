# Migration to 0.3.0 from 0.2.0

The third minor version. It moves the order of the releases out of the plan index into a file of its own, adds **flows** (files of the plan that an orchestrator agent runs, step by step, to deliver releases), lets a project keep **adapters in its own repository**, and fixes defects found in use (seven issues: I-8 to I-13 and I-15). A project that ships no versions and starts no flow needs almost nothing from this version; the actions below say who needs what, and the last required action names the known limits of what the notes and the migration say.

## What changed for a project

- **The release order has a file of its own** (5.1). A project that ships versions names it in the new profile role `paths.releases` (this repository uses `docs/development-plan/releases.md`): one table `Release | Status | Tasks, in order | Consumers | Notes` and a list "Not scheduled", from the template `core/plan/releases-template.md`. The tools read the order of the tasks from it instead of the section "Order of development" of the plan index; the index shows the current and the next release in a generated block that links to the file. The script of this version moves a table of the section into the file, sets the role and leaves the block in the index. **An order written as prose** (arrows of phase numbers) cannot be read by a tool and is left as it is, with a message. `check plan` refuses a backlog item and an unknown id in the file.
- **Flows** (5.2, 5.4). With `paths.flows` (default `docs/development-plan/flows`, and only where there is a releases file), a flow is a file `flow-<n>-<slug>.md` — a settings block and a table of steps (`tasks`, `cut`, `consumer-take`, `triage-fix`, `decision`, `custom`) that delivers one or more releases — with its append-only log beside it. The new procedure `run-flow` (and its skill) says how an orchestrator runs one: decision levels D0 to D4, the modes `brainstorm` (asks the owner from `askAt` up, D2 by default) and `seamless`, the hard limits no mode crosses, the step report a worker ends with, and the unbiased analysis. `harness flow check` (also in `check all`), `status`, `next` and `prompt` read a flow against the repository, not against its State column. The resume phrases may name flows ("Run flow N").
- **The authority of a flow** (5.3, a change of the meaning of core rules, approved by the owner). A flow the owner started may cut releases and answer or close reports at the levels its settings give them (a development version D1, a final release or a hotfix D3, reports D4 by default), for its home repository only. The rule `agent.ask-merge` of the entry file lets such an orchestrator approve the merge of a release or hotfix pull request by merge commit once the required checks are green; the shell guard still refuses auto-merge and an administrator's bypass there. Nothing changes outside a flow.
- **Executors: the runtime-adapter contract is at version 2** (5.5). The new **required logic role `executors`** (`executorsFor(profile)`) says how an orchestrator starts a worker with a model and an effort, continues it, fetches its full report and reads its context: `session`, `subagent` or `manual`. The Claude Code preset maps the desktop app's sessions and the command line; the Cursor preset offers `manual` only. `harness flow dispatch` picks the executor, decides whether the previous step's worker continues it (`reuse: auto`, within `reuseLimits`), and prints the means. **A local runtime adapter must now fill the role** (below).
- **Usage** (5.6, 5.7). The optional runtime role `usage` reads the account's windows and carries a table of coefficients (provisional until measured). `harness flow estimate`, `gate` (GO, WAIT until a reset, STOP, ASK) and `sample` (appends to the flows' `usage.jsonl`), and `harness flow calibrate`, which proposes new coefficients and whether a warm start pays off and writes nothing. The flow settings `usage` gain `safetyFactor` and `maxWaitMinutes`.
- **Flows across repositories** (5.8). A flow's `repos` setting names external repositories as rows (`remote`, `role`, `kinds`); their folders are in the ignored `harness-profile.local.json`. The orchestrator only starts a worker there, and `flow status` reads the consumer's lock and pull requests through the **new optional host role `remote-state`** (the GitHub preset reads them with `gh`). The `repos` setting of 5.4 (a map of aliases to paths) is gone; nothing used it.
- **Adapters of a project's own repository** (3.4). A folder `harness-adapters/<axis>/<name>/` that the profile file selects as `local:<name>` is loaded like a preset; a sync and `migrate` leave it alone, `check adapters` holds its manifest to the contract, and the new check `local-adapters` runs the conformance suite on it. `harness migrate` stops before it commits when a local adapter no longer meets the contract.
- **Fixes.** A push from a linked Git worktree no longer lets the gate's tests rewrite the repository's Git config (I-8; a repository already damaged needs `git config core.bare false` and its `core.hooksPath` set back by hand). A condition inside a line of a procedure is rendered instead of copied into the generated skills (I-9). A flow continued from another account no longer resumes a worker that account cannot find (I-10): the log's "step started" line gains an `Account:` field. A worker that a flow starts on the command line is no longer refused every edit and command (I-11): the flow settings gain `permissions` (`{ "mode": "<a mode of the runtime>", "allow": ["<a tool by name>"] }`, in the runtime's own words, absent by default), which the Claude Code preset turns into `--permission-mode` and `--allowedTools`; `harness flow dispatch` prints what a worker will be allowed and warns when nothing is set, and `harness flow check` checks the setting. A session the desktop app starts runs under the app's own permission settings and is not affected. The migration of this version no longer writes prose into the release table (I-12, I-15): of an old table's cell only the ids the tools read stay in "Tasks, in order" (a task, "Phase N" of a phase that exists, an issue), and only those of the part of the cell that lists tasks (its start: ids, `,` `;` `+`, "then", "and" and notes in brackets), so a phase that the words later in the cell only mention ("Phase 17 is closed") is not taken and a cell that opens with words gives no id; the whole cell and the words around the ids go to "Notes", the sentence that stood before the old table and ended in its colon is closed with a full stop, a release skipped on purpose (a row with no task whose words say "skip") gets the new status ⏭ and is never "next", and an order of phases written as arrows beside the table is kept in "Notes" with a message that says how to keep it. The first `check all` after the take no longer fails on its own account (I-13): the releases file is put in the layer that claims the plan index (or the migration prints the layer to add), the ordinary word "base" of `core/plan/README.md` is reworded so a project whose product terms name it is not failed by the vendored copy, and the note and the procedure `update-framework` say that the first gate after a take runs every suite of the project. Smaller fixes of the flow tools: after a step that the orchestrator ran itself the next step may continue the previous worker, and `harness flow status` counts a pull request of an external repository as taking a version only when its title names it.

## Required actions

1. **Take the migration.** Run `sync` on a branch of its own, then `node harness/tools/harness.mjs migrate` if the `sync` did not start it. The script of this version moves a table of the "Order of development" section of your plan index into the releases file and sets `paths.releases`. If you ship no versions, it changes nothing. In the new table only task ids stay in "Tasks, in order", and they are read only from the part of an old cell that lists tasks (its start: ids, separators, "then", "and" and notes in brackets); the whole cell goes to "Notes", so **a cell that opens with words gives no id** and a phase that the words later in the cell only mention is not taken. A release you skipped on purpose gets the status ⏭, which keeps it out of "next". Read the messages it prints and review both columns.
   **The framework's own tests leave `harness/`.** If you never ran the optional second `sync` of `0.2.0` (the one that drops the framework's copied `*.test.mjs` files from `harness/`), this take deletes them: some sixty files (64 in a project that selects the stack `node-ts`, the runtime `claude-code` and the host `github`: 51 of `tools/` and 13 of those adapters; the count follows your adapters). That is the change of `0.2.0` ("`sync` no longer copies the framework's tests", `excluded` in `framework.json`) reaching your copy, and not a fault; review the deletions as part of the take. Check: `find harness -name '*.test.mjs'` prints nothing after the take.
   A project with a layer map of its own (`layers` in the profile file) gets the releases file in the layer that claims its plan index; the script says so, or prints a required action to add the file to a layer by hand. Check: `node harness/tools/harness.mjs check layers` exits 0.
   The first `check all` scans the vendored core with your own `terms`: a generic word of the core that your product terms also name (the version reworded "base", the one known case) is a failure of your project, not of the version; list the word in `productGeneric` of your terms, or report it, and do not edit the vendored copy.
   **Cost of the first gate:** a take changes `harness/**`, which a gate that decides by changed path counts as code, so the first push gate and the CI run of the take run every suite of the project, which can take minutes and need the services they use; run it once on purpose.
   Check: `node harness/tools/harness.mjs check generated` exits 0, and `migrations.version` in `harness.lock.json` is `0.3.0`.
2. **If your old order of development had prose in its cells, review the releases table the migration wrote.** The migration reads ids only from the part of an old cell that lists tasks, so check each row of `paths.releases` by hand against the old section: (a) each id stands under the release that holds it. This version's script does not take a phase that the old words only mention ("Phase 17 is closed"), but `check plan` accepts a wrong id wherever it came from, so only you can see one: a table that `0.3.0-dev.1` or `-dev.2` wrote (their script read the whole cell, and the script does not write a table that exists) may hold such ids. Move the id to the right release, or delete it from the wrong one. (b) **A row whose old cell opened with words** (for example "taken by task 17.18 …") gets **no ids and the status ⬜**, because there is no listing to read, and the plan index then calls such a release, even one long taken, the next one until you give the row its ids and its status (✅, or 🏷) by hand: look at every row whose "Tasks, in order" is empty. A release you skipped on purpose has the status ⏭ (the migration sets it for a row with no task whose words say "skip"; set it by hand on another row, and set 🏷 by hand on a release whose development version is tagged upstream: the script cannot know). (c) The sentence of the old section that ended in a colon where the table stood is closed with a full stop; read it in "Notes" and drop it if it says nothing now.
   Check: `node harness/tools/harness.mjs check plan` exits 0, and `node harness/tools/harness.mjs plan summary` names, in the block of the plan index, the release you expect next.
3. **If your order of development is prose** (arrows of phase numbers, not a table), write it as the table of `harness/core/plan/releases-template.md` in the file named by `paths.releases` (`docs/development-plan/releases.md` by default), set the role, and run `node harness/tools/harness.mjs plan summary`. The migration says when this applies and leaves the section as it was. The same message comes when a table is moved and an order of phases written as arrows stood beside it: the arrows are kept as text in "Notes" and are not read, so name the phases as "Phase N" in the table to keep that order.
   Check: `node harness/tools/harness.mjs check plan` exits 0.
4. **If you have a local runtime adapter** (`harness-adapters/runtime/<name>/`): fill the new required role `executors`. Copy `executors.mjs` from `harness/adapters/runtime/_skeleton/` and return `{ manual }` when the runtime offers no automation; add the role to the manifest and set `"contract": 2`. A local stack or host adapter needs nothing.
   Check: `node harness/tools/harness.mjs check local-adapters` exits 0.
5. **Say your resume phrases and your plan documents.** If you will use flows, add "Run flow N", "Run flows N–M" and "Continue flow N" to `plan.resumePhrases` of the profile file, and `paths.flows` (the index is created by `plan summary`); a document of yours that restates the order of development as a section of the plan index, or the rule that every release cut and every answer to a report is the owner's, now restates a changed rule: link to the core document instead.
   Check: `node harness/tools/harness.mjs check all` exits 0.
6. **Know the limits of what this version says** (recorded as I-16 of the framework's issue queue, to be fixed in a later version). They are about the notes and the messages of the migration, and none blocks a take; do not trust the table the migration wrote until you have read it (action 2).
   - `harness migrate` prints the notes of the versions between the two and may leave this note out when only development versions lie between (a take of `0.3.0-dev.2` points to this note, which `migrate` does not print), so read `migrations/0.3.0.md` of the vendored copy (or of the framework's repository) by hand in that case.
   - The check `migrations.version` is `0.3.0` of action 1 is a check of the final version: after a development version of `0.3.0` the lock names that development version.
   - An order of phases written as arrows that no release of your table holds (the history of a consumer) is left as text in "Notes", and that is all there is to do; the message of the migration calls it a "Required action" although nothing is to be done. Naming the phases as "Phase N" (action 3) is only for the phases a release holds.
   - The statuses 🏷 (a release whose development version is tagged upstream) and ⏭ (a release skipped on purpose, on a row the script does not set it for) are set by hand (action 2).
   Check: you have read `migrations/0.3.0.md` and the table of `paths.releases` once; `node harness/tools/harness.mjs check plan` exits 0.

## Optional actions

- **Start your first flow.** Copy `harness/core/plan/flow-template.md` to `<paths.flows>/flow-1-<slug>.md` and its log from `flow-log-template.md`, name the releases it delivers (each a row of your releases file, declared by at most one flow), list the steps, and run `node harness/tools/harness.mjs flow check`. The defaults (brainstorm mode, session executor, `reuse: auto`) are the safe ones. Then say "Run flow 1". A step in another repository (a consumer taking a version) needs a `Repo` column, a row in `repos`, and the folder in the ignored `harness-profile.local.json` (`{ "repos": { "<alias>": "../<folder>" } }`).
  Check: `node harness/tools/harness.mjs flow status 1` prints the next step.
- **Tell the tools your subscription**, so that `harness flow estimate` and the check of oversized steps use your table: `{ "usage": { "subscription": "pro" } }` in the ignored `harness-profile.local.json` (`pro`, `max5x`, `max20x` or `api` for Claude Code).
  Check: `node harness/tools/harness.mjs flow estimate 1` names the subscription.
- **Say what a worker of a flow may do.** If a flow starts workers on the command line (`claude -p`), set `permissions` in its settings block (for the Claude Code preset, for example `{ "mode": "acceptEdits", "allow": ["Bash(git *)", "Bash(gh *)", "Bash(npm *)", "Bash(node *)"] }`): without it such a worker has no one to answer a permission prompt and reports itself blocked at its first edit. The choice is the owner's. A local runtime adapter may add an optional `permissions` operation to an executor.
  Check: `node harness/tools/harness.mjs flow dispatch 1 1` prints what the worker will be allowed, and no warning that it will be refused.
- Adapters of your own repository: see the guide `harness/core/contracts/new-adapter.md` and the procedure `new-adapter`.

## How to verify

```bash
node harness/tools/harness.mjs check all
node harness/tools/harness.mjs flow check
node harness/tools/harness.mjs probes 0.2.0 0.3.0
```

The first two exit 0 on a healthy project; the third lists the probes whose areas this version touched (the mode of `probes.run` decides whether to run them).
