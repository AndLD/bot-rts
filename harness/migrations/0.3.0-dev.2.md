# Migration to 0.3.0-dev.2 from 0.3.0-dev.1

The second development version of `0.3.0`. It fixes what the first take of `0.3.0-dev.1` found in the migration of `0.3.0` (I-12 and I-13) and adds nothing else. The note of the final version, `0.3.0.md`, tells the whole story from `0.2.0` and is finished with that version, so a project that takes `0.3.0` after this one reads that note, and this one stays as it is. A project that takes this version straight from `0.2.0` reads `0.3.0.md` for what the version is, and this note only for what differs from `0.3.0-dev.1`.

## What changed for a project

- **The releases table the migration writes is readable by the tools** (I-12). Of a cell of the old table, only the ids the tools read (a task of a phase, "Phase N" of a phase that exists, an issue) go into "Tasks, in order"; the words around them go to "Notes", and the migration says so. A release you skipped on purpose (a row with no task whose words say "skip") gets the new status ⏭, which is in the legend of the releases template and is never "next" in the plan index. An order of phases written as arrows beside the table is kept in "Notes", where the tools do not read it, and the migration now prints a required action about it. **This is a change of the script, and `0.3.0-dev.1` already wrote your table**: its script has the role set now, so it does not write the table again (see required action 2).
- **The releases file joins a layer** (I-13). A project with a layer map of its own (`layers` in the profile file) gets the releases file in the layer that claims its plan index, or a required action that names what to add by hand. The script of `0.3.0` runs again for each development version, so taking this version from `0.3.0-dev.1` does this for you.
- **The core no longer uses the word "base" in `core/plan/README.md`**, so a project whose product terms name "base" is not failed by the scan of its vendored core (`check core`, part of `check all`). Taking this version brings the reworded line.
- **The cost of the first gate is said** (I-13), in the procedure `update-framework` and in the note of `0.3.0`: a take changes `harness/**`, which a gate that decides by changed path counts as code, so the first push gate and the CI run of each take run every suite of the project. **Taking this version is another take, so the cost comes again**; run the gate once on purpose.

## Required actions

1. **Take the version.** Run `sync` on a branch of its own, then `node harness/tools/harness.mjs migrate` if the `sync` did not start it. Read what the migration prints: it adds the releases file to the layer of your plan index, or prints a required action to do it by hand.
   Check: `node harness/tools/harness.mjs check layers` and `check generated` exit 0, and `migrations.version` in `harness.lock.json` is `0.3.0-dev.2`.
2. **If you took `0.3.0-dev.1`, review the releases file it wrote, by hand.** The script does not rewrite a table that exists, so the table of `dev.1` keeps what it wrote. For each row: only task ids stay in "Tasks, in order" (the words go to "Notes"); a release you skipped on purpose gets the status ⏭ (add it to the legend line of the file if it is not there); an order of phases that stood beside the table as arrows is named as "Phase N" in the table, or it is no longer read. A project that already repaired the table by hand, or whose cells hold only ids, has nothing to change. To see what the fixed script writes, run it on a scratch branch taken from the state before the take (a fresh take from `0.2.0`); do not replace a table you have repaired with it.
   Check: `node harness/tools/harness.mjs check plan` exits 0, and `node harness/tools/harness.mjs plan summary` names the release you expect as the next one.

## Optional actions

- **Remove a workaround for "base".** If you listed the word in `productGeneric` of your `terms` to pass `check core` on `0.3.0-dev.1`, you may remove it once the reworded line is in your copy; leaving it does no harm.
  Check: `node harness/tools/harness.mjs check core` exits 0.

## How to verify

```bash
node harness/tools/harness.mjs check all
node harness/tools/harness.mjs probes 0.3.0-dev.1 0.3.0-dev.2
```

The first exits 0 on a healthy project, and `version` in `harness.lock.json` is `0.3.0-dev.2`; the second lists the probes whose areas this version touched (the first gate after the take runs every suite of the project, as said above).
