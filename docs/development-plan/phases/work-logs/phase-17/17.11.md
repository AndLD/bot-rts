### 2026-11-02 — the hooks, the Git guards and the Claude Code preset
- **Branch:** `chore/17.11-runtime-hooks` — done. The claim was opened first; the code was written while 17.10's CI ran and moved onto this branch
  once 17.10 had merged.
- **Decisions / deviations from the plan:**
  - **The four hooks are the framework's** (`tools/runtime-hooks/`, vendored): the shell parser and the refusals of `hook-guard-bash` are
    `tools/lib/guard.mjs` (its tests moved with it), and the hooks read their values from the profile file (the protected branches, the phases folder,
    the method). `scripts/hook-*.mjs` and their tests are gone; `.claude/settings.json` calls the vendored scripts.
  - **`io.mjs` holds both runtimes' forms** instead of a module per adapter: a vendored copy has only the selected adapters, and the hooks must read
    either runtime's event. So the contract role `hook-io` is optional, and a new runtime adds its form to `io.mjs`. Events are read by what they do
    (`shell`, `edit-before`, `edit-after`, `session-start`); Cursor is recognised by `cursor_version`, in native and compat mode. A hook script says
    what it is for, so an event that does not name itself is still read.
  - **Samples.** `tests/fixtures/events/` holds the events of both runtimes. The Claude Code ones have the shape Claude Code sends; the Cursor ones
    are written from Cursor's documentation (design §9), not recorded in a live session, which the owner's Cursor proof checks (task 1.5 of the
    framework's plan). The preset for Cursor itself is that plan's task 1.2.
  - **`--no-verify`** is refused by `guard-shell` for `git push` and for `git commit` (`--no-verify`, `-n`, and short flags that contain it). 12.4
    was merged first, so the gate runs in every worktree (H-20261030-02).
  - **The Git guards.** `tools/git-hooks/pre-commit` refuses a commit on a protected branch and lets the root commit of a new repository through;
    `pre-push` runs the vendored check first (before anything else, as 17.4 requires), then the protected-ref and deleted-ref guard, then the project's
    `hooks.prePushSetup` (here `scripts/pre-push-setup.sh`, the `.env` and the database addresses), then `harness gate`. This repository's
    `.githooks/` folder is two shims that run them, so a checkout whose `core.hooksPath` is `.githooks` needs no new setting.
  - **The merge guard** (`adapters/host/github/merge-guard.mjs`) reads the checks with `gh pr checks --json name,bucket`: every required check
    must be `pass` or `skipping`, and checks that cannot be read refuse the merge. It runs only when `host.protection` is false; this repository's
    host protects, so it is tested with a stand-in `gh` and a profile that says otherwise.
  - **`access.denyRead`** (new profile role, default `.env`, `.env.*`, `!.env.example`, `*.pem`, `*.key`) becomes `Read(...)` deny rules in
    `.claude/settings.json`: a pattern without a slash at any depth, a carve-out as a rule of its own. **Not verified in a live Claude Code
    session**: whether `Read(!**/.env.example)` is honoured as a carve-out, and whether the rules apply as the design says. If the carve-out is not
    honoured, `.env.example` cannot be read by the agent and the rule needs another form; the owner's next session shows it.
  - **The generated rule-map rows** (`tools/lib/rule-map.mjs`): a managed block in `docs/engineering/rule-checks.md`, built from the `enforces`
    declarations of the manifests (early, local, remote; a `condition` for a host that protects or cannot) and the framework's Git hooks. A rule that
    nothing declares is judgment, and one held only in part is "partly" (`nn.secrets`: nothing scans committed content). Both protection cases
    are tested. Rows 27, 32 and 93 of the hand-written table now say what really holds them, and rows 10, 13, 14, 33 and 95 name the new hooks.
  - **`harness check scaffold`** also holds the runtime's configuration: a missing hook entry or `Read(...)` deny rule fails it.
