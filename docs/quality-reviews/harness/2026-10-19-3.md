### D3 Injection and parametrization — 5

Every H-17 site is re-opened and closed:
- `release.yml:23-24` reads `paths.changelog` through `harness-profile.mjs`. The "no value spelled out" test now reads every workflow, and a
  second test refuses a branch name in a workflow outside its `branches:` trigger.
- `requiredChecks` is a list in `harness-profile.json`, and `protect-branches.sh` builds the ruleset from it. One test compares the list with
  the job names of the profile's row. Another runs the script against a stand-in `gh` and compares the checks and branch refs it sends.
- Rule-map rows 11 and 13, `DEPLOYMENT.md`, `testing/README.md` and `e2e-matrix.md` say "the production branch" and "the integration branch".
  `RELEASING.md` uses `<production>` and `<integration>`, with one line that names the profile and the command that prints the values. A test
  scans the three adapter folders outside fenced blocks.

The anchor for 5, "every value lives once, rules cite roles", holds for the rules, the adapters and the tooling. To rename the integration
branch you edit `harness-profile.json` and the profile table, and the CI triggers fail a test until they match. What a rename would still miss
is in the profile layer itself, where values are allowed. The review bindings copy the branch name into seven lines of commands and prompts,
although the profile says a binding "links to its row instead of copying it". The branch rows of `profile.md` are also not compared with the
profile file, while the required checks are (H-22). Each copied command would fail loudly on a renamed branch. This is maintainability, and it
does not hold the score.

**Keep:** the pattern "value in the profile file, a reader script, and a test for every place that cannot read it" (CI triggers, the profile
table, the protection script's output).
