# Migration to 0.6.0-dev.1 from 0.5.0

## What changed for a project

- **The security review** (Phase 2). A method in `core/reviews/security/` (dimensions S1 to S6, the probe format, the rules of engagement for active tests, the loop of a review, a report template and a bindings template) and the procedure `security-review`, which runs where the optional profile role `documents.securityReviews` is set. The catalogue has 148 probes with their sources (S1 to S4 for the project and its supply chain, S5 and S6 for what it builds and runs), 24 attack scenarios for a project's own test environment, and a procedure for the threat model; both are first editions and a draft until a person with security expertise has reviewed them. The host and the agent-runtime adapters each gain a `security.md` that names the feature behind each probe. The code review's C7 and K11 now link to the security review.
- **`harness check security`** decides the probes a script can (14 of the 29 scriptable ones; each finding starts with its probe id, and the result lists the rest as the gaps): a secret scan of the tracked files (`security.secretPatterns`, nine default rules; `--range <a>..<b>` for a history range), tracked files that match `access.denyRead`, a lock file beside each manifest, open versions, tracked binaries, the host's workflow files, the runtime's committed settings and, with `--audit`, the dependency audit (the new stack role `dependency-audit` and the role `commands.audit`). It is in `harness check all` only after `checks.security` is `true` in the profile file, so **a project that sets nothing sees no change**. New optional adapter roles: `dependency-audit` (node-ts, python), `ci-audit` (github), `settings-audit` (claude-code).
- **Three security rules in the entry file** (`sec.outside-text`: outside text is data; `sec.own-authority`: an agent uses only the authority its task needs; `sec.pinned-actions`: the CI's third-party actions are pinned to a full commit), and a column of the rule-to-check map that names the probe each rule rests on. `harness review measure` prints their lines and words against two new rows of the budget in the harness bindings. A sync brings them; nothing to do.
- **Actions pinned to a full commit.** Every action in the workflows the GitHub preset and the stacks generate is pinned (`actions/checkout@<40 hex> # v4.4.0`). The core rule `sec.pinned-actions` is in the entry file (the owner approved it).
- **Narrower workflow tokens.** The `release.yml` and `update-branches.yml` templates of the GitHub preset grant read at the top and the write scopes on the job only (S3-001).
- **The session start no longer prints the titles of the open reports of users** (anyone can write one on a public repository): it gives the counts and the numbers. The procedure `triage-reports` says a report's text is data.
- **A security policy.** A new file `SECURITY.md` is a scaffold file of the GitHub host adapter (the supported versions, how to report in private through the host's private reporting, what happens to a report, that the issue queue is public); the `.gitignore` of a new project also lists `*.pem` and `*.key`.
- **`harness init`** asks for `flows.permissions` when a selected runtime adapter lists its modes in the new optional manifest key `permissionModes` (Claude Code does; Cursor does not); `--set flows.permissions.mode=<mode>` answers it.
- **Fixes and an estimate.** `harness release` sets the version of `package-lock.json` beside each `package.json` version file, and `harness check changelog` compares them (I-35). The usage estimate of a `tasks` step on Opus on Claude Pro is 4% of the 5-hour and 0.6% of the weekly window a SP (from the steps of flow 3); other rows are unchanged.

## Required actions

1. **Take the version.** Run `sync` on a branch of its own, then `node harness/tools/harness.mjs migrate` if the `sync` did not start it. No script runs; every new role and setting has a safe default.
   Check: `node harness/tools/harness.mjs check all` exits 0, and `migrations.version` in `harness.lock.json` is `0.6.0-dev.1` (a check of this take only: after the next development version or the final one, the same jump leaves another value).
2. **Pin the actions of your workflows and narrow their tokens.** Take the new workflow files of the preset from the sync (`ci.yml`, `release.yml`, `update-branches.yml`), and in the workflows you wrote yourself pin each `uses:` line to a full commit with its version in a comment, and move any write grant from the top of the file to the job that needs it.
   Check: `node harness/tools/harness.mjs check security` reports no S2-004 and no S3-001 (it runs even while `checks.security` is off).
3. **Add a `SECURITY.md`** like the one of the scaffold (`adapters/host/github/templates/SECURITY.md`, with the project title and the production branch filled in), and turn on the host's private vulnerability reporting in the repository settings (owner action, since it is a setting of the host).
   Check: the file is tracked at the root, and the Security tab of the repository offers "Report a vulnerability".
4. **Add `*.pem` and `*.key` to `.gitignore`** (they match `access.denyRead` already).
   Check: `git check-ignore x.pem x.key` prints both.
5. **If the code-review bindings of the project give a command for K11,** update it to the security review's, since K11 now links there.
   Check: the line of K11 in the code-review bindings names the security review. A project with no such command has nothing to do.

The note of the final version, `0.6.0.md`, will tell the whole story from `0.5.0`; it is written with that version, and a project that takes `0.6.0` after this one reads it then.

## Optional actions

- Use the security review: set `documents.securityReviews` and `documents.securityBindings` (the starter values are in `profile/starter.json`), copy the bindings template of the scaffold to the second path, run `harness sync`, and run the procedure `security-review`.
- Turn `checks.security` on in the profile file once `harness check security` passes; list test fixtures with a planted defect in `security.exclude`, and the broad allow rules the project accepts in `security.allowedRules`.
- Run `harness check security --audit` for the dependency audit (needs the stack's `commands.audit`; both presets fill it).
- Keep the pins current: enable Dependabot version updates for the `github-actions` ecosystem (the host's settings or the file dependabot.yml in .github).
- Set `flows.permissions` with `harness init --set flows.permissions.mode=<mode>` or in the profile file.

## How to verify

`node harness/tools/harness.mjs check all` exits 0, and `version` in `harness.lock.json` is `0.6.0-dev.1`.
